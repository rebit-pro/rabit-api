# E5 — заказ, снимок покупки и личный ключ

## Цель

Покупатель оформляет заказ из проверенного серверного расчёта (COM-10) и открывает его по личному ключу (COM-11). Организатор и куратор ищут заказы своей области и открывают служебную карточку (COM-12, COM-13). Заказ хранит неизменяемый снимок состава, цен, подарка и скидок; личный ключ отделён от ссылки галереи.

- Граф: `docs/waves/graph.json` (E5 зависит только от E4; решения D02, D04, D05, D07, D10 приняты). Канон: `../MoreFoto/docs/04-bitrix-modules/backend-waves.json`, контракты `../MoreFoto/docs/05-rest-api/endpoints.json` и `README.md` (идемпотентность, ошибки, `X-Order-Key`).

- Эталоны кода: чистые контроллеры и DTO F1/E4; `#[RequestHeader]`; резервирование ключа как в H1; повтор при deadlock как в `InstitutionTransaction`; проверка области с повторной сверкой `accessRevision` как в C4. Не копировать legacy `CatalogController`/`ConditionsController` (#24) и порядок идемпотентности F1 (#27).

## Scope

**Backend (`morefoto.commerce`, владелец):**

- Миграция: заказ, строки заказа, личные ключи, журнал повтора оформления (проект ниже).
- COM-10 `POST /api/v1/public/galleries/{gallery_token}/orders`: обязательный `Idempotency-Key`, резервирование ключа, повтор, проверка покупателя, `ValidateQuoteUseCase`, снимок, номер `MF-…`, выдача ключа; 201 + `Location`.
- COM-11 `GET /api/v1/public/orders/current` с `X-Order-Key`: покупательская проекция и `period`, единый 404.
- COM-12 `GET /api/v1/orders` и COM-13 `GET /api/v1/orders/{order_id}`: организатор и куратор в своей области, фильтры и пагинация в SQL до LIMIT, без ключей/токенов/журналов повтора; `correctionPhotos` в карточке.
- COM-08: `capabilities.purchaseEnabled` отражает серверный флаг оформления.
- Внутренний жизненный цикл ключа: выдача при создании, срок, отзыв/замена без HTTP (восстановление — будущая волна).

**Смежные изменения, нужные завершённому сценарию:**

- `morefoto.access`: право `order.read` по D08 (организатор — всё, куратор — свои учреждения).
- `morefoto.media`: контракт готовых кадров выбранных детей группы для `correctionPhotos`.
- `rebit.share`: `createdJson()` у `PrivateApiJsonController`; необязательное `error.details` в едином ответе ошибки (для `PRICE_CHANGED`).
- Frontend: живое оформление, карточка заказа по ключу, служебный список и карточка в сокращённом составе E5; `quoteToken` из COM-09; тип `capabilities`/`purchaseTerms`; маршруты, навигация «Заказы», исключение `/orders/access/` из access log nginx.
- E2E: миграции в `api/tools/e2e/prepare.php`, фикстура заказов, live-спецификация, пост-браузерная проверка на реальной MySQL; обновить ожидания E4 (кнопка оформления и `purchaseEnabled`).
- Документы: `docs/waves/e5/`, раздел в `docs/architecture.md`, граф и канонический контракт MoreFoto с patch.

Редактирование и удаление созданного заказа. Долг #23/#24/#26/#28 вне E5, но новые классы E5 соблюдают эти правила сразу.

## Решения

### Приняты пользователем 2026-09-22

Пользователь подтвердил все пять решений в предложенном виде («я все подтверждаю. Все пять пунктов»).

**E5-DEC-01 — формат, срок и повтор личного ключа.** D07 требует утвердить формат в волне заказа.

- Ключ — 32 случайных байта в 64 hex, как у capability галереи и quote. В БД только SHA-256; поиск по хешу.
- Срок — 30 календарных дней от выдачи по `Europe/Moscow` (рабочий параметр D07). Продление после оплаты — G1/J1.
- Ключи в отдельной таблице: выдача, срок, отзыв, инициатор и причина без секрета; не более одного действующего ключа на заказ.
- Повтор COM-10 с тем же `Idempotency-Key` возвращает тот же ключ. При создании сохраняется копия ключа, зашифрованная AES-256-GCM ключом, выведенным HKDF-SHA256 из `Idempotency-Key` клиента. Сам `Idempotency-Key` хранится только хешем, поэтому одна БД не раскрывает ни ключ повтора, ни ключ заказа; серверный секрет не нужен.
- Альтернативы: шифрование серверным `REBIT_ENCRYPTION_KEY` (утечка БД и окружения раскрывает все ключи) или повтор без ключа (нарушает контракт «тот же ID/ключ/ответ»).

**E5-DEC-02 — включение оформления.** Флаг `MOREFOTO_CHECKOUT_ENABLED`, по умолчанию выключен. COM-08 отдаёт `purchaseEnabled` по флагу; при выключенном флаге COM-10 → 403 `PURCHASE_DISABLED`. Включается только на изолированном стенде E2E; stage и production — отдельным решением при развёртывании. `purchaseTerms` остаётся `null`: реквизиты продавца, оферта и согласие на обработку ПДн нужны до продаж (D09/N2).

**E5-DEC-03 — изображения в заказах.** Проекции заказа отдают метаданные кадра (`assignmentId`, `photoId`, код, размеры) без URL. Capability галереи не попадает в заказ (D07), а служебные превью сейчас доступны только организатору. Карточка покупателя показывает коды кадров; организатор видит миниатюры через существующие служебные превью; доступ куратора к превью решается в I1 вместе с формой исправления.

**E5-DEC-04 — фильтры COM-12.** `late` и `settlement` → 422 `FILTER_UNAVAILABLE`, пока их поставщики (G1/I1–I3) не существуют; пустой список вместо данных не выдаётся. `q` — поиск без учёта регистра по номеру, имени, email и цифрам телефона внутри области и остальных фильтров; это ограниченный скан без заявленного индекса подстроки, замер на 1000+ заказов.

**E5-DEC-05 — устаревший расчёт.** Один заказ на quote (UNIQUE): тот же quote с другим ключом повтора → 409 `QUOTE_ALREADY_USED`. Изменились деньги → 409 `PRICE_CHANGED` с новым `quote`, `quoteToken`, `expiresAt` в `error.details` по контракту; прочие расхождения → `QUOTE_STALE`, истечение → `QUOTE_EXPIRED` без details.

### Следуют из принятых правил

- Порядок COM-10: формат запроса → флаг → capability (404) → резерв ключа повтора → другое тело с тем же ключом (409 `IDEMPOTENCY_CONFLICT`) → повтор (201, тот же ответ даже после закрытия; отозванная ссылка галереи → 404) → покупатель, `reviewed`, канал чека (422) → `ValidateQuoteUseCase` (`GALLERY_CLOSED`, `QUOTE_*`, `INVALID_CART`, `STAFF_ELIGIBILITY_REQUIRED`) → создание.
- Ключ повтора: 32 hex, обязателен (422 `INVALID_IDEMPOTENCY_KEY`); область — хеш capability. Резервирование `INSERT … ON DUPLICATE KEY` + `FOR UPDATE` до replay и проверок устаревания закрывает класс дефекта #27. Ошибки не сохраняются; deadlock — ограниченный повтор всей операции.
- Покупатель: имя 2–100, телефон 10–15 цифр (нормализация `+7…`), email обязателен (до 254), комментарий до 1000, `reviewed=true`. `receiptChannel` необязателен и допускается только из подключённых каналов; до G2 их нет. Ошибка — код на поле (`INVALID_BUYER_EMAIL` и т.п.).
- Номер `MF-` + минимум 6 цифр из внутреннего счётчика заказа, UNIQUE; доступа не даёт.
- Снимок: строки со своими UUID (`order_line_id` для будущих исправлений), товар (название, вид, формат, единица, `printCount`, цена, флаг льготы), кадр и ребёнок, суммы и подарок, названия учреждения/съёмки/группы на момент покупки. Новая цена каталога снимок не меняет.
- Статусы нового заказа `paymentStatus=unpaid`, `productionStatus=not-started` — собственные поля заказа; будущие владельцы обновляют их. `paidAt`/`latePayment` отсутствуют.
- `period` — календарь группы из контракта Organization: `sentAt`, `closesAt`, `deliveryDueAt`, состояние, зона, серверное `now`. История продлений (K2) и куратор не выдумываются.
- `version` — непрозрачная строка ревизии заказа.
- Доступ сотрудников: head/teacher → 403 `FORBIDDEN`; чужой или отсутствующий заказ → 404 `ORDER_NOT_FOUND`; куратор без назначений получает пустой список. После чтения — повторная сверка `accessRevision` (409 `ACCESS_CHANGED`). Отказы Access переводятся в коды commerce.
- COM-11: неверный формат, неизвестный, отозванный и истёкший ключ дают одинаковый 404 `ORDER_NOT_FOUND`. Отзыв ссылки галереи не отключает ключ заказа.
- Публичные ответы `no-store` и `no-referrer`. Сырые ключи, `Idempotency-Key`, токен галереи и контакты не пишутся в логи.

## Проект хранения

Все таблицы InnoDB, моменты UTC, деньги — целые копейки в BIGINT.

- `mf_order`: внутренний ID, публичный UUID, номер; хеш capability и quote (UNIQUE), нативные и публичные ID учреждения/съёмки/группы (цепочка неизменяема), вид группы, названия на момент покупки; покупатель и нормализованные поля поиска; итоги, ревизии каталога/условий; статусы оплаты/исполнения; версия; даты. Индексы под область и фильтры: учреждение, группа, съёмка, статусы, дата создания + ID.
- `mf_order_line`: UUID, заказ, порядковый номер, связь ребёнок—снимок, ребёнок, кадр, товар и его снимок, количество, цены, скидка, покрытие подарком.
- `mf_order_access_key`: заказ, SHA-256 ключа (UNIQUE), выдан, действует до, отозван, инициатор, причина; один действующий ключ на заказ.
- `mf_order_checkout`: хеш capability + хеш `Idempotency-Key` (PK), хеш нормализованного тела, заказ (заполняется в той же транзакции), зашифрованная копия ключа; создан.
- `down()` не удаляет таблицы с данными.

## Риски и ограничения

- Объём волны близок к E4. Пользователь 2026-09-22 разрешил до 6 тыс. рукописных строк одной волной; при превышении — обсудить разделение.
- SERIALIZABLE-проверка quote и конкурентные вставки: риск deadlock; нужен повтор и реальный конкурентный тест.
- Изменения в `rebit.share`, Access и Media затрагивают чужие модули; нужны их тесты и регрессия.
- Миниатюры в карточке покупателя и у куратора в E5 недоступны (E5-DEC-03).
- Фильтры UI по съёмке и группе берут варианты из существующих live API Organization. Если уровень недоступен куратору, фильтр скрывается, а API-фильтр проверяется HTTP-тестом.
- ПДн покупателя появляются только на изолированном стенде; хранение, согласие и сроки — до продаж.

## Критерии приёмки

1. COM-10…13 соответствуют уточнённому канону; ключи, токены и журналы повтора не попадают в служебные проекции, логи и БД в открытом виде.
2. Двойной и конкурентный submit с одним ключом создают один заказ и одинаковый ответ; другое тело — 409 без второго эффекта; повтор работает после закрытия приёма.
3. Устаревший, истёкший, изменившийся или уже использованный quote не создаёт заказ; `PRICE_CHANGED` отдаёт новый расчёт.
4. Снимок не меняется после смены цен каталога и условий.
5. COM-11: действующий ключ открывает только свой заказ; неверный, отозванный, истёкший ключ, номер `MF` и токен галереи дают единый 404.
6. COM-12/13: организатор видит всё, куратор — только свою область, head/teacher — 403; фильтры, пагинация и total считаются в SQL до LIMIT; смена прав во время чтения даёт 409.
7. Миграция ставится на пустую БД, повтор `up()` безопасен, `down()` не уничтожает данные.
8. Реальный browser E2E: оформление, заказ по ключу, служебные экраны; визуально desktop и mobile без переполнения и demo-хранилища.
9. Backend/frontend проверки, архитектурные тесты, DAG/99 API — PASS; PR без чужих коммитов.

Серверный порядок (`CreateOrderUseCase::execute/place`, `CheckoutReceipts::reserve`):

- До поиска по ключу повтора (ответ ничего не говорит о прежней попытке): ошибки формата запроса (`VALIDATION_FAILED`, `UNKNOWN_FIELD`, `INVALID_IDEMPOTENCY_KEY`, форма строк → `INVALID_CART`), 403 `PURCHASE_DISABLED`, 404 `GALLERY_NOT_FOUND`, 409 `GALLERY_NOT_READY`, 409 `IDEMPOTENCY_CONFLICT`; 408/429 — только промежуточные сервисы.
- После поиска, когда заказа по ключу нет: `GALLERY_CLOSED`; `INVALID_BUYER_*`, `REVIEW_REQUIRED`, `RECEIPT_CHANNEL_UNAVAILABLE`; `QUOTE_STALE`, `QUOTE_EXPIRED`, `PRICE_CHANGED`, `QUOTE_ALREADY_USED`; `INVALID_CART`, `DUPLICATE_CART_LINE`, `DIGITAL_ALREADY_IN_BUNDLE`, `STAFF_ELIGIBILITY_REQUIRED`.

Решение (подтверждено пользователем 2026-09-22: «Реализовать, E2E после ревью»):

- Разрешение сбросить попытку отделено от текста ошибки. Первая отправка с новым ключом: любой 4xx доказывает, что по ключу ничего не сохранено (ключ раньше не отправлялся), поведение прежнее. Восстановление (pending был до отправки): тело и ключ сбрасываются только кодами «после поиска»; прочие 4xx, включая `PURCHASE_DISABLED`, 408/429 и неизвестные, оставляют экран восстановления со своим сообщением.
- `INVALID_CART` разрешает сброс: после поиска это предметный отказ (иначе покупатель навсегда остался бы в восстановлении), а форматная проверка того же тела детерминирована и отклонила бы и первую попытку.
- Остаточный риск: постоянный отказ до поиска (например, смена формата контракта между попытками) держит экран восстановления; новой покупки автоматически нет, выход — повтор после исправления или обращение (K1).
- Альтернатива (не выбрана): удерживать попытку при любом отказе до поиска и для первой отправки. Проще правило, но ошибка формата при первой отправке навсегда блокирует оформление покупателя.
