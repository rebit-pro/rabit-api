# Issues #31, #33 и #34 — массовая загрузка фото без ожидания превью и наблюдаемая очередь

## Цель и контекст

- [#31](https://github.com/rebit-pro/rabit-api/issues/31): организатор загружает крупную съёмку без ручного разбиения на пакеты по 50.
- [#33](https://github.com/rebit-pro/rabit-api/issues/33): очередь отправляет следующий оригинал, не дожидаясь превью предыдущего.
- [#34](https://github.com/rebit-pro/rabit-api/issues/34): задержка обработки ≈ 57–58 с и «немая» публикация задания в очередь.

Объём «#31, #33, #34 одной веткой» задал пользователь 2026-09-22. Решение по #31 принято пользователем в тот же день: снять лимит 50 и загружать папку целиком через очередь #33, без ZIP и без импорта по ссылке. Это issue-ветка, не продуктовая волна: `docs/waves/graph.json` не меняется, прецеденты — #29 и #45.

## Установленные факты (main 5b750c0)

**Frontend** (`frontend/src/modules/morefoto/photos`):
- `usePhotoQueue.start()` отправляет файлы строго по одному и после каждого ждёт `poll()`: 120 × 500 мс ≈ 60 с. По таймауту файл получает `error`, повторить его нельзя: файл уже удалён из памяти.
- Каждый готовый кадр шлёт `photosChangedEvent`, а `usePhotoWorkspace` перечитывает на нём все страницы списка. Для 1000 кадров это тысячи запросов.
- Загрузка идёт с общим axios `timeout: 15000` (`src/api/http.ts:20`): оригинал 8 МБ на медленном канале обрывается.
- Лимит 50 — только клиентский `photoLimits.batch` (`rules.ts:2`), backend принимает по одному файлу на запрос.
- На каждое изменение прогресса очередь целиком пишется в `sessionStorage` и перерисовывается весь список строк.

**Backend** (`api/public/local/modules/morefoto.media`):
- `UploadPhotoUseCase` глотает любое исключение немедленной публикации без лога (`catch (\Throwable) {}`). Строка остаётся `UF_JOB_STATE='pending'` до dispatcher.
- Dispatcher `app:media:dispatch-pending`: на production это отдельный сервис `morefoto_stage_media_dispatcher`, запуск раз в минуту.
  - Первая ошибка обрывает весь проход.
  - Строки берутся без порога возраста. Если publisher молча пропускает отправку из-за занятого ключа дедупа (окно 30 с), dispatcher всё равно ставит `published`. При одновременном сбое немедленной отправки кадр может навсегда остаться в `processing`.
- Consumer и обработчик не пишут ни времени ожидания, ни времени рендера. GD рендерит 320 и 1200 px в одном вызове `render()`.

**Production (чтение 2026-09-22):**
- За 7 дней 8 фото, все 21.09, все `ready/done`: ни одного быстрее 5 с, 3 — от 5 до 40 с, 5 — дольше 40 с, максимум 878 с.
- Dispatcher с перезапуска в 14:09 UTC 22.09: 113 запусков, 0 опубликованных задач (новых загрузок не было).
- У FPM переменная `MESSENGER_TRANSPORT_DSN` задана.
- Причину сбоя немедленной публикации на stage по этим данным установить нельзя. Её покажут новые логи.

## Scope

### #34 — наблюдаемая публикация и устойчивый dispatcher

1. `UploadPhotoUseCase`: logger канала `media` через DI (`Log::channel(LogChannelEnum::media)`).
   - При сбое пишется предупреждение с `photoId`, `revision`, этапом (`publish` или `markPublished`) и классом исключения. Без текста исключения, путей, токенов и payload — по образцу `QueueEmailUseCase`.
   - Кадр остаётся `pending` для dispatcher.
   - Информационная запись о приёме: длительности проверки, сохранения, регистрации и публикации (мс) и флаг `published`.
2. `DispatchPendingPhotoJobsUseCase`:
   - изоляция строк: ошибка одной логируется и не мешает остальным;
   - порог возраста `pending` 45 с, больше окна дедупа 30 с;
   - результат — число опубликованных и число ошибок; команда выводит оба.
3. `PhotoRepository::pendingJobs(limit, minAgeSeconds)` — условие по `UF_CREATED_AT`.
4. `ProcessPhotoMessageHandler`: запись об обработке с ожиданием от создания до начала обработки, временем рендера 320/1200 px, числом попыток и размером кадра. При сбое — класс исключения и номер попытки.
   - Замеры приходят из `GdPreviewRenderer` в `PreviewOutputDto`: поля `thumbMs`, `previewMs` — данные, не логика.
5. Class-level phpDoc на русском для изменённых UseCase/Service (обязательное правило CLAUDE.md).
6. PHPUnit:
   - сбой publisher и сбой `markPublished` пишутся в лог, исключение наружу не выходит, `pending` сохранён;
   - dispatcher продолжает после ошибки строки и передаёт порог возраста;
   - обработчик пишет замеры, а при ошибке — `markAttemptFailed` и лог.

### #33 и #31 — параллельная очередь без ожидания превью и крупные съёмки

1. Пул отправки: `photoLimits.parallel = 2` одновременных POST. Сразу после ответа 202 берётся следующий файл.
   - Новый статус `uploading` («Загружается оригинал»), `processing` означает «Принят, ждёт обработки».
2. Отслеживание принятых кадров: один общий цикл, не больше 2 запросов `GET /photos/{id}` в секунду по всей очереди.
   - У каждого кадра интервал растёт 2 → 5 → 10 с.
   - Таймаут «ошибка через минуту» убран. Через 10 минут показывается «Обработка задерживается», проверка продолжается.
   - Новый эндпоинт и изменение загрязнённого `MediaController` не требуются. Issue допускает «пакетно либо с ограниченной частотой».
3. После обновления страницы принятые кадры (`processing` с `serverId`) продолжают отслеживаться без повторной отправки. `queued`/`uploading` без `serverId` становятся `interrupted`, как сейчас.
4. Таймаут загрузки 300 с на запрос (как `max_execution_time` PHP) вместо общих 15 с.
5. Обновление рабочего списка — не чаще раза в 5 с плюс финальное, вместо полного перечитывания на каждый кадр. Запись в `sessionStorage` не чаще раза в секунду и сразу при смене статуса.
6. #31: лимит выбора 50 → 2000 файлов, текст «до 2000 файлов за раз».
7. «Пауза» и «Продолжить»: пауза не запускает новые отправки, начатые завершаются.
8. Длинная очередь: строка списка пропускает перерисовку через `v-memo`, прогресс обновляется шагами.
9. Demo-режим (подготовка в браузере) остаётся последовательным. Меняются только лимит и подписи.

### Исключено

- ZIP-архив и импорт по ссылке — решение пользователя, при необходимости отдельным issue.
- Изменения HTTP-контрактов и API ID, `MediaController` и граф волн.
- Число media workers и ресурсы сервера: решается после замеров на stage.
- EXIF-ориентация превью — отдельное наблюдение.

## Решения, риски и ограничения

- D1. #31 без ZIP (пользователь, 2026-09-22).
- D2. Параллельность 2 — стартовое значение из #33. Константа, меняется после замера.
- D3. Статусы через существующий `GET /api/v1/photos/{id}` с общим ограничением частоты. Пакетный эндпоинт потребовал бы переписать загрязнённый контроллер и новый API ID.
- D4. Порог dispatcher 45 с закрывает гонку с окном дедупа. Цена: восстановление после сбоя немедленной публикации занимает 45–105 с.
- D5. В логах только ID, этапы, классы исключений и длительности.
- Риски:
  - нагрузка 2 параллельных загрузок на stage с 1 CPU / 2 ГБ;
  - квота `sessionStorage` при 2000 строках (~0,6 МБ);
  - тайминговые проверки в E2E могут быть нестабильны — проверяется структура: не больше 2 одновременных POST и отсутствие ожидания превью.
- Деплой: backend (без миграций) и frontend. Backend переключается по процедуре F2 с проверкой монтирования `/app`.
- Полный `make test-e2e` — после review без блокеров. Opt-in замер на 50 кадрах требует стенда, запуск — с согласия пользователя.

## Критерии приёмки

1. На партии из N файлов одновременно идёт не больше 2 POST. Следующий POST стартует сразу после ответа предыдущего, без ожидания превью.
2. После обновления страницы принятые кадры показываются с верным статусом без повторной отправки и дублей.
3. Ошибка одного файла не останавливает остальные, повтор не создаёт дубль.
4. Выбор больше 50 файлов (до 2000) принимается одной партией.
5. Для каждого принятого фото по логам видно, опубликовано ли задание сразу, когда началась обработка и чем она закончилась.
6. При отказе транспорта фото не теряется и обрабатывается dispatcher. Причина видна в логе, дублей нет.
7. Приватность оригиналов и защищённая выдача превью не меняются.
