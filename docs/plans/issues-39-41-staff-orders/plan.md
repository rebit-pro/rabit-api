# Issues #39 и #41 — фильтры области служебных заказов и экран восстановления оформления

## Цель и контекст

Закрыть два неблокирующих замечания ревью E5 (PR #37):

- [#39](https://github.com/rebit-pro/rabit-api/issues/39) (P2). Служебный список заказов `/cabinet/orders` не умеет
  ограничивать выдачу учреждением, съёмкой и группой. Backend COM-12 (`GET /api/v1/orders`) эти фильтры уже принимает:

  их отбрасывает в `StaffOrderFilters`, в URL/API mapper `orders/live/rules.ts` и в форме `StaffOrdersLiveScreen.vue`.

  `recovering = draft.pending !== null && !submitting.value` становится `false` на время любой отправки. Во время
  «Повторить отправку» вместо экрана восстановления видна форма либо «Сначала выберите фотографии», загрузка кнопки
  повтора не видна никогда.

## Scope

### #41 — экран восстановления во время повтора

- `orders/live/rules.ts`: чистое правило `showsCheckoutRecovery(pending, submission)`. Сохранённая попытка остаётся
  на экране восстановления в покое и во время собственного повтора. Первая отправка остаётся на форме.
- `useLiveCheckout.ts`: вместо `submitting: boolean` хранится вид текущей отправки `'idle' | 'first' | 'recovery'`.
  `busy` и `recovering` вычисляются из него.
- Unit-тест правила в `tests/commerce/orders-live.test.mjs`.
- Live E2E `zzzzz-orders.spec.ts`: сценарий «потерянный ответ» после закрытия группы и перезагрузки задерживает ответ
  на повтор. Проверяется: экран восстановления виден, кнопка «Повторить отправку» в состоянии загрузки, формы и
  «Сначала выберите фотографии» нет.

### #39 — фильтры учреждения, съёмки и группы

- `orders/live/types.ts`: `StaffOrderFilters` получает `institutionId`, `shootId`, `groupId`.
- `orders/live/rules.ts`:
  - единый список ключей фильтров, `staffOrderParams` и `staffFiltersFromQuery` учитывают новые поля;
  - `staffFilterQuery` строит URL-query (переносится из `useStaffOrders.apply`);
  - `staffScopePatch` при смене родителя сбрасывает зависимые значения;
  - `staffScopeOptions` строит варианты трёх списков.
- Варианты берутся из действующих Organization API, которые frontend уже вызывает через `structureApi`:
  - `GET /api/v1/institutions` — учреждения области сотрудника. Организатор видит все, куратор только назначенные;
    отбор выполняет сервер.
  - `GET /api/v1/institutions/{id}` — съёмки и группы учреждения в области сотрудника (роли organizer/curator/head).
    У группы есть `shootId`, поэтому группы выбранной съёмки фильтруются на клиенте без отдельного запроса.
- `curator/useStaffOrderScope.ts`: загрузка вариантов с обходом всех страниц (`pageSize=100`, максимум API) и
  защитой от устаревших ответов.
- `useStaffOrders.ts`: `apply` пишет новые ключи в URL, `reset` очищает всё, `selectScope` применяет `staffScopePatch`.
- `StaffOrdersLiveScreen.vue`: строка из трёх `v-select` «Учреждение» / «Съёмка» / «Группа» с пунктами «Все …».
  «Сбросить» учитывает новые поля.
- Unit-тесты правил: URL/API mapper, сброс зависимых значений, варианты списков.
- Live E2E `zzzzz-orders.spec.ts`:
  - ручной `?groupId=` ограничивает запрос;
  - каскадный выбор, сохранение фильтров при переходе список → карточка → список, сброс зависимых значений и общий сброс;
  - варианты учреждений куратора ограничены его областью.

### Исключено

- Backend: COM-12 и Organization API не меняются. Серверная проверка области остаётся единственной гарантией доступа.
- Отдельный endpoint «справочник области заказов» не вводится: хватает действующих API.
- Автоприменение фильтров при выборе в списке. Как и остальные уточнения, выбор применяется кнопкой «Найти» или Enter.
- Demo-экраны и mock-режим (`CuratorScreen`, `useDemoCheckout`).
- Граф волн и канонический план MoreFoto.

## Решения, риски и ограничения

- D1. #41 решается видом отправки (`'idle' | 'first' | 'recovery'`), а не отдельным флагом. `draft.pending`
  заполняется до запроса и в первой отправке, поэтому по одному `pending` первую отправку от повтора не отличить.
- D2. Каскад строится на `GET /api/v1/institutions/{id}` вместо `GET /api/v1/shoots/{id}`. Второй endpoint доступен
  только организатору (`GetShootUseCase`), первый также куратору в пределах его учреждений. Один источник для обеих ролей.
- D3. Если у сотрудника ровно одно доступное учреждение, съёмки и группы грузятся для него без выбора учреждения. Так
  куратору одного учреждения доступны все уровни сразу. В запрос это учреждение не добавляется: область и так
  ограничена сервером.
- D4. Смена учреждения сбрасывает съёмку и группу, смена съёмки — группу. Страница сбрасывается применением фильтров:
  `apply()` ведёт на первую страницу. При восстановлении фильтров из URL сброс не выполняется, иначе ссылка с тремя
  значениями теряла бы съёмку и группу. Поэтому сброс вызывается только из обработчика выбора, а не watcher.
- D5. Если значение из URL не найдено среди загруженных вариантов (например, ручной `?groupId=` без учреждения),
  список показывает пункт «Выбрано по ссылке». Запрос при этом ограничен, недоступную группу отсекает сервер.
- D6. Ошибка загрузки вариантов не блокирует список заказов: показывается сообщение у фильтров, зависимые списки
  остаются с пунктом «Все …». Mock и fallback-данных нет.
- Риск R1: учреждение с сотнями групп требует нескольких запросов по 100 записей. Для текущих объёмов (до ~100 групп
  на учреждение) это 1–2 запроса при выборе учреждения.
- Риск R2: названия групп повторяются в разных съёмках. Без выбранной съёмки в названии группы указывается съёмка.
- Ограничение: полный `make test-e2e` запускается после review без блокирующих замечаний. До review — быстрые проверки
  и адресный браузерный прогон на стабах API. Он не заменяет live E2E.

## Критерии приёмки

1. Во время повтора сохранённой попытки виден экран восстановления, кнопка «Повторить отправку» в состоянии загрузки.
   Формы и «Сначала выберите фотографии» нет, в том числе после закрытия группы и перезагрузки.
2. Первая отправка остаётся на форме, загрузку показывает «Создать тестовый заказ».
3. Удержанный отказ при повторе возвращает причину на экран восстановления, успешный повтор открывает заказ.
4. `institutionId`/`shootId`/`groupId` попадают в URL и в запрос `GET /api/v1/orders`. Пустые значения не передаются.
5. Ручной `/cabinet/orders?groupId=<UUID>` ограничивает запрос этой группой; итог совпадает с API.
6. Варианты учреждений, съёмок и групп берутся из Organization API. Куратор видит только учреждения своей области.
7. Смена учреждения сбрасывает съёмку и группу, смена съёмки — группу; применение ведёт на первую страницу.
   «Сбросить» очищает все фильтры, включая область.
8. Фильтры сохраняются при переходе список → карточка → список.
9. На 1280 и 390 px нет горизонтальной прокрутки, подписи списков не обрезаются.
10. `npm run check` и `npm run test:commerce` зелёные; live E2E зелёный после review.
