# Issues #72 и #73 — повтор загрузки фильтров заказов и замер параллельности загрузок

## Цель и контекст

Закрыть два замечания, найденные при review PR #71 и gate PR #67:

- [#72](https://github.com/rebit-pro/rabit-api/issues/72) (P3). `curator/useStaffOrderScope.ts` загружает варианты
  фильтров «Учреждение/Съёмка/Группа» (прецедент — [issues-39-41](../issues-39-41-staff-orders/plan.md)). После ошибки

  имеет разрешение 1 мс, `responseEnd` отсчитывается от него. Когда очередь стартует следующий POST сразу после
  предыдущего, интервалы на границе пересекаются, и `peakOverlap` иногда даёт 3 при лимите 2. Тест #54/#55 того же
  файла уже переведён на Resource Timing страницы.

## Scope

### #72 — повтор загрузки вариантов фильтров

- `orders/live/rules.ts`: тип `StaffScopeLoad` (`idle | loading | ready | failed`) и чистое правило
  `staffScopeRetry(list, card)`. Повторяется только источник в состоянии `failed`. Источник в `loading` второй раз
  не запускается, загруженный сохраняет варианты.
- `curator/useStaffOrderScope.ts`:
  - флаги `listed`/`listFailed`/`openFailed` заменяются двумя состояниями `StaffScopeLoad`;
  - новый `retry()` повторяет список и/или карточку учреждения по правилу;
  - `listing` отдаётся экрану для индикатора загрузки списка учреждений.
- `StaffOrdersLiveScreen.vue`: у сообщения об ошибке фильтров кнопка «Повторить», вызывает `retry()`. Список
  «Учреждение» показывает загрузку.
- Unit-тест правила в `tests/commerce/orders-live.test.mjs`.
- Live E2E в `zzzzz-orders.spec.ts`: ошибка первого списка учреждений и ошибка карточки единственного учреждения
  куратора, сымитированные `route.abort('failed')`. Повтор восстанавливает варианты, выбранные значения сохраняются.

### #73 — замер параллельности по Resource Timing

- `e2e/live/zz-media.spec.ts`, тест #33: интервалы POST-загрузок берутся из `performance.getEntriesByType('resource')`
  страницы, а не из `request.timing()`. Проверка `peakOverlap(...) <= 2` не ослабляется.
- Функция `span()` удаляется, если у неё не останется вызовов.

### Исключено

- Backend и Organization API не меняются.
- Автоматический повтор по таймеру или при нажатии «Найти»: повтор только явный.
- Очередь загрузки `usePhotoQueue` и лимит `photoLimits.parallel` не меняются.
- Demo-экраны и mock-режим.
- Граф волн и канонический план MoreFoto.

## Решения, риски и ограничения

- D1. Состояние каждого источника вариантов — `StaffScopeLoad`, а не набор флагов. Правило повтора читается из
  одного значения: `failed` повторяется, `loading` защищает от параллельного запроса. Отдельный счётчик для списка
  не нужен, для карточки остаётся счётчик `request`: он отсекает устаревшие ответы при смене учреждения.
- D2. Повтор не трогает фильтры: `filters` принадлежат `useStaffOrders`, `useStaffOrderScope` их только читает.
  Выбранные значения видны и во время повтора: для значения вне загруженных вариантов остаётся пункт
  «Выбрано по ссылке».
- D3. Повтор карточки идёт по ID последней запрошенной карточки (`opened`). Если после повтора списка у сотрудника
  одно учреждение, карточка загружается уже действующим наблюдателем `institutionId`.
- D4. Возврат со страницы карточки заказа по-прежнему повторяет упавший список без кнопки: наблюдатель `active`
  запускает список в состояниях `idle` и `failed`.
- D5. Кнопка «Повторить» фильтров находится в блоке фильтров отдельно от «Повторить» ошибки заказов. В E2E она
  ищется внутри `order-scope-filters`.
- D6 (#73). POST и GET списка кадров идут по одному пути `/api/v1/shoots/{id}/photos`. Список всегда передаёт query
  (`groupId`, `status`, `page`, `pageSize`), загрузка — без query. Поэтому POST отбираются по точному совпадению
  `entry.name` с URL загрузки без query и `initiatorType === 'xmlhttprequest'` (axios). Число отобранных записей
  сверяется с числом POST из `requestfinished`/`requestfailed`. Лишняя или пропущенная запись роняет тест, а не
  ослабляет проверку.
- D7 (#73). `page.reload()` очищает буфер Resource Timing. Записи снимаются сразу после первой партии, до загрузки
  `after-reload.png` и перезагрузки. Размер буфера увеличивается `setResourceTimingBufferSize(1000)` через
  `addInitScript`, как в тесте #54/#55: превью и статусы не должны вытеснить загрузки.
- Риск R1: `route.abort('failed')` даёт сетевую ошибку. Ответ 5xx не используется: в других файлах live E2E
  5xx на `/api/` роняет тест, а обрыв сети лучше описывает временный сбой.
- Риск R2: у `c4-curator` нет `order.read` в интерфейсе, поэтому сценарий куратора использует `curator`. У него после
  `beforeAll` не меньше одного учреждения. Для сценария «единственное учреждение» ответ списка учреждений сокращается
  до E4 через `route.fulfill` с настоящим ответом сервера, отфильтрованным до E4.
- Ограничение: полный `make test-e2e` и 5 прогонов группы `a` — после review без блокеров. До review — быстрые
  проверки и адресный прогон в Chromium на стабах API. Он не заменяет live E2E.

## Критерии приёмки

1. После ошибки первого списка учреждений у фильтров видны сообщение и кнопка «Повторить». Повтор загружает
   учреждения без перезагрузки страницы и без ухода с неё.
2. После ошибки карточки единственного учреждения куратора повтор загружает съёмки и группы.
3. Выбранные значения «Учреждение/Съёмка/Группа» и URL не меняются при ошибке и повторе.
4. Повторное нажатие во время загрузки не отправляет параллельный запрос того же источника.
5. «Повторить» ошибки заказов по-прежнему перезагружает только заказы.
6. Тест #33 проверяет не более 2 одновременных POST-загрузок по Resource Timing. Число учтённых загрузок равно 6.
7. При лимите очереди 3 проверка перекрытия падает.
8. На 1280 и 390 px нет горизонтальной прокрутки, блок ошибки с кнопкой не ломает сетку фильтров.
9. `npm run check` и `npm run test:commerce` зелёные; live E2E зелёный после review.
