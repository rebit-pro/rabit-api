## Установленные факты (main 54bd4ab)

**#26, backend:** `page()` выполняет `GROUP BY STATUS`, `COUNT(*)`, список `PUBLIC_ID`, затем на каждый ID `request()` и `view()` → `rows()`, `history()`, `results()`: 3 + 4N запросов (N=100 → 403). `options()` — ещё один запрос на список.

**#26, frontend:** `loadLiveHandoff()` читает страницу 1 (pageSize 100) и последовательно все остальные; при открытии карточки дополнительно читает HND-08. Фильтры статуса и съёмки применяются на клиенте к полному массиву. Экран разворачивает серверный порядок `.reverse()`, хотя сервер уже отдаёт `UPDATED_AT DESC`. Маршруты `/staff-requests` и `/staff-requests/:id` используют один компонент без `key`, поэтому смена маршрута не перезагружает workspace.

**#27:** `StaffRequestWorkflow::save()/clarify()` проверяют replay (`SELECT … FOR UPDATE` в `mf_staff_request_idempotency`) до блокировки заявки. В READ COMMITTED блокировка отсутствующей записи ничего не резервирует. PK таблицы `(ACTOR_ID, RESOURCE_KEY, IDEMPOTENCY_KEY)` уже есть — миграция не нужна. Для create конкурентный дубль сейчас падает на PK при `saveIdempotency()` → 503 `HANDOFF_UNAVAILABLE`.

**#28:** `staffRequestError()` сводит транспортную ошибку к «Сервер не сохранил список»; `useHandoffEditor.reset()` вызывает локальную factory, которая берёт revision из неизменного workspace; `open()` восстанавливает draft независимо от серверной revision.

## Решения

- R1 (#26). HTTP-контракт HND-06/HND-08 не меняется: элемент списка по-прежнему содержит `rows`, `history`, `results`. Связанные данные читаются пакетно по ID страницы: один SQL карточек страницы, один SQL строк (строки и итог переноса из одного запроса), один SQL истории. Итого на список 5 SQL Handoff + 1 `options()` независимо от N. Удаление `history` из элементов списка — изменение контракта, в этой ветке не делается (вопрос Q1).
- R2 (#26). Новое чтение — SQL с массивными строками (`Result::fetch()`), без Objectify-коллекций; `request()`/`view()` для карточки HND-08 переиспользуют те же пакетные методы с одним ID.
- R3 (#26, frontend). Список читает одну страницу (pageSize 20) с серверными фильтрами `status` и `shootId`, навигация — `v-pagination`. Карточка читает HND-08 и scope через HND-06 с `pageSize=1`; другие страницы не читаются. Смена маршрута, фильтра или страницы перезагружает workspace. Демо-режим сохраняет локальный расчёт и отдаёт новые списки первыми (как раньше).
- R4 (#27). Ключ резервируется до мутации: `INSERT IGNORE` в `mf_staff_request_idempotency` с пустым `RESULT_JSON`. Если строка вставлена — выполняется мутация и `UPDATE` результата в той же транзакции. Если нет (конкурент зафиксировал ключ, либо ожидание его блокировки завершилось) — читается зафиксированная строка: совпал hash → replay, иначе `IDEMPOTENCY_CONFLICT`. Порядок блокировок: ключ → заявка; одинаков для create/update/clarify. Rollback любой ошибки снимает резерв, поэтому ошибки не запоминаются (как и раньше).
- R5 (#28). Нет HTTP-ответа (`!error.response`) → текст «Ответ сервера не получен… изменения могли сохраниться»; черновик с тем же `Idempotency-Key` и телом сохраняется и после reload, повтор безопасен.
- R6 (#28). «Загрузить актуальные данные» — асинхронный `reset()`: перечитывает workspace с сервера (`useHandoff.reload()` возвращает успех), затем пересобирает команду из серверного состояния с новым ключом и удаляет draft. Ошибка чтения оставляет форму и показывает причину.
- R7 (#28). `open()` не восстанавливает draft, если его `revision` отличается от серверной revision свежей команды (устаревший draft); форма открывается по серверному состоянию с пояснением. После ошибки сохранения закрытие диалога перечитывает workspace, чтобы повторное открытие сравнивало draft с актуальной revision.
- R8. Демо и live drafts уже разделены префиксом ключа `morefoto:{demo|live}:handoff-draft`; серверные проверки не ослабляются.

## Риски и ограничения

- `INSERT IGNORE` превращает нарушения CHECK в предупреждения; значения ключа/hash валидируются VO и `hash()`, поэтому пропуск строки возможен только при дубле PK.
- При rollback владельца ключа два и более ожидающих могут получить deadlock на вставке; `BitrixHandoffTransaction` с одной попыткой отдаст 503. Вероятность низкая (требует ошибки у первого запроса), исход безопасен — повтор тем же ключом.
- Реальные время/память на 1000 заявок измеряет только верификатор gate; до запуска gate — PENDING.
- E2E-сценарии написаны, но не запускались (gate после review).

## Критерии приёмки

1. HND-06 выполняет постоянное число SQL независимо от числа элементов страницы; scope, фильтры, порядок и meta сохранены.
2. UI загружает одну страницу с серверными фильтрами и пагинацией; карточка не читает остальные страницы.
3. Конкурентные одинаковые create/update/clarify возвращают один успешный результат; иное тело — `IDEMPOTENCY_CONFLICT`; история и revision не дублируются.
4. Потерянный ответ показывает неопределённый исход; повтор использует тот же ключ и тело; «Загрузить актуальные данные» читает сервер; повторное открытие не возвращает устаревший draft.
5. Быстрые проверки зелёные; E2E написан и ждёт gate.
