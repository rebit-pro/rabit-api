# Issues #68 и #69 — доработки E6 после ревью

## Цель

Закрыть неблокирующие замечания ревью PR #66 (волна E6):

- #68 — выключение учёта расходов на оплату сохраняется даже при неверном черновом значении ставки в отключённом поле;
- #69 — тест-кейс E6-T04 в плане E6 ожидает фактический `maxRateBps = 1000`.

## Контекст и база

Исправления опираются на код E6, который ещё не слит в main. По правилу «без stacked PR» ветка `codex/issues-68-69-payment-costs` создана локально от головы PR #66 (`01f024b`). PR в main открывается только после merge #66, затем в ветку вливается main, и diff содержит лишь эти исправления. Задача вне графа волн: ID волны не используется.

## Scope

1. Frontend (`conditions-command.ts`):
   - ставка проверяется только при включённой политике;
   - при выключенной политике в тело уходит введённая ставка, если она корректна, иначе сохранённая (`savedRateBps` из ответа COM-04), поэтому сохранённая ставка не затирается;
   - при повторном включении ставка снова проверяется.
2. Тип команды: `paymentCosts.savedRateBps`. Черновики без этого поля не восстанавливаются: их писала только неслитая сборка PR #66.
3. Тесты: unit — выключение при неверной ставке, сохранение корректной новой ставки при выключении, повторная проверка при включении; live — шаг сценария E6 «ввести 10,5 %, выключить, сохранить».
4. Документация: E6-T04 в `docs/plans/E6_payment-cost-pricing/plan.md` — `maxRateBps` 1000 (#69).

Вне scope: backend (сервер и так принимает любую ставку 0…1000 при выключенной политике), другие замечания и issue.

## Решения

- Поле ставки при выключенной политике остаётся отключённым, как было. Проверка и тело запроса учитывают состояние переключателя.
- Сохранённая ставка берётся из снимка COM-04, а не из константы 380: выключение не должно менять ранее настроенную ставку.
