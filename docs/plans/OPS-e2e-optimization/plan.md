# OPS — ускорение полного E2E-гейта

> Техническая задача вне графа волн: ветка `codex/ops-e2e-optimization` от `main` `aee6808`, один PR в `main`.
> Исходная инструкция — [frontend/docs/e2e-optimization.md](../../../frontend/docs/e2e-optimization.md).
> Продуктовый код, API, миграции и сценарии не меняются; меняется оркестрация проверки.

## Цель и контекст

Полный `make test-e2e` занимает около 9,5–10 минут. Последний полный прогон на коде текущего `main` (`c304270`, 77 сценариев) длился 9 мин 39 с. Время распределилось так:

- `npm ci` — 114 с;
- `npm run check` — 42 с;
- unit-тесты — 3 с;
- `npm run build` с повторным `vue-tsc` — 32 с;
- MySQL, RabbitMQ и vendor — 22 с;
- PHPStan с `--debug` — 25 с;
- PHPUnit — 8 с;
- браузер — 316 с;
- очистка — 6 с.

Все этапы идут последовательно, браузер использует один worker.

Нужно сократить время гейта и сдержать его рост. Состав проверок, реальный путь HTTP → nginx → Bitrix/PHP-FPM → MySQL/RabbitMQ и достоверность результата должны сохраниться.

## Scope

1. Замер этапов монотонными часами. В `state.json` сохраняются длительность и результат каждого этапа, в том числе при ошибке. В конце печатается сводка. Фиксируются commit, изменённые пути, hash незакоммиченного diff, hash lockfile, ID образов, CPU/RAM и состав сценариев по группам.
2. Постоянный npm-кеш: том `rabit-e2e-npm-cache`, `npm ci --prefer-offline`. Установка остаётся строго по lockfile. Пустой или повреждённый кеш означает обычную загрузку из registry.
3. Типы проверяются один раз. `npm run build` = `npm run typecheck && npm run build-only`, а оркестратор вызывает только `build-only`. `npm run check` раскладывается на входящие в него `npm run <script>` и выполняется параллельно.
4. PHPStan запускается без `--debug`, с сохраняемым result cache (том `rabit-e2e-phpstan-cache`). Конфиг `api/tools/e2e/phpstan.neon` подключает основной `phpstan.neon` без изменений правил и путей, ограничивая число процессов двумя по лимиту контейнера `--cpus 2`. Кеш PHPStan инвалидирует сам: учитываются версия, PHP, расширения, конфиг, stubs и зависимости.
5. Этапы совмещаются: frontend (зависимости → lint/types/unit/сборка), backend (vendor → lint/PHPStan/PHPUnit) и сервисы MySQL/RabbitMQ всех стендов стартуют одновременно. Первая ошибка останавливает одноразовые контейнеры запуска. Отмена (SIGINT/SIGTERM/SIGHUP) удаляет только ресурсы своего запуска. Образы PHP при отсутствии готовых собираются параллельно и используют Docker build cache.
6. Браузерный набор делится на две независимые группы. Каждая группа идёт на отдельном свежем стенде: своя MySQL, RabbitMQ, FPM, media worker, nginx и runtime. Сборка, node_modules и vendor общие для стендов одного запуска; node_modules у каждого запуска свой, так как `vue-tsc` и Vite пишут в него.
   - Группы задаются в `frontend/e2e/live/groups.json`, из них строятся Playwright-проекты.
   - Если spec-файл не входит ровно в одну группу, конфиг сообщает об ошибке.
   - Внутри группы сохраняется прежний порядок файлов.
   - Каталоги `var` и Playwright-отчёты разделены по стенду и группе в папке запуска.
   - Верификаторы MySQL запускаются на стенде группы, где лежат нужные им сценарии.
7. Итоговая проверка состава: каждый spec-файл группы присутствует в результатах; нет unexpected, skipped и flaky, нет ошибок загрузки; все группы полного гейта выполнены.
8. Режимы:
   - по умолчанию — стенд на каждую группу;
   - `E2E_STANDS=1` — прежнее последовательное выполнение на одном стенде, для сравнения и машин с малой RAM;
   - `E2E_GROUPS=<список>` — быстрый частичный прогон, явно помеченный как неполный гейт.
   `make e2e-up/e2e-test/e2e-down` сохраняются: один стенд, группы идут последовательно.
9. `XDEBUG_MODE=off` во всех PHP-контейнерах стенда. Production-образы Xdebug не содержат, а сейчас FPM на каждый запрос пытается подключиться к отладчику. Эффект измеряется по `durationMs` запросов.
10. Документация: A8 «Воспроизведение», frontend README, статус и результаты в `frontend/docs/e2e-optimization.md`.

## Вне scope

- Изменение сценариев, ассертов и фикстур spec-файлов; несколько workers на одном backend, что потребовало бы изолировать учётки и данные внутри одной БД; sharding между машинами; CI (Actions выключены).
- Ускорение отдельных сценариев, например ожидание смены минуты в `zzzz-links` (до 60 с). Это кандидат для follow-up.
- Кеш подготовленного vendor: копирование 8 с не лежит на критическом пути.
- Образ или том с готовым `node_modules`: с прогретым npm-кешем установка занимает 12 с против 72 с без кеша.

## Зависимости и решения

- Зависимостей по волнам нет, база — `main` `aee6808`. Меняются только `tools/run-browser-e2e.py`, live-конфиг Playwright, `package.json` (scripts), новые `groups.json` и `api/tools/e2e/phpstan.neon`, документация.
- Разбиение взято из анализа зависимостей между spec-файлами:
  - A: `catalog`, `conditions`, `organization`, `staff`, `z-institution-detail`, `zz-media`, `zz-media-bench` (только с `E2E_MEDIA_BENCH`), `zz-notification`;
  - B: `zzz-handoff`, `zzzz-links`, `zzzz-storefront`, `zzzzz-orders`, `zzzzzz-transfers`.

  На одном стенде A, затем B повторяют прежний порядок имён. Между группами нет данных. Разные стенды устраняют общие токены учёток, проверку пустого каталога, ревизию условий и отзыв сессий.
- `verify-notification.php` выполняется один раз на первом стенде. `prepare-storefront.php` выполняется на каждом стенде до браузера, как сейчас, чтобы предусловия группы совпадали с прежним последовательным прогоном.
- Верификаторы и нужные им сценарии:
  - storefront ← handoff и storefront;
  - orders ← orders и transfers;
  - links ← links;
  - transfers ← transfers.
- Оркестратор собирает frontend одновременно с lint и проверкой типов. Результат сборки используется только после успешного завершения всех проверок. Это отступление от формулировки «сборка после check»: итог гейта не меняется, окно для правок исходников во время прогона становится меньше.

## Риски и ограничения

- RAM: два стенда и параллельные проверки увеличивают пик. Пик измеряется; при нехватке памяти используется `E2E_STANDS=1`. Машина общая с другими стендами и сервисами: около 16 ГиБ, свободно около 7 ГиБ.
- Скрытая зависимость между группами проявится падением группы на свежем стенде. Каждая группа проверяется отдельно.
- Параллельные прогоны разных worktree используют общий PHPStan-кеш. При гонке записи PHPStan отбрасывает повреждённый кеш и анализирует заново; корректность не страдает.
- Отчёты браузера переезжают из общего `frontend/reports/e2e-live/` в папку запуска `api/var/e2e/<run>/<stand>/<group>/`. Документация обновляется.
- Файлы, созданные контейнерами, принадлежат root, как и раньше.

## Критерии приёмки

- На том же коде сохранены все этапы: frontend lint/types/unit/сборка без mocks, PHP lint/PHPStan/PHPUnit, реальная схема и фикстуры, Notification на MySQL/RabbitMQ, все браузерные сценарии и четыре MySQL-верификатора. Число и состав сценариев совпадают с базовым прогоном (77, без bench).
- Нет пропусков, повторов, flaky, OOM и зависимости от порядка групп. Ошибка любого этапа или отсутствие ожидаемого результата делает гейт красным.
- Чистый запуск без кешей работает. Смена lockfile или кода корректно инвалидирует соответствующий кеш.
- После успеха, ошибки или отмены не остаётся контейнеров, сетей и томов запуска. Общие тома-кеши не удаляются.
- Сравнение до/после воспроизводимо: команды, холодный/прогретый кеш, число стендов, CPU/RAM, пик памяти, состав тестов записаны в `progress.md` и `e2e-optimization.md`.
