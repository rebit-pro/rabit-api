## Scope

### Backend (`morefoto.access`, `rebit.auth`, `rebit.share`)

- `DELETE /api/v1/users/{user_id}` → новый чистый `StaffArchiveController` (`AuthenticatedApiJsonController`,
  `ArchiveStaffRequestDto` с `#[RouteParameter]`, stateless input mapper) → `ArchiveStaffUseCase`. Ответ `204`.
- `ArchiveStaffUseCase` в `AccessStateRepository::run`:
  1. `assertCan(STAFF_MANAGE)`; себя — `CANNOT_ARCHIVE_SELF` 409;
  2. профиль под `FOR UPDATE`, нет — `STAFF_NOT_FOUND` 404;
  3. активный организатор и `activeOrganizerCountForUpdate() <= 1` — `LAST_ORGANIZER` 409;
  4. `lockParticipants`, удаление назначений учреждений и групп, запись `recordChange` c `{"archived":true}`,
     удаление профиля, `advanceState()`;
  5. `StaffIdentityGatewayInterface::archive()` — учётка переходит в «ожидает регистрации» (`ACTIVE=N`,
     `UF_AUTH_REGISTRATION_PENDING=1`, случайный пароль), токен сессии очищается, ссылки доступа отзываются.
- Повторное добавление того же email идёт существующим путём `SaveStaffUseCase` (учётка без профиля) и отправляет
  новое приглашение, потому что учётка снова pending.
- Сортировка списка: `sort=name|email|role|assignments|status`, `direction=asc|desc`, по умолчанию `name asc`,
  белый список в `StaffManagementRepository`, добивка `p.UF_USER_ID` для стабильных страниц.

### Frontend (`frontend/src/modules/morefoto/staff`)

- `StaffManagementScreen.vue` переходит на `UiDataTable`: колонки «Сотрудник», «Роль», «Назначения», «Статус»,
  сортировка по колонкам и на мобильном, выбор строк, действия строки «Открыть»/«Удалить».
- Панель выбора «Выбрано: N · Удалить выбранных · Снять выбор»; диалог подтверждения с перечнем имён.
- Массовое удаление — последовательные `DELETE`; 404 считается успехом; итог «Удалено N из M» и причины отказов.
- `useStaffManagement` хранит `sort` и `pageSize`, `staffApi.list` передаёт их в запрос.

### Исключено

- Остальные таблицы, удаление структурных сущностей (#92).
- Восстановление из архива отдельной кнопкой: восстановление = повторное добавление по email.
- Bulk-эндпоинт: не нужен при нынешних объёмах (единицы-десятки сотрудников).
- Разовая очистка боевой базы от тестовых данных — отдельная OPS-операция, не код этой ветки.

## Решения, риски и ограничения

- D1. Архив, а не физическое удаление учётки Bitrix (решение пользователя 2026-09-25): ID сотрудника остаётся
  в `b_hlbd_mf_access_change`, имена в журналах передач и обращений хранятся копией (`ACTOR_NAME`).
- D2. Архив = удаление строки профиля, а не флаг: все места, которые ищут профиль (`StaffAuthorization`, списки,
  назначения, счётчик организаторов), сразу перестают видеть сотрудника без правки каждого запроса и без миграции.
  Цена: у журнала `b_hlbd_mf_access_change` уникальный ключ `(UF_AGGREGATE_ID, UF_TO_REVISION)`, поэтому
  `SaveStaffUseCase` при создании профиля для учётки с историей продолжает ревизию с последней записи журнала
  (`StaffManagementRepository::lastRevision()`), иначе повторное добавление падало бы на дубле ключа.
- D3. Сброс учётки в pending, а не только блокировка: иначе повторно добавленный сотрудник с паролем не получит
  приглашение и войдёт со старым паролем.
- D4. Новый контроллер вместо метода в «загрязнённом» `StaffController` (правило чистых контроллеров, #24).
- Риск: `lockParticipants` и `advanceState` — тот же порядок блокировок, что в `SaveStaffUseCase`, чтобы не
  получить deadlock при параллельном сохранении.
- Полный `make test-e2e` — после review без блокирующих замечаний; до review — быстрые проверки.

## Критерии приёмки

- Организатор удаляет одного и нескольких сотрудников с подтверждением; они исчезают из списка и счётчиков, их
  сессии завершены, ссылки приглашений не работают.
- Себя и последнего активного организатора удалить нельзя, отказ показан по-русски.
- Повторно добавленный по тому же email сотрудник получает новое приглашение.
- Сортировка по каждой колонке работает на desktop и mobile и сохраняется при смене страницы.
