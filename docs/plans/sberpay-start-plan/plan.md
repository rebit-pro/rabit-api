# СберПэй для MoreFoto на Битрикс «Старт»

## Цель, контекст и scope

Адаптировать интеграцию СберПэй из `orteka.payment` для RaBit API с обязательным реестром эквайринговых платежей и денежными возвратами в админ-панели MoreFoto. Размещение UI и редакция «Старт» подтверждены пользователем 2026-09-21.

Текущий срез — исследование, отдельная ветка и обновление плана. Продуктовая реализация G1/G2/I2 остаётся заблокированной до merge зависимостей; этот срез не объявляет оплату реализованной.

- Источник `/home/user/orteka/local/modules/orteka.payment`, ветка `TASK-10094235_sberpay-web-sdk`, SHA `c3bcc1b32eac197d7511920de92ac71342811814`.
- Канонический граф `/home/user/MoreFoto/docs/04-bitrix-modules/backend-waves.json`; активная копия `docs/waves/graph.json`.
- PHP 8.4, Bitrix Main/D7, строгие слои текущего проекта; денежные инварианты оправдывают сохранение архитектуры уровня L.

В текущем scope: изучение источника, целевые границы/хранение/UI, уточнение G1/G2/I2, синхронизация графов и генератора, проверка DAG и 99 действующих API ID.

Вне текущего scope: runtime-код зависимых волн, реальные деньги, merge/deployment, реквизиты и история платежей Orteka, PayKeeper/YandexPay/1С, установка sale/catalog и хранение в b_sale_*, изменение W00. Реестр относится к платежам MoreFoto; импорт всей истории банковского мерчанта не предполагается.

## Решения и зависимости

1. Заказы и строки покупки принадлежат `morefoto.commerce`, попытки/провайдер/подтверждённые денежные факты — `morefoto.payments`, резервы/распределение возвратов и решения исполнения — `morefoto.settlement`. Всё хранится в собственных таблицах, миграции — `migrations.foundation`. Ни `Bitrix\Sale\Order/Payment`, ни ID платёжных систем Sale не используются.
2. По подтверждению пользователя 2026-09-21 договор эквайринга находится в процессе получения. Сейчас публикуется только план; реализация откладывается до соответствующих волн и получения банковских условий/настроек. СберПэй — выбранный провайдер (часть D09). Фискализация, точный refund/reconciliation контракт, настройки merchant/sandbox ещё открыты. Весь D09 не добавляется в acceptedImplementationDecisions; D10/D12 и прежние зависимости сохраняются.
3. G1 зависит от E5/F2: собственные заказы E5 и F2 отсутствуют в проверенном main. G2 зависит от G1/H1; I1 — от E5/G1/G2; I2 — от G1/I1. Ни заглушки заказов, ни перенос незамерженного кода не закрывают зависимости.
4. UI — существующий frontend RaBit API, раздел «Эквайринговые платежи». Данные реестра относятся к G1, денежный возврат и его UI — I2. Роли и область проверяются сервером через Access; исходная модель плана — организатор/куратор в разрешённой области.
5. Общие контракты — `rebit.share/lib/Contracts/`; реализации и DI принадлежат владельцам. Не создавать универсальный rebit.payment без отдельного сценария повторного использования.

Хранение Payments: локальная попытка и связь с заказом Commerce; сумма/валюта; provider и его идентификаторы; idempotency/fingerprint; сохранённое состояние pending/unknown/confirmed/failed; журнал подтверждённых фактов и попыток сверки. Уникальные ключи и блокировки выбираются под проверенные гонки. Settlement хранит собственную операцию возврата, резерв/allocations, статус, автора/причину/историю. Точные названия таблиц определяются в реализации, не выдаются за существующие.

Неизвестный исход сохраняется после timeout/сбоя фиксации. HTTP банка выполняется вне долгой SQL-транзакции. Callback/return — сигнал сверки, а не доказательство оплаты; проверять локальную попытку, merchant object ID, сумму/валюту. Подтверждённый денежный факт не стирается при refund; сумма confirmedRefunds + pendingReserve не превышает paid. Повтор unknown не вызывает второй refund.

## Обязательный интерфейс

- Реестр: дата/время, заказ, идентификатор попытки/банка, способ оплаты, сумма, состояние, подтверждённо возвращено, резерв возврата и доступный остаток; фильтры периода/статуса/заказа, серверная пагинация со стабильной сортировкой.
- Карточка: попытки, подтверждённые операции, возвраты, последние результаты сверки; без банковских credentials, raw payload и capability ключей.
- Возврат: полный или частичный (существующая модель SET-04), сумма/позиции, причина и явное подтверждение, ограничения files/production; сервер возвращает allowedActions и остаток. Два клика/две вкладки не создают два возврата.
- pending/unknown отображаются честно; кнопка retry доступна только по допустимому failed состоянию. Подтверждённый refund обновляет остаток/историю, не переписывает снимок покупки.
- Реальные данные реестра и UI не включаются с mock fallback. Desktop/mobile проверяются браузером.

Нужное расширение API: служебные список и карточка платежа (проектируемые `GET /api/v1/payments` и `GET /api/v1/payments/{payment_attempt_id}`), финансовые действия используют SET-04/05/06. В действующих 99 ID отдельных методов реестра нет. До старта G1 закрепить дополнительные ID/DTO/права/фильтры в генераторе API и Postman, не переименовывая старые ID; эта плановая правка не притворяется уже обновлённым REST-реестром.


### Банковский контракт: проверка источника 2026-09-21

Официальная [документация шлюза](https://ecomtest.sberbank.ru/doc) описывает полный и частичный `refund.do`. При этом обработка `x-idempotencyKey` помечена как находящаяся в разработке. Поэтому нельзя строить гарантию повторного refund только на этом заголовке: до I2 проверить фактическую версию merchant API и сценарий timeout, сохранять локальную операцию/резерв и сверять результат перед повтором. Это проверка документации, не успешный sandbox-вызов.

Официальные материалы для следующего среза: [СберПэй Web SDK](https://ecomtest.sberbank.ru/promo/sponline.pdf), [FAQ тестирования](https://ecomtest.sberbank.ru/promo/sberpay_tfaq.pdf). Адрес/версию merchant API нужно согласовать с выданным кабинетом; код Orteka сам по себе не доказывает доступность тех же функций у MoreFoto.
