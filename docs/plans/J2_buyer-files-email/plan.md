# J2 — автоматическая email-доставка файлов покупателю

## Цель

После подтверждённой оплаты покупатель автоматически получает письмо со ссылкой, по которой скачивает разрешённые файлы (J1 + J4) — по одному и ZIP; ручной повтор (FIL-05) и статус (FIL-06) доступны. Требование R04 плана владельца `docs/plans/OPS-telemos-feedback-plan/` (встреча 11.10.2026); граф: `docs/waves/graph.json`, волна J2 (MVP, открывает J3 и N3).

## Контекст

- Ветка `codex/j2-buyer-files-email` от main 0d02adf (merge #160). Зависимости H1, J1, E8, J4 слиты; решения D07, D10 приняты.
- Активация — после восстановления SMTP на сервере (#161; диагностика — ветка `codex/ops-gmail-delivery-diagnostics`, не слита): с сервера нет TCP до smtp.yandex.ru:465/587. Код и проверки J2 от этого не зависят; реальная доставка в контролируемый ящик — отдельная проверка запуска.

## Факты инвентаризации

- **H1 (rebit.notification):** контракт `Rebit\Share\Application\Contract\Notification\EmailNotificationInterface` (`queue`, `status`); таблица `b_rebit_notification_operation` (UNIQUE consumer+dedup, статусы `pending|processing|retryWait|accepted|unknown|failed`, `ACCEPTED_AT`, тело письма хранится открытым текстом без очистки); worker `app:notification:consume`, cron `app:notification:dispatch-pending` раз в минуту; повторы 30·2^(n−1) с до 3600 с, `maxAttempts` 1…10 (по умолчанию 3), затем `failed`. `accepted` = письмо отдано SMTP-серверу (msmtp), не доставка.
- **Оплата:** `PaymentReconciler` в одной транзакции пишет денежный факт и `applyPayment('paid')`; Commerce меняет статус и продлевает ключ заказа ровно один раз. Общего outbox/событий нет. Вызов H1 внутри платёжной транзакции опасен: публикация до commit, nested rollback Bitrix откатит оплату, повтор транзакции при deadlock.
- **Ключ заказа:** хранится только SHA-256, у заказа ровно один действующий ключ (`ux_mf_order_key_active`), по D07 перевыпуск заменяет прежний. Ссылку заказа покупателя в письмо положить нельзя.
- **Files:** только FIL-01…04; токен скачивания живёт 10 минут — в письмо не годится. Files не читает таблицы Commerce; email покупателя наружу из Commerce не отдаётся.
- **FIL-05/06 (w00):** `POST /public/orders/current/file-deliveries` `{channel:"email"}` → 202 `{id,status}`, `X-Order-Key` + `Idempotency-Key`; `GET …/file-deliveries/{id}` → `id,status,sentAt?,error?`. Кодов ошибок, лимита и списка нет. Персонал (FIL-07/08) — J3.
- **E2E:** consumer уведомлений на стенде не запущен, почтового приёмника нет; `verify-access.php` достаёт ссылку из тела письма в БД. `pay-fixture.php` (J4) оплачивает заказ кодом G1.
- **Оферта 2026-10-12** письмо с файлами не обещает; согласие покупателя покрывает отправку писем о заказе.

## Решения (варианты на момент паузы)

- **J2-DEC-01. Ссылка в письме.** Рекомендация: отдельная ссылка только на файлы со своим ключом (хранится SHA-256, срок — до конца месяца файлов, отзывается новой отправкой); открывает страницу «Ваши файлы» с теми же проверками J1. Ссылка заказа покупателя не меняется. Альтернативы: перевыпустить ключ заказа (старая ссылка покупателя перестанет работать, D07); второй действующий ключ заказа (меняет инвариант Commerce).
- **J2-DEC-02. Заказы, оплаченные до выкладки J2.** Рекомендация: автописьмо не отправляется; покупатель может запросить его сам на странице заказа (FIL-05). Альтернатива: разослать тем, у кого месяц файлов ещё идёт.
- **J2-DEC-03. Неподтверждённый email (D07).** Рекомендация: отправлять автоматически на email заказа; на странице заказа показать, куда ушло письмо; смена адреса — J3. Альтернативы: вводить email дважды при оформлении; подтверждать адрес кодом до отправки файлов.
- **J2-DEC-04. Видимость для оператора.** Рекомендация: в карточке заказа сотрудника — блок «Письма с файлами» (когда, статус, причина ошибки; без ссылок и ключей). Альтернатива: только журнал/БД до J3.

Технические решения (по умолчанию, без отдельного согласования):

- **T-01. Триггер.** Files-диспетчер раз в минуту спрашивает Commerce через контракт об оплаченных (не поздних) заказах без автописьма и создаёт запись доставки (UNIQUE заказ + `auto`) в своей транзакции, затем ставит письмо в H1 после commit. Платёжная транзакция не меняется; событие не теряется — его источник — сам факт оплаты.
- **T-02. Дедупликация.** Ключ H1 — `files:<deliveryId>`; повтор webhook/воркера не создаёт второе автописьмо (UNIQUE), FIL-05 создаёт новую доставку по `Idempotency-Key`.
- **T-03. Повторы.** H1 `maxAttempts=10` (≈5 ч при недоступном SMTP), затем `failed`: видно покупателю и оператору, покупатель может повторить.
- **T-04. Лимит FIL-05.** Не чаще раза в 10 минут и не больше 5 в сутки на заказ → 429 `DELIVERY_TOO_SOON`.
- **T-05. Новая отправка отзывает прежние ссылки на файлы этого заказа.**
- **T-06. Тело письма с ссылкой** очищается в H1 после финального статуса (`accepted`/`failed`); ссылки и ключи не логируются.
- **T-07. Поздняя оплата (`review`)** — письма нет до решения I3; FIL-05 отвечает 409 `FILES_UNAVAILABLE`.
- **T-08. Статусы FIL-06:** `pending` (pending/processing/retryWait/unknown), `accepted` («передано почтовому серверу», `acceptedAt`), `failed` (+ `error`). `sentAt` из w00 заменяется на `acceptedAt`.
- **T-09. Письмо** не продлевает срок J1 и не содержит вложений и оригиналов.

## Scope (после согласования решений)

1. **Files:** миграция `mf_file_delivery` (заказ, вид `auto|manual`, статус, операция H1, хеш ключа ссылки, срок, отзыв, ключ идемпотентности), диспетчер (cron), FIL-05/06, доступ по ключу ссылки к FIL-01…04, шаблон письма.
2. **Commerce:** контракт для Files — оплаченные заказы без письма и email заказа (только для доставки).
3. **Notification:** очистка тела письма после финального статуса.
4. **Frontend:** страница по ссылке из письма; на странице заказа — куда и когда отправлено письмо, «Отправить ещё раз»; карточка сотрудника (по DEC-04).
5. **Тесты:** PHPUnit (диспетчер, лимиты, отзыв, статусы, архитектура), frontend unit, live E2E (оплата фикстурой → диспетчер → ссылка из письма → файлы и ZIP; FIL-05/06; чужой/истёкший/отозванный ключ), верификатор MySQL.
6. **Документация:** `docs/waves/j2/`, граф (J4 `merged`, J2 `review`), контракт FIL-05/06.

## Исключено

- Восстановление SMTP на сервере — OPS #161.

## Риски и ограничения

- Запуск J2 невозможен до восстановления SMTP-маршрута (#161). Отправитель — ящик другого бренда (риск доставляемости).
- Опечатка в email отправит ссылку чужому (DEC-03).
- Реальная доставка не доказывается E2E — отдельная проверка с контролируемым ящиком после #161.

## Критерии приёмки

- Оплата → в течение ~минуты запись доставки и письмо в H1 с ссылкой на файлы; ссылка открывает файлы и ZIP позже 10 минут, в пределах права.
- Повтор сверки/webhook/диспетчера не создаёт второго автописьма; падение между оплатой и постановкой восстанавливается диспетчером.
- FIL-05: ручной повтор по `Idempotency-Key`, лимит, отзыв прежней ссылки; FIL-06: статус; ошибка письма не мешает скачиванию из заказа.
- Чужой, истёкший, отозванный ключ ссылки — 404; поздняя оплата — письма нет.
- Desktop/mobile: страница по ссылке, блок письма на странице заказа (и в карточке сотрудника по DEC-04).
