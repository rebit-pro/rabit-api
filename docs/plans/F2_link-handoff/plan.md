# F2 — подготовка и факт передачи ссылки

## Цель

Сотрудник получает ссылку галереи группы только после серверной проверки готовности материалов. Сроки приёма и доставки считаются от записанного факта ручной передачи ссылки родителям. Исправление ошибочной даты сохраняет историю. Операции HND-01…HND-05, владельцы `morefoto.handoff`, `morefoto.organization`, `morefoto.media`.

Источники: `docs/waves/graph.json`, канонический `../MoreFoto/docs/04-bitrix-modules/backend-waves.json`, контракты `../MoreFoto/docs/05-rest-api/endpoints.json`, домен `../MoreFoto/docs/02-domain/README.md`, D10 `docs/waves/w05/decisions.md`, прототип `frontend/src/modules/morefoto/handoff/*`.

## Scope

- HND-01 `GET /api/v1/group-links`: список ссылок и сроков по серверной области с фильтрами `institutionId`, `shootId`, `state` и пагинацией.
- HND-02 `GET /api/v1/groups/{group_id}/link`: карточка с ключом галереи, revision, signature, готовностью, проблемами, сроками и историей.
- HND-03 `POST …/link-preparations`: подтверждение проверки организатором и выдача ключа галереи.
- HND-04 `POST …/link-transmissions`: запись факта ручной передачи. Сроки меняет Organization, сообщения не отправляются.
- HND-05 `POST …/link-date-corrections`: исправление даты с причиной, историей и сохранением продления.
- Межмодульные контракты: календарь Organization с явной датой, каталог групп для Handoff, актор Access с блокировкой, материалы и ключ ссылки Media, готовность условий Commerce.
- Защита от гонки: разметка и обложка (MED-05/06) повторно проверяют редактируемость группы после блокировки ревизии медиа.
- Live frontend экрана «Ссылки и сроки», дата передачи в карточке съёмки.
- Unit/architecture/contract-проверки, E2E-спецификация и verifier на MySQL, отчёт волны.

## Не входит

- Переносы ребёнка и служебной заявки (MED-07, HND-10/11) и их влияние на подготовку — D3 (решение F2-D3-ORDER).
- Заказы E5, запрет разметки после заказа и цепочка «→ заказ» — проверяет D3 после E5.
- Продление приёма (SUP-06) — K2. F2 только сохраняет уже существующее продление при исправлении даты.
- Ограничения исправления после оплаты или производства по D12 — G1 и волны L. В F2 оплат и производства ещё нет.
- Отзыв и перевыпуск ключа из интерфейса. Внутренний отзыв E4 сохраняется, отозванная ссылка не работает.
- Ранее найденные дефекты вне F2: коды 401/403 `StaffAuthorization` (`SERVICE_UNAVAILABLE` вместо кода), issues #26–#28 по F1, долг `CalendarCommandInputDto` с валидацией в конструкторе. Их фиксирует отчёт, но не исправляет F2.
- Merge и deployment.

## Зависимости

- `dependsOn`: E3 (#20), F1 (#25), E4 (#30) — все в `main` 8cba22c. Гейты D05, D07, D10 приняты.
- F2 больше не зависит от D3 и E5: порядок F2 → D3 принят пользователем 22.09.2026, записан в обоих графах (`decisionEvidence.F2-D3-ORDER`).
- E5 (PR #37) не слита. F2 не использует её код и не опирается на `HttpException::getDetails()`. После её merge ожидаются текстовые конфликты в `graph.json`, `tools/run-browser-e2e.py`, `api/tools/e2e/prepare.php`, router и `CabinetLayout.vue`. Их разрешить при обновлении base и повторить затронутые проверки.

## Принятые решения (22.09.2026)

1. **Ключ галереи.** В `mf_gallery_capability` рядом с `TOKEN_HASH` хранится сырой ключ `TOKEN` открытым текстом (решение пользователя; риск раскрытия при утечке БД принят). Ключ выдаётся при первой подготовке HND-03. HND-02 возвращает действующий ключ, HND-01 ключ не отдаёт. Ключи, выданные до миграции без сохранённой копии, продолжают работать, но не показываются. При подготовке выдаётся новый ключ.
2. **Дата передачи.** `sentAt` — ISO 8601 со смещением, целые секунды. Дата не может быть в будущем по серверному времени и не может быть раньше выдачи ключа, округлённой вниз до минуты. Иначе 422.
3. **Списки сотрудников.** Незавершённые (не `transferred`) заявки F1 со строками этой группы блокируют подготовку проблемой `staffRequestsPending`. Такие группы до D3 не открываются.
4. **Версия ссылки.** Handoff ведёт собственный агрегат «ссылка группы» с revision: отсутствующая запись имеет revision 1, каждая успешная команда увеличивает её на 1. Изменения материалов, условий, названия группы и воспитателя меняют signature, а не revision.

## Архитектурные решения

- Signature — SHA-256 от серверного состояния:
  - группа: ID, название, тип, съёмка, учреждение, воспитатель;
  - отпечаток материалов Media: все кадры группы с revision и статусом, назначения детям, обложка;
  - отпечаток условий Commerce: действующие условия и товары группы с ревизиями;
  - незавершённые заявки сотрудников группы с их revision.
- Проблемы готовности — коды без текста (значения enum в camelCase по правилу проекта):
  - `noPhotos` — нет готовых кадров;
  - `photosProcessing` — есть кадры в обработке;
  - `unassignedPhotos` — готовые кадры без ребёнка;
  - `noProducts` — нет активного товара с ценой;
  - `staffRequestsPending` — незавершённые списки.
  - Кадры `failed`/`duplicate` в галерею не попадают и подготовку не блокируют.
  - Тексты формирует frontend.
- `prepared` = передача уже была, либо сохранённая подпись подготовки совпадает с текущей и проблем нет. HND-04 требует актуальной подготовки и совпадения signature клиента.
- Повторная передача после записанного факта — пустой повтор: 200 с текущими сроками без истории и без изменения revision, даже при устаревшей форме (правило прототипа и D10).
- HND-05:
  - требует записанной передачи, причины 5–500 символов после trim, `confirmed=true`, актуальных revision и signature;
  - дата должна отличаться от текущей;
  - `closesAt = max(sentAt + 7 дней, продлённое закрытие)`, `deliveryDueAt = closesAt + 7 дней` в Europe/Moscow;
  - сдвиг в прошлое может сразу закрыть приём.
- Порядок блокировок команды:
  1. состояние Access;
  2. учреждение → съёмка → группа (Organization);
  3. профиль и учётная запись актора (Access);
  4. идемпотентность;
  5. запись ссылки;
  6. ревизия медиа съёмки;
  7. условия Commerce в режиме share.

  Проверка идемпотентности после блокировки группы превращает конкурентный повтор с тем же ключом в воспроизведение результата.
- Права (D08):
  - читать могут организатор, куратор и руководитель в своих учреждениях, воспитатель в своих группах;
  - HND-03 — только организатор; HND-04 — организатор, куратор, воспитатель; HND-05 — организатор и куратор;
  - группа вне области — 404 `GROUP_NOT_FOUND`, запрещённое действие в своей области — 403 `FORBIDDEN`.
- Коды ошибок:
  - 409: `REVISION_CONFLICT`, `SIGNATURE_CONFLICT`, `LINK_NOT_READY`, `LINK_NOT_PREPARED`, `LINK_ALREADY_SENT`, `LINK_NOT_SENT`, `IDEMPOTENCY_CONFLICT`;
  - 422: `SENT_AT_IN_FUTURE`, `SENT_AT_BEFORE_LINK`, `SENT_AT_UNCHANGED`, `INVALID_SENT_AT`, `INVALID_REASON`, `REVIEW_REQUIRED`, `CONFIRMATION_REQUIRED` и строгие ошибки DTO.
- Слои:
  - новые SQL-репозитории в `Infrastructure`, порты в `Domain`/`Application`;
  - UseCase тонкие, с русским phpDoc;
  - DTO пассивные, преобразования в mapper;
  - контроллер чистый, на базе `AuthenticatedApiJsonController`;
  - канал логов `handoff`.
- Ответ HND-02 дополнен полями, нужными экрану:
  - `state`, `timezone`, `deliveryAt`, `referenceNow`;
  - названия учреждения, съёмки и группы, `kind`;
  - `photoCount`, `childCount`.
  
  Элемент HND-01 — та же проекция без `galleryToken` и истории. Уточнения вносятся в канонический `build.py` MoreFoto.

## Риски и ограничения

- Сырые ключи в БД: утечка БД раскрывает действующие галереи (принято пользователем).
- Глобальная блокировка состояния Access сериализует команды ссылок всей компании; для редких служебных операций допустимо.
- Новая заявка сотрудника, созданная одновременно с передачей, не блокируется (F1 не блокирует группу); остаётся D3.
- Отзыв сессии актора в течение одной команды не перепроверяется по Bearer, как в F1; роль и назначения перечитываются под блокировкой.
- Размер волны ориентировочно 4–5 тысяч рукописных строк; при приближении к 6 тысячам обсудить разделение.

## Критерии приёмки

- Группа открывается только после подготовки с актуальной signature и без проблем; любое изменение материалов или условий сбрасывает `prepared` до передачи.
- Факт передачи устанавливает `sentAt`, `closesAt = +7`, `deliveryDueAt = +7` по Europe/Moscow. Повтор не меняет сроков, исправление сохраняет прежние даты и причину в истории.
- Роли и области соблюдаются на сервере; повтор ключа возвращает тот же результат, другое тело — 409.
- Галерея MED-01 и quote COM-09 работают по выданной ссылке после передачи; до передачи — preparing, после закрытия — closed.
- Карточка съёмки (ORG-08) и галерея показывают фактические сроки; экран ссылок работает в live-режиме без mock.
- Все быстрые проверки зелёные; полный E2E и визуальная проверка выполнены после review.

## Тест-кейсы

1. **F2-GRAPH.** Предусловие: граф изменён. Действие: `python3 tools/verify-wave-graph.py docs/waves/graph.json`, `python3 /home/user/MoreFoto/docs/05-rest-api/validate.py`, `cd /home/user/MoreFoto && node docs/05-rest-api/validate-postman.cjs`. Ожидается: DAG, 99 API ID и негативные fixtures проходят, готовы E5 и F2.
2. **F2-CALENDAR.** Предусловие: value object календаря. Действие: `recordLinkSent`/`correctLinkSent` на границах месяца, года и 29 февраля, с будущей датой, повтором и продлением. Ожидается: +7/+7 в Europe/Moscow, повтор без изменений, продление сохраняется, будущее отклоняется. Команда: PHPUnit `morefoto.organization/tests/Unit`.
3. **F2-READINESS.** Предусловие: политика готовности. Действие: наборы с нулём кадров, обработкой, неназначенными, без товаров, с заявками; изменение любого компонента. Ожидается: точные коды проблем, изменение signature при любом изменении. Команда: PHPUnit `morefoto.handoff/tests/Unit`.
4. **F2-PERMISSIONS.** Предусловие: роли О/К/Р/В с разными областями. Действие: чтение и три команды. Ожидается: матрица D08, 404 вне области, 403 для запрещённого действия. Команда: PHPUnit и E2E.
5. **F2-PREPARE.** Предусловие: готовая группа. Действие: HND-03 с актуальными revision/signature и флагами. Ожидается: 200, revision+1, `prepared=true`, выдан ключ, событие `prepared`. Негатив: проблемы → 409 `LINK_NOT_READY`; устаревшие revision/signature → 409; флаг false → 422 `REVIEW_REQUIRED`; после передачи → 409 `LINK_ALREADY_SENT`. Команды: PHPUnit, E2E.
6. **F2-TRANSMIT.** Предусловие: подготовленная группа. Действие: HND-04 с `sentAt` в пределах [выдача, now]. Ожидается: 200, сроки +7/+7, событие `transmitted`, запись в журнале Organization, галерея `open`. Негатив: подготовка устарела → 409 `LINK_NOT_PREPARED`; будущая дата → 422 `SENT_AT_IN_FUTURE`; раньше выдачи → 422 `SENT_AT_BEFORE_LINK`. Команды: PHPUnit, E2E, verifier.
7. **F2-REPEAT.** Предусловие: передача записана. Действие: повтор HND-04 тем же ключом, другим ключом и устаревшей формой. Ожидается: тот же ответ, сроки и история не изменились. Тот же ключ с другим телом → 409 `IDEMPOTENCY_CONFLICT`. Команды: PHPUnit, E2E.
8. **F2-CORRECT.** Предусловие: передача записана. Действие: HND-05 куратором с причиной. Ожидается: новые сроки, событие `corrected` с прежними датами и причиной. Негатив: причина короче 5 или длиннее 500 → 422 `INVALID_REASON`; та же дата → 422 `SENT_AT_UNCHANGED`; до передачи → 409 `LINK_NOT_SENT`; воспитатель → 403. Команды: PHPUnit, E2E.
9. **F2-EXTENSION.** Предусловие: закрытие продлено внутренним `extend`. Действие: исправление даты передачи. Ожидается: продлённое закрытие сохраняется, если оно позже нового `sentAt + 7`. Команды: PHPUnit, verifier.
10. **F2-CLOSE-BOUNDARY.** Предусловие: исправление или прошлые данные на MySQL. Действие: `now == closesAt` и `now = closesAt − 1 с`. Ожидается: `closed` и `open` соответственно в HND-02, ORG-08 и MED-01; COM-09 в закрытой группе → 409 `GALLERY_CLOSED`. Команды: PHPUnit, verifier.
11. **F2-INVALIDATION.** Предусловие: подготовленная группа. Действие: изменить условия группы (COM-07), обложку или назначение (MED-05/06), название группы. Ожидается: `prepared=false`, новая signature, передача отклоняется 409. Команды: PHPUnit, E2E.
12. **F2-RACE-MEDIA.** Предусловие: передача и разметка одновременно. Действие: unit-проверка порядка — повторная проверка `groupEditable` после `lockRevision`. Ожидается: разметка после передачи → 409 `GROUP_LOCKED`. Команда: PHPUnit `morefoto.media/tests/Unit`.
13. **F2-GALLERY-QUOTE.** Предусловие: переданная ссылка. Действие: открыть `/g/<token>`, выбрать кадр и товар, получить quote. Ожидается: галерея `open` с фактическими сроками, COM-09 200; отозванный ключ → 404. Команда: E2E.
14. **F2-TOKEN.** Предусловие: HND-03 выполнена. Действие: HND-02 разными ролями, HND-01. Ожидается: ключ в карточке, отсутствует в списке; в БД хранятся `TOKEN` и его SHA-256. Команды: E2E, verifier.
15. **F2-ARCH.** Предусловие: новые классы. Действие: architecture-тесты контроллера и DTO, PHPStan, phplint, php-cs-fixer по изменённым файлам. Ожидается: чистый контроллер, пассивные DTO, русский phpDoc у UseCase/Service, 0 ошибок. Команды: PHPUnit, PHPStan, phplint, php-cs-fixer.
16. **F2-CONTRACT.** Предусловие: DTO и serializer. Действие: строгий разбор тел/query/path/header, форма ответов, `no-store`. Ожидается: лишние поля и неверные типы → 422, ответы по контракту. Команда: PHPUnit contract-тесты.
17. **F2-UI.** Предусловие: live-стенд. Действие: организатор проверяет и передаёт ссылку, копирует её, куратор исправляет дату, руководитель только читает. Ожидается: реальные HTTP без mock, тексты проблем, история. Команды: `npm run check`, `npm run test:commerce`, `make test-e2e`.
18. **F2-VISUAL.** Предусловие: live-стенд. Действие: экран ссылок и диалоги на 1440×1000 и 390×844. Ожидается: нет горизонтального переполнения, тексты читаемы; скриншоты просмотрены. Команда: `make test-e2e` + ручной просмотр PNG.
19. **F2-PUBLISH.** Предусловие: быстрый gate зелёный. Действие: `git diff --check`, commit/push, один PR в `main`. Ожидается: PR с зависимостями, решениями, ограничениями и отложенным полным E2E. Команда: `gh pr create`.
