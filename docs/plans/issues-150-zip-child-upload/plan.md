# #150: загрузка кадров из ZIP с папками детей и автоматическими буквами

## Цель

В рабочем месте «Кадры» два режима загрузки в выбранную группу:

1. **По фото** — текущий поток без изменений: файлы → очередь → превью → ручная разметка буквой.
2. **ZIP по детям** — один или несколько архивов. Папка с кодом (`A`, `B`, …, `AA`, `BK`) — ребёнок с этим
   кодом. Папка с префиксом `GROUP` (`GROUP-1`, `GROUP-F`) — групповые кадры: они лежат в архиве один раз и
   достаются каждому ребёнку группы. Коды проставляются автоматически при загрузке, ручная разметка не нужна.

Фотограф видит этапы архива: чтение содержимого, сверку «папка → код», отправку оригиналов и создание защищённых
превью — общими индикаторами и по каждому ребёнку.

## Контекст (main `41b1146`)

- Код ребёнка — латиница `^[A-Z]{1,3}$`: `PhotoInputMapper`, `frontend/.../photos/rules.ts::validChildCode`,
  генератор `childCodeAt` (`A…Z`, `AA…`). Кадр получает номер `A001` при привязке (`photoCode`).
- Загрузка: `POST /api/v1/shoots/{shoot_id}/photos` (multipart, один файл, `groupId`, `fingerprint`) →
  `UploadPhotoUseCase` → очередь превью. Дубль по содержимому в съёмке возвращает `duplicate` + `existingPhotoId`.
- Разметка: `POST /api/v1/groups/{group_id}/photo-assignments` → `AssignPhotosUseCase`: блокировка revision съёмки,
  идемпотентность, только кадры `ready`, до 100 кадров за запрос, ребёнок создаётся по коду при первой привязке.
- Очередь фронта `usePhotoQueue`: 2 параллельные отправки, до 2000 файлов, 25 МБ/40 Мп на файл, опрос статуса,
  черновик в `sessionStorage`. Прогресс — `MfProgress` «Загружено» и счётчики.
- Лимиты сервера: PHP `post_max_size = 200M`, nginx `client_max_body_size 1000M`. Архив съёмки — единицы ГБ.

## Scope

- Переключатель режима в `PhotoUpload.vue`: «По фото» / «ZIP по детям».
- Чтение ZIP **в браузере** без загрузки архива целиком в память: оглавление читается сразу, каждый файл
  распаковывается по очереди в момент отправки.
- Разбор структуры и экран сверки: папка → предложенный код → число кадров, проблемы (пустые папки, недопустимые
  файлы, файлы вне папок, конфликт кодов, превышение лимитов). Код в сверке можно поправить вручную до старта.
- Отправка каждого файла текущим endpoint с новым необязательным полем `childCodes`; сервер привязывает кадр к
  ребёнку (или ко всем детям группы для группового кадра) атомарно при приёме. Файл хранится один раз.
- Прогресс архива: «Прочитано/Отправлено/Превью готовы» + таблица по детям (готово / в работе / требуют внимания).
- Продолжение после перезагрузки вкладки: повторный выбор того же архива продолжает незавершённые файлы;
  повторная отправка безопасна за счёт дедупликации.
- Backend unit, frontend unit, live E2E, визуальная проверка desktop/mobile.

## Вне scope

- Приём ZIP на сервере и серверная распаковка (см. ZIP-DEC-01).
- Кириллические коды детей в системе (ZIP-DEC-02: только латиница).
- Отдельная сущность «групповой кадр группы» в галерее и заказах: групповой кадр — общий кадр всех детей
  (ZIP-DEC-03), модель данных не меняется.
- Групповые кадры в режиме «По фото»: там по-прежнему можно вручную привязать кадр к нескольким детям.
- Вложенные папки как отдельные дети, несколько групп в одном архиве (одна загрузка = одна выбранная группа).
- Демо-режим (`VITE_API_MOCKS_ENABLED`): переключатель ZIP в нём скрыт.
- Изменение графа волн: задача оперативная, вне `graph.json`.

## Решения

Статус на 26.09.2026: ZIP-DEC-02 и ZIP-DEC-03 (в редакции после проверки съёмки 158) приняты пользователем. ZIP-DEC-01/04/05/06 — рекомендации плана,
пользователь может оспорить на ревью.

### ZIP-DEC-01. Где распаковывать архив — принято в плане, можно оспорить

Рекомендация: в браузере, библиотекой `@zip.js/zip.js` (BSD-3, случайный доступ к `Blob`, нативный
`DecompressionStream`, поддержка кодировки имён CP866). Загружается динамическим `import()` только в режиме ZIP.

| Вариант | Плюсы | Минусы |
|---|---|---|
| Браузер (рекомендуется) | нет новых лимитов сервера, пофайловый прогресс и дедупликация как сейчас, без временного места на диске сервера | новая frontend-зависимость (~30–40 КБ gzip, отдельный chunk) |
| Сервер | фронт проще | архив > 200 МБ не пройдёт, двойное место на диске, долгий единый запрос, прогресс превью только после полной распаковки, повтор при обрыве — с нуля |
| Выбор папки (`webkitdirectory`) вместо ZIP | без библиотеки | не то, что готовит фотограф; оставить как возможное расширение |

### ZIP-DEC-02. Имена папок — принято: только латиница

Ответ пользователя 26.09.2026: папки называются латиницей (`A`, `B`, `AA`, `BB`); кириллица в первом описании —
следствие диктовки. Имя папки приводится к верхнему регистру и обрезается по пробелам; допустимые коды —
`^[A-Z]{1,3}$`, как во всей системе. Папка с кириллицей или другим именем — ошибка сверки
«Имя папки должно быть латинской буквой: A, B, AA». Отдельная подсказка, если имя похоже на кириллическую
`А/В/С/Е/…`, чтобы фотограф увидел причину, а не «невидимую» ошибку.

### ZIP-DEC-03. Групповые кадры — принято: папка `GROUP…`, кадр получают все дети группы

Первая редакция (26.09.2026): `AA`/`BB` — групповые. Проверка реальной съёмки 158 её опровергла: 59 детей
получили коды `A…Z, AA…AZ, BA…BK`, `AA` и `BB` — обычные дети, а групповые папки `F`, `L`, `U`, `AX` по имени от
детей не отличаются (признак был только в `158_соответствие.csv`). Решение пользователя после проверки:

- Групповая папка — имя с префиксом `GROUP` без учёта регистра, дальше любое окончание: `GROUP`, `GROUP-1`,
  `GROUP_F`, `group 2`. Такое имя не может совпасть с кодом ребёнка (`^[A-Z]{1,3}$`), путаницы нет.
  Скрипт подготовки архива называет групповые папки так вместо очередной буквы.
- Любая другая папка с допустимым кодом — ребёнок. Недопустимое имя — ошибка сверки (ZIP-DEC-02).
- На экране сверки у каждой папки есть переключатель «групповые»: им можно поправить архив, подготовленный без
  префикса, не пересобирая его. Для папки-кода, отмеченной вручную, код ребёнку не присваивается.
- Групповой кадр привязывается к каждому ребёнку группы: детям из всех выбранных архивов и детям, уже
  размеченным в этой группе. Модель данных прежняя: один кадр, несколько привязок (`mf_photo_assignment`),
  файл не дублируется. Отдельного «ребёнка-группы» в системе не появляется.
- Родитель видит групповые кадры в наборе своего ребёнка; заказ оформляется на реального ребёнка, поэтому печать и
  выдача раскладываются по его конверту.
- Групповые папки отправляются после папок детей, поэтому групповые кадры идут в конце набора каждого ребёнка.
- Для съёмки 158: 59 детей × 15 групповых кадров = 885 дополнительных привязок, файлов по-прежнему 591.

Следствия, которые нужно знать:

- Перенос ребёнка в другую группу (MED-07) отклоняется для набора с общими кадрами (`SHARED_PHOTO`) — групповой
  снимок принадлежит старой группе. Если перенос нужен, групповые кадры сначала снимаются с ребёнка вручную.
  Отдельного изменения переноса в этой задаче нет.
- Ребёнок, добавленный в группу после загрузки архива, групповые кадры автоматически не получает. Повторная
  загрузка той же части с групповой папкой это исправит: дубль по содержимому привяжется к новым детям без новых
  файлов.

### ZIP-DEC-04. Где проставлять код — рекомендация: на сервере при приёме

Необязательное поле `childCodes` в `POST /api/v1/shoots/{shoot_id}/photos`: коды через запятую, 1–100 штук
(`A` для кадра ребёнка, `A,B,C,…` для группового кадра). Multipart-поля в `rebit.share` строковые, поэтому список
передаётся строкой и разбирается `PhotoInputMapper`. Список для группового кадра собирает сверка: дети архива плюс
уже размеченные дети группы.

`UploadPhotoUseCase` после регистрации кадра в одной транзакции блокирует revision съёмки, повторно проверяет, что
группа редактируема, для каждого кода находит или создаёт ребёнка и привязывает кадр (в т. ч. в статусе
`processing`), один раз продвигает revision. Ответ дополняется `childCodes`. Без поля поведение прежнее.

Альтернатива — фронт ждёт `ready` и вызывает существующий `photo-assignments` пачками по 100: без изменений
backend, но разметка теряется при закрытии вкладки до конца обработки, а revision-конфликты с ручной разметкой
обрабатывает клиент. Не рекомендуется.

Следствия серверного варианта:

- Привязка `processing`-кадра допустима: галерея, счётчики и готовность группы и так учитывают только `ready`.
  Сбой превью оставляет кадр `failed` с кодом; повторная отправка того же файла возвращает тот же кадр (текущая
  дедупликация) и привязка не дублируется.
- Дубль в той же группе: существующий кадр привязывается к кодам запроса (повтор архива идемпотентен и
  догоняет групповыми кадрами новых детей). Дубль из другой группы не привязывается, файл помечается
  «уже есть в группе …».
- Порядок номеров `A001…` — порядок приёма. Очередь отправляет файлы в порядке имён внутри папки; при 2
  параллельных потоках возможна перестановка соседних кадров — допустимо (номер не несёт смысла для покупателя).
- Ручная разметка в этой же вкладке во время загрузки ZIP получит `REVISION_CONFLICT`; кнопки разметки в режиме
  активной ZIP-загрузки блокируются с подсказкой, workspace обновляет revision после каждого изменения.

### ZIP-DEC-05. Существующие коды в группе — рекомендация: дополнять

Если у ребёнка `A` в группе уже есть кадры, новые кадры из папки `A` добавляются к нему. Сверка показывает
предупреждение «у A уже N кадров — новые добавятся». Переименование и объединение наборов не выполняются.

### ZIP-DEC-06. Структура архива — принято в плане

- Служебные записи игнорируются: `__MACOSX/`, `.DS_Store`, `Thumbs.db`, `desktop.ini`, скрытые файлы.
- Если все папки лежат внутри одной общей корневой папки, которая сама не является кодом, она снимается.
- Папка ребёнка = первый уровень после корня. Вложенные подпапки ребёнка разворачиваются в него.
- Файлы вне папок — проблема сверки «без кода»: их можно исключить или загрузить без привязки (тумблер).
- Допустимые файлы — по расширению `.jpg/.jpeg/.png/.webp`; окончательную проверку делает сервер, как сейчас.
- Имена без флага UTF-8 декодируются как CP866 (архивы проводника Windows), с флагом — UTF-8.
- Лимиты текущей очереди: до 2000 файлов и 25 МБ на файл; архив сверх лимита не стартует, сверка объясняет почему.

### ZIP-DEC-07. Несколько архивов за одну загрузку — принято в плане

Пользователь 26.09.2026 готовит съёмку 4,4 ГБ и делит её на архивы примерно по 500 МБ.

- Делить архив не обязательно: архив целиком на сервер не отправляется, браузер читает его по одному файлу.
  Архив больше 4 ГБ требует формата Zip64; его понимает `@zip.js/zip.js`, проверка — T17.
- Если архивов несколько, их можно выбрать или перетащить **одновременно**. Сверка объединяет их в один план:
  папка `A` из разных частей — один ребёнок, групповые наборы получают полный список детей из всех частей.
  Групповые файлы всех частей отправляются после файлов детей.
- Части должны быть самостоятельными ZIP-архивами. Тома одного архива (`.z01`, `.zip.001`) по отдельности не
  читаются; сверка распознаёт их и объясняет, как пересобрать.
- Если части загружаются в разное время, групповой кадр получит только детей, известных на момент его загрузки.
  Повторная загрузка части с `AA`/`BB` после остальных догоняет привязки (T16), новых файлов не создаёт.

### ZIP-DEC-08. Большой объём без отказов — принято в плане

Цель пользователя: загрузка нескольких гигабайт без отказов и без отката уже принятого.

Принцип: каждый файл — независимая идемпотентная операция. Ошибка одного файла не откатывает принятые файлы и не
останавливает очередь. Повтор того же файла безопасен: сервер находит его по SHA-256 содержимого и не создаёт
второй кадр, а привязки не дублируются.

| Источник отказа | Что есть сейчас (main `41b1146`) | Что делаем |
|---|---|---|
| Недопустимый файл (формат, > 25 МБ, > 40 Мп, пустой) | сервер отклоняет файл во время загрузки | сверка до старта: расширение и размер по оглавлению архива, размеры в пикселях по заголовку изображения; проблемные файлы видны сразу списком, старт — только для допустимых. Лимиты сверяются на реальном архиве (шаг 3): если кадры камеры больше 25 МБ или 40 Мп, решение о лимитах принимается до реализации |
| Обрыв сети, 408/429/5xx, таймаут | файл получает «ошибку» и ждёт ручного повтора | автоповтор до 6 раз с паузой 2 → 5 → 15 → 30 → 60 → 120 с; при `offline` очередь ставится на паузу и продолжает сама при `online`. Ручной повтор остаётся для исчерпанных попыток |
| Ошибка 4xx по содержанию (формат, `FINGERPRINT_MISMATCH`) | ошибка файла | без автоповтора, причина в списке «требуют внимания», очередь идёт дальше |
| Истечение сессии (401) | сессия сбрасывается, уход на вход, очередь в памяти теряется | до старта: если сессия истечёт раньше расчётного конца загрузки (объём ÷ измеренная скорость ×2), предложить перезайти. Во время загрузки: 401 ставит очередь на паузу с сохранённым прогрессом; после входа — повторный выбор архивов продолжает с места остановки |
| Закрытие или перезагрузка вкладки, сон ноутбука | черновик очереди в `sessionStorage`, файлы нужно выбрать снова | прогресс архива хранится в `localStorage` по отпечатку архива (имя, размер, дата) и группе: при повторном выборе принятые файлы пропускаются без повторной отправки. Во время загрузки запрашивается Screen Wake Lock и показывается предупреждение при закрытии вкладки |
| Группа передана во время загрузки | `GROUP_MEDIA_LOCKED` на каждый файл | первый такой ответ останавливает очередь с понятным текстом, остальные файлы не отправляются |
| Нехватка места на сервере | не проверяется | перед первой загрузкой на stage/prod: свободное место ≥ 2,5 × объёма съёмки (оригиналы + превью + запас), запись в progress |
| Медленная подготовка превью | очередь RabbitMQ, dispatcher для зависших | загрузка оригиналов не ждёт превью; индикатор «Превью готовы Y из N» показывает отставание очереди. На реальной съёмке замеряется скорость воркера (T15); если отставание больше часа — отдельное issue о числе воркеров |
| Лимиты цепочки прокси/PHP | PHP `upload_max_filesize = 200M`, `max_execution_time = 300` | один файл ≤ 25 МБ укладывается; цепочка nginx frontend → API на stage проверяется загрузкой файла 25 МБ (T19) |

Параллельность остаётся 2 потока. На реальном архиве замеряется скорость; увеличение до 3–4 — только по замеру,
чтобы не перегрузить сервер и канал.

## Архитектура изменений

### Backend (`morefoto.media`)

- `UploadPhotoRequestDto`: `#[FormField] public ?string $childCodes` (паттерн `^[A-Z]{1,3}(,[A-Z]{1,3}){0,99}$`,
  код ошибки `INVALID_CHILD_CODES`). `PhotoInputMapper` убирает повторы и передаёт `list<string>` в
  `UploadPhotoInputDto::$childCodes`.
- `UploadPhotoUseCase`: после регистрации вызывает `ChildAssignmentOnUpload` (Application Service) — транзакция через
  `MediaTransactionInterface`, `MediaMutationRepository::lockRevision/child/assign/advanceRevision`, новый метод
  чтения внутреннего ID кадра группы без условия `ready`. Логирование этапа `assignMs`, без содержимого запроса.
- `UploadPhotoOutputDto`/`UploadPhotoResultDto`/mapper: `childCodes` (пустой список, если кадр не привязан).
- Без миграций: таблицы `mf_media_child`/`mf_photo_assignment` уже есть.
- phpDoc нового Service и обновлённый phpDoc `UploadPhotoUseCase` по правилу CLAUDE.md.

### Frontend (`frontend/src/modules/morefoto/photos`)

- `archive.ts` — чистые функции: нормализация путей, код из имени папки (ZIP-DEC-02), разделение на детей и
  групповые наборы по префиксу `GROUP` и ручной отметке (ZIP-DEC-03), построение плана `{ code, kind: 'child' | 'group', folder, entries[] }[]`,
  списка кодов для групповых кадров и списка проблем. Без Vue и без zip-библиотеки → покрывается `node --test`.
- `zip-reader.ts` — тонкая обёртка над `@zip.js/zip.js`: чтение оглавления, распаковка записи в `File`.
- `upload-retry.ts` — чистая политика: какие ошибки повторять, пауза по номеру попытки, реакция на 401/409/offline.
  Покрывается `node --test`.
- `archive-progress-store.ts` — прогресс архива в `localStorage` (`try/catch`, при недоступности хранилища работа
  продолжается в памяти): ключ = отпечаток архива + группа, значение = принятые пути записей.
- `usePhotoQueue`: `addArchive(plan, groupId)` создаёт задания с `childCodes`, `archivePath`, сначала дети, затем
  групповые наборы; воркер распаковывает запись лениво перед отправкой; `photosApi.upload` передаёт `childCodes`. Черновик в `sessionStorage` хранит путь,
  размер и код, при повторном выборе того же архива задания продолжаются.
- `PhotoUpload.vue`: переключатель режима; в режиме ZIP — выбор/перетаскивание одного или нескольких `.zip`, состояние «Читаем архив…»,
  компонент сверки `ArchivePlan.vue`: дети (папка/код/кадров), групповые наборы (папка/кадров/«получат N детей»),
  предупреждения и кнопка старта.
- `ArchiveProgress.vue`: два индикатора «Отправлено X из N» и «Превью готовы Y из N» + строки по детям и
  групповым наборам.
  `UploadQueue` показывает бейдж кода у файла.
- `PhotoWorkspace`: блокировка ручной разметки во время активной ZIP-загрузки, обновление списка/сводки по мере
  готовности (существующий `photosChangedEvent`).

Оценка объёма: ~1300–1800 рукописных строк — одна задача, в пределах лимита волны.

## Риски

- CP866/UTF-8 имён: папки латинские, но имена файлов внутри могут быть русскими — неверная кодировка испортит
  только имя файла в списке, не код; тест-кейс T08 с обоими архивами.
- Групповой кадр на 25–30 детей = столько же привязок в одной транзакции под блокировкой revision съёмки;
  для 2000 файлов с парой десятков групповых — порядка тысячи строк, приемлемо. Время записи `assignMs` в журнале.
- Большой архив на слабом устройстве: чтение оглавления — O(число записей), распаковка по одной записи;
  в памяти не больше `parallel` распакованных файлов.
- Сжатые JPEG почти не сжимаются: архив «store» и «deflate» должны работать одинаково — оба в тестах.
- Конкурентная ручная разметка в другой вкладке получает `REVISION_CONFLICT` чаще — ожидаемо, текст ошибки уже
  есть.
- Новая зависимость фронта — проверка лицензии и размера chunk в сборке.

## Критерии приёмки

- Режим «По фото» работает как раньше (регрессия покрыта существующими E2E).
- ZIP с папками `A`, `B`, `AA`, `GROUP-1` загружается в выбранную группу; после обработки кадры `A`/`B`/`AA`
  привязаны к своим детям, кадры `GROUP-1` — к каждому ребёнку группы, без ручных действий; файл группового кадра
  хранится один раз; групповые кадры идут в конце набора ребёнка. Ребёнка-группы не появляется.
- Съёмка 158 (11 частей, 591 файл, 59 детей, 15 групповых кадров в папках `GROUP-…`) загружается без отказов.
- Во время загрузки видно: этап чтения архива, сверку, «Отправлено X из N», «Превью готовы Y из N», разбивку по детям,
  проблемные файлы с причиной и повтором.
- Повторная загрузка того же архива не создаёт дублей кадров и привязок.
- Архив не загружается целиком ни в память браузера, ни на сервер.
- Несколько архивов выбираются одновременно и загружаются одним планом; архив больше 4 ГБ (Zip64) читается.
- Кратковременный обрыв сети, 5xx и перезагрузка вкладки не требуют ручных действий по каждому файлу:
  очередь повторяет или продолжает сама, принятые файлы повторно не отправляются. Ошибка файла не откатывает
  принятые.
- Загрузка в переданную (заблокированную) группу отклоняется целиком с понятным текстом.
