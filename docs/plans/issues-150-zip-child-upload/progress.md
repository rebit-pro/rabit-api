## Журнал

### 2026-09-26

- Изучен текущий поток: `UploadPhotoUseCase` (приём без кода), `AssignPhotosUseCase` (только `ready`, revision,
  идемпотентность, ≤100 кадров), `usePhotoQueue` (2 потока, 2000 файлов, `sessionStorage`), коды `^[A-Z]{1,3}$`.
- Ограничения сервера: PHP `post_max_size = 200M` → серверный приём архива съёмки невозможен без смены лимитов;
  выбрана распаковка в браузере (ZIP-DEC-01).
- Открытых issue/PR по ZIP-загрузке нет; создан #150.
- Подготовлен план; решения ZIP-DEC-02/03 вынесены пользователю, остальные — с рекомендацией.
- Ответ пользователя: папки только латиницей (кириллица была от диктовки) → ZIP-DEC-02 «только латиница».
  `AA`/`BB` — групповые фото, которые кладут один раз вместо копирования в папку каждого ребёнка → ZIP-DEC-03:
  удвоенная буква = групповой набор, кадр привязывается ко всем детям группы (архив + уже размеченные).
- Поле загрузки стало `childCodes` (строка через запятую): multipart-поля `rebit.share` (`FormField`) только
  строковые. Добавлен T16 (догон групповых кадров для нового ребёнка повторной загрузкой).
- Пользователь: съёмка 4,4 ГБ, делится на архивы по ~500 МБ; требование — большие объёмы без отказов и отката.
  Найдено: 401 сбрасывает сессию и уводит на вход (`frontend/src/api/http.ts`), сессия 24 ч без продления
  (`REBIT_TOKEN_TTL_HOURS`); сетевые ошибки не повторяются автоматически; черновик очереди в `sessionStorage`.
  Добавлены ZIP-DEC-07 (несколько архивов одним планом, Zip64, тома не поддерживаются) и ZIP-DEC-08 (сверка
  лимитов до старта, автоповтор, пауза офлайн/401, прогресс в `localStorage`, Wake Lock, проверки stage),
  тест-кейсы T17–T22, шаг 3a.
- Шаг 3 — проверка реальной съёмки 158 (оригиналы и `158_parts` в Downloads пользователя; имена детей и
  персональные данные в архивах отсутствуют, в журнал не переносятся):
  - оригиналы: 591 JPEG, 4,73 ГБ, все 3000×4500 (13,5 Мп), размер 6,3–10,1 МБ → лимиты 25 МБ / 40 Мп
    не нарушаются, отказов по лимитам не будет;
  - части: 11 самостоятельных ZIP (`158_part01…11.zip`, 71 МБ–492 МБ), метод store, без Zip64, флаг UTF-8
    не выставлен (имена ASCII, декодирование не важно); структура `<КОД>/<КОД><NNN>.jpg`, без общего корня,
    глубина 2; каждая папка целиком в одной части; 591 файл, повторов имён нет;
  - 63 папки подряд: `A…Z`, `AA…AZ`, `BA…BK`; рядом `158_соответствие.csv` (Архив;Буква;Тип;Новое имя;
    Исходный файл): 59 папок — «ребёнок» (в т. ч. `AA`, `BB`), 4 папки — «группа»: `F` (9), `L` (1), `U` (2),
    `AX` (3), всего 15 групповых кадров;
  - вывод: правило ZIP-DEC-03 «удвоенная буква = групповые» на реальных данных неверно — при 59 детях `AA`, `BB`
    обычные дети. Групповую папку по имени отличить нельзя; нужен явный признак.
- Ответ пользователя: групповые папки отмечаются префиксом `GROUP` (`GROUP-1`, `GROUP-F`), на сверке есть
  ручной переключатель; групповой кадр получают все дети группы. ZIP-DEC-03 переписано, T07/T09/T15/T18 обновлены.
- Backend: необязательное multipart-поле `childCodes` (`^[A-Z]{1,3}(,[A-Z]{1,3}){0,99}$`, 422 `INVALID_CHILD_CODES`),
  Application Service `UploadChildAssignment` (транзакция, `lockRevision`, повторная проверка редактируемости →
  409 `GROUP_MEDIA_LOCKED`, `groupPhoto` без условия `ready`, `child` + `assign` на каждый код, одно продвижение
  revision). Дубль размечает кадр-владелец содержимого (`existingPhotoId`), кадр другой группы не размечается.
  Разметка идёт после постановки превью в очередь, чтобы сбой разметки не задерживал превью. `LogSanitizer`
  пропускает `assignMs`; число кодов пишется в существующий `added`.
