## Принятые решения

1. Пользователь 17.11.2026 выбрал **7 суток с момента готовности ZIP**. Состав и манифест сохраняются после удаления файла.
2. Пользователь выбрал **всю историю оплаченных покупок учреждения**, включая старые заказы с истёкшим сроком покупательской выдачи. Исходники должны существовать; покупательские ключи и сроки не продлеваются. Служебная выгрузка не восстанавливает удалённые оригиналы.
3. Только `PAYMENT_STATUS=paid`, без неразрешённой поздней оплаты, только `digital`/`bundle`, `COVERED_BY_GIFT=0`. Печатные строки, GIFTS, неоплаченные и ожидающие решения оплаты исключены.
4. Комплект раскрывается по J1 через текущие `ready`-кадры купленного ребёнка в съёмке заказа. Состав фиксируется при запросе; новые покупки и позднее добавленные кадры входят в следующий выпуск. Один photoId внутри группы выдаётся один раз; все основания сохраняются для сверки.
5. Срок закрытия печати не проверяется. Все существующие группы и съёмки учреждения участвуют на момент снимка. Сервер проверяет роль/принадлежность и при создании, и при скачивании: организатор управляет, куратор читает своё учреждение; другие роли не получают архивных прав.
6. Исходный basename сохраняется. Совпадения имён разводятся дополнительным каталогом с устойчивым ID фото, совпадения имён групп — устойчивым ID группы. Небезопасное имя даёт явную ошибку, без тихого переименования. Папки Nшт отсутствуют.
7. Пустой результат, очередь, сборка, ошибка, готовность и истечение явно различаются. Отсутствие нужного оригинала или сбой источника не дают частичного успешного ZIP. Повтор запроса идемпотентен, зависшая сборка восстанавливается; готовый файл публикуется атомарно.

### Контракты и HTTP

- Commerce: `PurchasedDigitalLinesInterface::forInstitution(int $institutionId, DateTimeImmutable $at): array` → список типизированных строк с order/line/group/shoot/child/photo и основанием покупки, одной выборкой учреждения. Репозиторий читает Result, адаптер превращает его в контрактные DTO. Исходные строки/покупатели не сериализуются целиком.
- Планируемые staff endpoints: GET/POST `/api/v1/institutions/{institution_id}/digital-archives`; GET `/api/v1/institution-digital-archives/{archive_id}`; GET `.../{archive_id}/download`; GET `.../{archive_id}/manifest`.
- POST принимает Idempotency-Key; Bearer разрешается общей обвязкой. GET download выдаёт короткую подписанную ссылку на отдельный content endpoint; перед байтами повторно проверяются актуальная роль, учреждение и срок. Токен покупателя не используется.
- Ошибки: общие 401/403/404, конфликт повторного ключа/параллельной операции 409, невалидный ввод 422; ошибки оригиналов/имён/размера/сборки показываются явно. Внутренние пути и секреты в ответы/логи не входят.
- Content: GET `/api/v1/institution-digital-archives/content/{archive_ticket}`; HMAC включает контекст `institution-digital`, archiveId и actorId, срок не больше 2 минут и срока ZIP. Повторная проверка Access не зависит от наличия Bearer в ссылке. URI с ticket исключается из access log.
- `PurchasedDigitalLineOutputDto`: orderId/orderNumber/lineId/groupId, shootId/childId, childCode, kind и nullable photoId. `forInstitution` возвращает максимум 50000 строк или явную ошибку; время отсечения фильтрует подтверждение оплаты, покупательские сроки игнорируются. Комплекты раскрываются пакетами детей одной съёмки; дополнительные запросы на каждую строку/ребёнка не выполняются.
- Domain Files: `DigitalArchive`, `DigitalArchiveFile`, `DigitalArchivePolicy`, `DigitalArchiveLayout`; `DigitalArchiveRepositoryInterface` хранит/возвращает эти типы, не HTTP DTO. `DigitalArchiveFile` сохраняет group/photo, исходное имя, путь ZIP, nullable метаданные оригинала и типизированный список оснований order/line/kind/childCode.
- Application Files: `DigitalArchiveAccess`, `DigitalArchiveSnapshot`, `DigitalArchiveView`, `DigitalArchiveBuild`, UseCase Create/Get/List/Download/Export/MaintainInstitutionDigitalArchive; новые DTO только данные. I/O сборки/манифеста закрывает `DigitalArchiveWriterInterface`. Публикация сообщения использует существующую фабрику Files и отдельный тип сообщения/handler в той же очереди.
- Технические границы: не более 10000 файлов, 20 ГиБ исходников и 50000 связей файл/строка в одном выпуске; превышение — `DIGITAL_ARCHIVE_TOO_LARGE`, без усечения. API списка возвращает последние 20 выпусков с явно обозначенной границей UI. Источник Commerce также ограничен 50000 купленных строк учреждения.
- Lifecycle: `pending/ready/failed/empty/expired`; attempts позволяет различить очередь/попытку сборки. Максимум 3 попытки, аренда 30 минут, повтор через минуту; request/build/purge защищены scoped MySQL named lock, публикация — CAS по случайному owner. Пути всех попыток сохраняются до уборки, устаревший owner не публикует результат.
- Отзыв доступа — только 401/403/404 при проверке прав; 5xx источника повторяются как технический сбой, без ложного сообщения об отзыве. Повторная уборка перечитывает состояние под тем же lock и пропускает уже убранные failed-попытки.
- Список последних выпусков читает только метаданные и JSON_LENGTH состава; dispatch — только ID/attempts, purge — список ID с последовательным чтением одного снимка. Большие JSON нескольких выпусков одновременно не декодируются.
- Media предоставляет отдельный `BoundedChildPhotosInterface::ready(int $shootId, array $childIds, int $limit): array`, не более 50001 назначений. Files запрашивает остаток лимита связей + 1 и явно отклоняет превышение; прежний ChildPhotosInterface сохраняет лимит и поведение покупателей. GalleryPhotoRepository::children получает optional limit=5001, ChildPhotos реализует оба контракта с optional третьим параметром; прежние вызовы совместимы. Причина: обнаруженный прежний SQL LIMIT 5001 без признака усечения нельзя использовать как полный состав нового ZIP.
- Коллизии путей учитывают также совпадение basename отдельного файла с каталогом другого фото; необходимые файлы детерминированно перемещаются в каталог своего photoId без изменения basename.
- Новая таблица `mf_institution_digital_archive` и миграция `Version20261117180001`; actor/key уникальны, статусы/индексы/поля снимка и путей попыток. Уборка обслуживается действующим `app:files:purge`, восстановление — `app:files:dispatch-pending`, без новых cron/service/env. JSON-метаданные после срока сохраняются; ZIP удаляется через существующий ProtectedStorage.
- Команды dispatch/purge суммируют обе части отчёта и возвращают ненулевой exit status, если какая-либо часть batch завершилась ошибкой; unit проверяет успешный и ошибочный исход через Console CommandTester.
- Историческая E2E-фикстура сохраняет собственные реальные child/photo/assignment связи каждой строки заказа, включая coveredByGift. Перед завершением setup проверяется согласованность этих связей; существующий D3 verifier остаётся без ослабления.
- Ошибки состояния: `ORIGINAL_MISSING`, `COMPOSITION_CHANGED`, `INVALID_ORIGINAL_FILENAME`, `DIGITAL_ARCHIVE_TOO_LARGE`, `ARCHIVE_FAILED`. Ошибки запросов: `DIGITAL_ARCHIVE_IN_PROGRESS`/`IDEMPOTENCY_CONFLICT`/`OPERATION_IN_PROGRESS` (409), `IDEMPOTENCY_KEY_REQUIRED` (422), `INSTITUTION_NOT_FOUND`/`ARCHIVE_NOT_FOUND` (404). Сбой источника не превращается в пустую выгрузку.

### Данные и отказ

Files владеет своей новой таблицей. Записываются UUID/учреждение/инициатор, момент снимка UTC, неизменяемый состав и основания покупки, исходные имена/пути ZIP, статус/попытки/аренда, приватный путь/размер/готовность/срок. Архивные метаданные не удаляются при истечении ZIP. Миграция повторяема; down не удаляет пользовательские данные незаметно.

Поставка: foundation-миграция до обновления backend/Files consumer; frontend и backend поставляются вместе. Files явно подключает существующих поставщиков Organization/Access; новые зависимости уже в main. При откате маршруты/действие возвращаются прежней версией, таблица со снимками сохраняется. Новый consumer и dispatch/purge должны обновляться вместе, чтобы не читать ещё не созданную таблицу.

Повтор с тем же actor/key возвращает прежнюю операцию; конфликт учреждения отклоняется. Сбой после записи до очереди восстанавливается действующим dispatch. Публикация готовности только после полной проверки состава и атомарного ZIP; параллельный или просроченный владелец не публикует чужой результат. Байты отдаёт internal nginx, PHP/JS не буферизуют ZIP. Удаление по сроку не удаляет оригиналы Media и чужие архивы.
