# Issues #105 и #106 — группа со страницы учреждения и удаление кадров

## Цель

Убрать два UX-тупика, найденных пользователем при ручной проверке 2026-09-25:

1. **#105.** На странице учреждения организатор видит группы, но не может создать или изменить группу —
   только подсказка «откройте её съёмку».
2. **#106.** На странице кадров группы нельзя удалить лишние фотографии: в API нет удаления, во frontend нет действия.

## Контекст

- Группа принадлежит съёмке: `POST /api/v1/shoots/{shoot_id}/groups`, `PATCH /api/v1/groups/{group_id}`.
  Экран учреждения уже получает группы со `shootId`, но редактор создан только для съёмок.
- Кадры — HL `b_hlbd_mf_photo`; назначения `mf_photo_assignment` и обложка `mf_media_group_cover` ссылаются на кадр
  через FK `RESTRICT`, дубликаты — через `UF_EXISTING_PHOTO_ID`. Оригинал хранит `LocalPrivatePhotoStorage`
  (`delete()` есть), превью пишет `GdPreviewRenderer` (удаления нет).
- Заказы и корзина появляются только после отправки ссылки (`UF_SENT_AT`), а после неё группа не редактируется
  (`groupEditable = false`). Пока группа в «Подготовке», кадр не может быть в заказе.
- Право `media.manage` есть только у организатора.

## Scope

**#105 — frontend `structure`**
- В блоке «Группы учреждения»: «Новая группа» (шапка и пустое состояние) и «Редактировать» у каждой группы для
  организатора с `organization.manage`. Подсказку «откройте её съёмку» убрать.
- В диалоге группы на экране учреждения — поле «Съёмка»: одна съёмка выбрана заранее; несколько — по умолчанию
  самая поздняя по дате, выбор обязателен; при редактировании поле только для чтения.
- Без съёмок — кнопки «Новая группа» нет, пояснение «Сначала добавьте съёмку — группа создаётся внутри неё.».
- `useStructureEditor.open()` принимает явный родитель для группы; ключ черновика строится от выбранной съёмки.

**#106 — backend `morefoto.media` + frontend `photos`**
- `POST /api/v1/groups/{group_id}/photo-deletions`, тело `{ revision: int, photoIds: uuid[1..100] }` (как у обложки, без `shootId`),
  заголовок `Idempotency-Key`, ответ 200 `{ deleted: int, revision: int }`.
- `DeleteGroupPhotosUseCase` по шаблону `SetGroupCoverUseCase`: транзакция → группа и scope, `assertCan(media.manage)` →
  `groupEditable` → `lockRevision` и повторная проверка → идемпотентность → сверка ревизии.
- Отказы: неизвестный, чужой или уже удалённый кадр — 409 `PHOTO_NOT_DELETABLE`; кадр в обработке — 409 `PHOTO_PROCESSING`.
- В транзакции: дубликаты-ссылки → назначения → обложка (следующий кандидат или снятие) → строки кадров →
  `advanceRevision`. Коды оставшихся кадров не перенумеровываются.
- Файлы (оригинал, если `originalPathInUse` = false, и два webp-превью) удаляются после коммита, как в
  `DeleteStaffAvatarUseCase`. `PreviewRendererInterface` получает `remove()`.
- Чистый контроллер: `*RequestDto` собирает infrastructure mapper, controller передаёт DTO в UseCase.
- Frontend: «Удалить выбранные (n)» в панели выбора и «Удалить кадр» на карточке; диалог подтверждения;
  после успеха — обновление списка, счётчиков и ревизии, сообщение «Удалено кадров: n». Mock-режим поддерживает
  удаление.

## Вне scope

- Удаление учреждений, съёмок и групп — #92.
- Удаление кадров после отправки ссылки и из заказов.
- Корзина/восстановление удалённых кадров, мягкое удаление.
- Перенос группы между съёмками.
- Перенумерация кодов кадров после удаления.

## Решения

| ID | Решение | Почему |
|---|---|---|
| DEC-1 | Жёсткое удаление строк и файлов | Мягкого удаления в схеме нет; оно потребовало бы нового статуса, правки CHECK `ck_mf_photo_state` и фильтра во всех выборках. Заказов на кадры в «Подготовке» нет |
| DEC-2 | Удалять можно только в «Подготовке» | Совпадает с остальными мутациями медиа; исключает кадры из корзин и заказов |
| DEC-3 | Кадры `processing` не удаляются (409 `PHOTO_PROCESSING`) | Иначе рендер допишет превью-сироты после удаления строки |
| DEC-4 | Коды A001… не перенумеровываются | Коды стабильны для родителей и печати; дыры допустимы |
| DEC-5 | Ресурс `photo-deletions` через POST | Пакетная операция с телом и `Idempotency-Key`, как `photo-assignments`; DELETE с телом нежелателен |
| DEC-6 | Съёмка по умолчанию — самая поздняя по дате | Обычно организатор готовит ближайшую съёмку |

Решения DEC-1…DEC-6 приняты: пользователь 2026-09-26 взял PR #107 в реализацию без правок.

## Зависимости и риски

- Зависимостей от незамерженных веток нет; base `origin/main` `caa37b6`. Миграций нет.
- Риск: заявка сотрудника (`mf_staff_request_row.PHOTO_IDS_JSON`) со снимком удалённого кадра → перенос вернёт
  `SET_CHANGED`. Это ожидаемое поведение, проверяется тестом.
- Риск: подготовленная ссылка теряет подпись материалов (`GroupMaterials`) → потребуется подтвердить заново.
- Риск: сбой удаления файлов после коммита оставляет сироты на диске — логируется, ответ остаётся успешным.
- Пересечение с #92 и открытым PR #104 (`UiDataTable`) минимально: затрагиваются `InstitutionCollection.vue` и
  `photos/*`, не таблицы.

## Критерии приёмки

- Организатор создаёт и редактирует группу со страницы учреждения, выбрав съёмку; группа видна и в учреждении,
  и в съёмке. Без съёмок — понятный путь к созданию съёмки. Куратор кнопок не видит.
- Организатор удаляет один и несколько кадров группы в «Подготовке»; кадры исчезают из списка, у детей и в
  статистике; файлы удалены.
- Удаление обложки назначает следующую или снимает её; FK-ошибок нет.
- Отказы: отправленная группа 409 `GROUP_LOCKED`, обработка 409 `PHOTO_PROCESSING`, старая ревизия 409
  `REVISION_CONFLICT`, куратор 403, чужой или удалённый кадр 409 `PHOTO_NOT_DELETABLE`. Повтор с тем же ключом идемпотентен.
