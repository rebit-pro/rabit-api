# E9 — продажи группы в кабинете воспитателя

## Цель

Воспитатель входит в свой кабинет и в «Обзоре» по каждой своей группе видит, сколько продано:

- печатных фото — с разбивкой по форматам;
- цифровых файлов;
- оплаченных заказов;
- купивших семей;
- сколько заплатили родители.

## Контекст

- Запрос владельца 15.10.2026. Волна добавлена в граф PR #207 (OPS-waves-e9-j5). Ветка `codex/e9-teacher-sales` от main e728d8c.
- Зависимости уже в main: B2 (назначения воспитателя), E5 (снимок заказа), G1 (подтверждённая оплата), U6 («Обзор» по ролям).
- «Обзор» воспитателя (`frontend/src/modules/morefoto/overview/LiveOverview.vue`) показывает карточки групп из HND-01. Финансовые плитки организатора остаются «недоступно» до N1.
- Данные — `mf_order` / `mf_order_line` (неизменяемый снимок). Деньги хранятся в копейках, индекс `ix_mf_order_group (GROUP_PUBLIC_ID, …)`.

## Решения

Владелец принял рекомендации 16.10.2026.

| ID | Решение |
| --- | --- |
| E9-DEC-01 | «Цифровые файлы» — только оплаченные digital-кадры (строка с кадром, не покрыта подарком). Бесплатные копии печати J4 и подарок GIFTS продажей не считаются. |
| E9-DEC-02 | «Купившие семьи» — уникальные дети группы, у которых есть хотя бы один оплаченный заказ. |
| E9-DEC-03 | UI — только «Обзор» воспитателя. Organizer и curator получают ту же сводку через API в своей области. |
| E9-DEC-04 | Уточнение DEC-01 при реализации. Купленный комплект «все фото ребёнка» (bundle) — тоже оплаченная цифровая покупка, но число кадров в снимке не хранится. Поэтому он считается отдельно: «и N комплектов „все фото“». Bundle, покрытый подарком, не считается. |
| E9-DEC-05 | Уточнение при реализации. Поздняя оплата (`LATE_PAYMENT=1`, ждёт решения SET-07) не входит, как в L1/J2. Возвратов до I2 нет. |

## Scope

1. **Backend, morefoto.commerce.** `GET /api/v1/groups/{group_id}/sales-summary` (COM-14):
   - RequestDto → UseCase → два агрегирующих SQL-чтения: итоги и печать по продукции;
   - область через Access (`StaffRequestAccessInterface`), группа через Organization (`GroupDirectoryInterface::find`);
   - DI, маршрут.
2. **Права:**
   - organizer — любая группа;
   - curator — группы своих учреждений;
   - teacher — свои назначенные группы;
   - остальные роли — 403 `FORBIDDEN`;
   - чужая или несуществующая группа — 404 `GROUP_NOT_FOUND`.
3. **Ответ без персональных данных:**
   - `groupId`, `paidOrders`, `families`, `prints`, `digitalFiles`, `bundles`, `paidTotal` (копейки);
   - `products[] {id, name, prints}` по убыванию печати.
4. **Frontend.** Блок «Продажи» (`GroupSales.vue`) в карточке группы «Обзора» воспитателя:
   - сумма оплат и четыре плитки;
   - печать по форматам;
   - состояния: загрузка, ошибка с повтором, «продаж пока нет».
5. **Проверки:**
   - PHPUnit: UseCase/права/маппинг, архитектура controller/DTO/phpDoc/отсутствие ПДн;
   - frontend unit для правил отображения;
   - live E2E: роли, сверка с COM-12, неоплаченный заказ не меняет сводку, visual desktop/mobile;
   - полный гейт.
6. **Документы:** граф (E9 inProgress → review), README волны, план и журнал.

### Вне scope

- UI для organizer/curator и финансовый отчёт N1 (комиссии, себестоимость, возвраты, вознаграждение).
- Кеш: чтение лёгкое и по индексу группы.
- Ссылка без входа: владелец выбрал кабинет.

## Риски и ограничения

- Воспитатель без доступа в кабинет сводку не увидит: нужны приглашение B2 и рабочая почта (#161).
- Переименование продукции между заказами: печать группируется по `PRODUCT_PUBLIC_ID`, название берётся из снимка (MAX), так что дублей формата нет.
- E2E назначает `another-teacher` на печатную группу J4 в последней спеке группы b — другие сценарии это не затрагивает.

## Критерии приёмки

- Воспитатель видит блок «Продажи» только своих групп. Числа совпадают с независимым расчётом по COM-12 той же группы: только paid, без поздней оплаты.
- Неоплаченный заказ не меняет сводку. Чужая группа — 404, роль head — 403, без входа — 401.
- В ответе нет email, имени, телефона, номера и ключа заказа.
- Desktop/mobile без горизонтальной прокрутки. Пустая группа показывает «Продаж пока нет».
