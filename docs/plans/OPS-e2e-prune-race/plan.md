# OPS — `e2e-prune` переживает исчезновение ресурса между list и inspect (#88)

> Техническая задача вне графа волн: ветка `codex/ops-e2e-prune-race` от `main` `94502a1`, один PR в `main`.
> Issue — [#88](https://github.com/rebit-pro/rabit-api/issues/88), находка ревью PR #87. Прецедент — [OPS-e2e-gate-findings](../OPS-e2e-gate-findings/plan.md), где появился `prune`.
> Продуктовый код, API и миграции не меняются. Меняются `tools/run-browser-e2e.py`, его unit-тесты и строка в `docs/waves/a8/README.md`.

## Цель и контекст

`inventory()` сначала получает ID ресурсов с меткой `rabit.browser_e2e`, затем одним вызовом делает `docker <kind> inspect`.
Одноразовые контейнеры `docker run --rm` параллельного прогона исчезают между этими вызовами. Docker печатает данные
оставшихся ресурсов, но завершается с кодом 1, `command()` бросает исключение, и `make e2e-prune` не выдаёт отчёт.

Цель — отчёт и очистка завершаются при такой гонке, настоящие ошибки Docker по-прежнему падают, а неполная проверка
запуска не даёт права его удалить.

## Scope

1. Листинг получает вместе с ID метку запуска (`--format '{{.ID}}\t{{.Label "rabit.browser_e2e"}}'`, для томов `{{.Name}}`),
   чтобы исчезнувший ресурс можно было отнести к запуску.
2. `inspect` вызывается одним пакетом, как раньше. При ненулевом коде:
   - каждая строка stderr обязана быть сообщением Docker «ресурс не найден» для одного из перечисленных ID
     (container: `No such container: <id>`, network: `network <id> not found`, volume: `get <id>: no such volume`);
   - число полученных записей + число исчезнувших обязано совпасть с числом перечисленных ID;
   - иначе — `RuntimeError`, как раньше (демон недоступен, неизвестное сообщение, нарушение формата).
3. Исчезнувший ресурс попадает в свой запуск как запись `gone`; `verdict()` оставляет такой запуск (`keep`) с причиной
   «disappeared during the check» — решение по нему принимает следующий прогон `prune`.
4. То же для сетей и томов: схема list → inspect у них общая.
5. Unit-тесты с подменой `subprocess.run`.

## Вне scope

- Повторный снимок целиком: под постоянной нагрузкой параллельных прогонов он может не сойтись; пропуск с `keep` проще и безопаснее.
- `exists()`/`owned()` в `stop()`: работают по ресурсам своего запуска по имени, гонки с чужими `--rm` там нет.
- Удаление ресурсов, `make test-e2e`, `make e2e-up`, `E2E_PRUNE_APPLY=1` — на машине работают стенды других сессий.

## Решения и риски

- Разбор сообщений Docker зависит от версии CLI/демона (проверено на 29.4.1). Если формат изменится, `prune` упадёт
  с прежней ошибкой — то есть поведение до исправления, без маскировки и без удаления.
- Запуск с исчезнувшим ресурсом не удаляется в этом проходе, даже если остальное брошено: цена — повторный прогон `prune`.
- Сообщение Docker содержит тот ID, который передан в `inspect`, поэтому сопоставление идёт по точному ID из листинга.

## Критерии приёмки

- Исчезновение контейнера, сети или тома между листингом и `inspect` не роняет `prune`; запуск этого ресурса — `keep`.
- Любая другая ошибка `inspect` (другое сообщение, недоступный демон, несовпадение числа записей) — `RuntimeError`.
- Dry-run не вызывает удаление; работающий стенд остаётся `keep`.
