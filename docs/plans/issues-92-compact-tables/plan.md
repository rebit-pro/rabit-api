# Issue #92 (срез 1) — компактные таблицы с CRUD: каталог, учреждение, ссылки и сроки

## Цель и контекст

Замечание пользователя 2026-09-26 по трём экранам кабинета организатора (скриншоты в запросе):

- **Каталог и цены** — крупные карточки по одной позиции, 4 позиции на экран, нет поиска, сортировки, выбора и удаления.

«Заказы» и «Платежи» — следующий срез, в этот не входят.

### Что на макетах

**Каталог.** Таблица с колонками «Продукция» (иконка типа + название, под ним формат · единица — описание в одну
строку с многоточием), «Тип», «Цена», «Сотрудникам», «Статус», «Действия» (Изменить, удалить). Фильтры: название,
тип, статус. Иконка по существующему полю `kind`: печать — принтер, электронный — облако, комплект — коробка
(отдельных kind для календаря/магнита нет, новое поле не вводим). Мультивыбор → «Снять с продажи», «Вернуть в
продажу», «Удалить». На 10 позиций — один экран вместо трёх.

**Учреждение.** Шапка: «Изменить учреждение», «Обновить», «Удалить учреждение». Реквизиты — одной строкой (адрес,
куратор, руководитель). Плитки: съёмки, группы готовятся (из N), приём открыт, финансы (недоступно). Два виджета-таблицы:
- «Съёмки N» + «Новая съёмка»: название (ссылка на съёмку), дата, число групп; действия — кадры, условия, изменить, удалить;
- «Группы N» + фильтр по съёмке + «Новая группа»: группа (ссылка на кадры группы, пометка «сотрудники»), съёмка,
  приём (статус), приём до; действия — ссылка и сроки, изменить, удалить.
Мультивыбор в каждом виджете → «Удалить». Пагинация в виджете скрыта, пока всё помещается на одной странице.

**Ссылки и сроки.** Плитки-фильтры по состоянию (требует проверки / готова к передаче / приём открыт / приём завершён).
Фильтры: поиск по группе и съёмке, учреждение, состояние. Таблица: группа (учреждение · съёмка), состояние (+ текущий
шаг подготовки «шаг 2 из 5: распределить кадры по детям»), передана, приём до (+ «осталось N дней»), доставка.
Действия по состоянию: для открытых — копировать ссылку, открыть галерею, меню (исправить дату, история, к фотографиям);
для неготовых — «Проверить»/«Передать» + меню. Мультивыбор → «Скопировать ссылки» (строки «Группа — URL»).
Удаления и добавления здесь нет: ссылка — часть группы, создаётся и удаляется вместе с ней.

**Mobile.** Все три таблицы используют существующую карточную раскладку `UiDataTable` (как «Сотрудники»): сортировка
выпадающим списком, «выбрать все», карточка на строку. Плитки — по две в ряд.

## Решения на согласование

| ID | Вопрос | Рекомендация | Альтернатива |
|---|---|---|---|
| DEC-01 | Удаление группы/съёмки/учреждения, по которым уже есть заказы | Отказ `409 STRUCTURE_HAS_ORDERS` и перечнем; такие объекты остаются для истории заказов и оплат | Архив с запретом новых действий (#92, п. 2) — отдельный срез: нужен признак архива во всех чтениях |
| DEC-02 | Группа без заказов, но ссылка уже передана родителям | Удалять с предупреждением в диалоге: ссылка перестанет открываться | Запрет, пока приём открыт |
| DEC-03 | Продукция, которую уже покупали (`mf_order_line`) | Отказ `409 PRODUCT_IN_ORDERS`, в диалоге подсказка «снимите с продажи» | Мягкое удаление (скрыть из каталога) |
| DEC-04 | Продукция, выбранная в условиях групп (`mf_group_product_condition`, FK RESTRICT) | Удалять строки условий в той же транзакции; ревизия условий групп растёт | Отказ, пока продукция в условиях |
| DEC-05 | Удаление учреждения | Входит в срез: каскад тот же, что у съёмок; кнопка на странице учреждения и в списке учреждений | Отложить |
| DEC-06 | Сортировка и фильтр каталога и виджетов учреждения | На клиенте: каталог и структура одного учреждения — десятки строк, загружаем до 100 за запрос | Серверные `sort`/`direction` (нужны при > 100 строк) |
| DEC-07 | Массовые операции | Последовательные одиночные запросы, итог «Удалено N из M» с причинами (как #91) | Bulk-эндпоинты |

## Scope

### Backend

Факты (разбор схемы 2026-09-26): все FK на продукцию/учреждение/съёмку/группу — `ON DELETE RESTRICT`, каскадов нет;
контракта «есть ли у группы заказы» нет (есть только `ChildOrdersInterface` по детям); событий удаления нет.

1. **Контракты** (`rebit.share/lib/Contracts/`, уточнено 2026-09-26 после разбора схемы). Общий DTO
   `Organization\Dto\StructureRemovalDto` (внутренние ID групп, съёмок, учреждений) и по интерфейсу на
   модуль-поставщика — так же, как устроены остальные межмодульные контракты (реализация и DI у поставщика):
   - `Commerce\StructureSalesRemovalInterface::remove()` — отказ `409 STRUCTURE_HAS_ORDERS`, если по группам,
     съёмкам или учреждению есть строки `mf_order`; иначе удаляет условия продажи групп, корзины и незавершённые
     оформления (`mf_cart_quote`, `mf_order_checkout` без заказа — они держат FK на ключ галереи);
   - `Handoff\StructureHandoffRemovalInterface::remove()` — ссылки групп и их история, строки и заявки списков
     сотрудников (строки, ссылающиеся на детей/группы удаляемой структуры; перенос в удаляемую группу забывается);
   - `Support\StructureSupportRemovalInterface::remove()` — вопросы родителей по удаляемым группам вместе с
     сообщениями (CHECK запрещает вопрос родителя без группы, поэтому обнулить нельзя);
   - `Media\StructureMediaRemovalInterface::remove()` → `RemovedMediaFilesDto` и `removeFiles()` после commit —
     кадры, дубли, назначения, обложки, дети, ключи галереи, состояние съёмки; кадры в обработке →
     `409 PHOTO_PROCESSING`; у кадров других групп, пришедших из удаляемой, «исходная группа» становится текущей;
   - назначения снимает сама организация через существующие `GroupAccessInterface::replace()` и
     `InstitutionAccessInterface::replace()`: история назначений и отзыв сессий остаются в `morefoto.access`.
   Порядок вызова: commerce → handoff → support → media → access → строки организации.
2. Единый код отказа при заказах — `STRUCTURE_HAS_ORDERS` (вместо трёх кодов в первой версии плана): текст
   подставляет фронтенд по удаляемому объекту.
3. **UseCase** в `morefoto.organization`: `DeleteGroupUseCase`, `DeleteShootUseCase`, `DeleteInstitutionUseCase`
   — право `organization.manage`, блокировка родителя, проверка заказов (DEC-01), участники, удаление строки,
   запись в `b_hlbd_mf_organization_change`, рост ревизии. Маршруты: `DELETE /api/v1/groups/{group_id}`,
   `DELETE /api/v1/shoots/{shoot_id}`, `DELETE /api/v1/institutions/{institution_id}` → `204`; 404 — «уже удалено».
4. **Каталог** (`morefoto.commerce`): `DeleteProductUseCase` + `DELETE /api/v1/catalog/products/{product_id}` → `204`,
   `409 PRODUCT_IN_ORDERS`, удаление условий групп (DEC-04), рост ревизии каталога.
5. **Чтение учреждения**: у съёмок `groupCount`, у групп `shootName` (иначе виджет не покажет съёмку группы вне
   первой страницы съёмок).
6. Новые HTTP-контроллеры — по правилу чистых контроллеров (`*RequestDto`, общий базовый controller, без Bitrix).
   Миграции не нужны (схема не меняется).

### Frontend

1. `UiDataTable` (общий): `width` у колонки, `actionsWidth`, `autoPager`; по умолчанию разметка прежняя,
   «Сотрудники» и «Учреждения» не меняются.
2. Каталог: `CatalogTable` на `UiDataTable`, фильтры, выбор, удаление, «снять/вернуть в продажу» (существующий PATCH).
3. Учреждение: `InstitutionOverview` (реквизиты строкой + плитки), `StructureWidget` для съёмок и групп, удаление
   одной/нескольких записей, удаление учреждения с возвратом к списку; кнопка удаления и в `StructureScreen`
   (список учреждений).
4. Ссылки и сроки: таблица, плитки-фильтры, фильтры, действия по состоянию, история в диалоге, «Скопировать ссылки».
5. Иконки: `mdi-cloud-download-outline`, `mdi-package-variant-closed`, `mdi-pencil-outline`, `mdi-refresh`,
   `mdi-progress-clock`, `mdi-open-in-new`, `mdi-check-all`, `mdi-history`, `mdi-calendar-edit-outline`,
   `mdi-map-marker-outline` в `plugins/icons.ts`.
6. Демо-режим (`ManagementScreen`, mock API) не трогаем.

### Исключено

- Архив объектов с заказами (DEC-01, альтернатива).
- `StaffRequestsScreen`, `TransferHistory`, `UploadQueue`, `WorkTable`, `PrintRows` — остальные пункты #92.
- Страница съёмки (`OrganizationShootScreen`) — только если после одобрения пользователь попросит то же оформление.

## Зависимости и риски

- Зависимостей от незамерженных веток нет; всё на `main` `41b1146e`.
- R1. Каскад по пяти модулям в одной транзакции: порядок удаления (дети → родители) проверяется интеграционным
  тестом на стенде E2E; RESTRICT-FK сами ловят забытую таблицу.
- R2. Стирание файлов после commit может не дойти (сбой диска) — остаются «сироты» на диске, как в удалении кадров;
  фиксируем в логе, без повторной очереди.
- R3. Параллельная выгрузка кадров в удаляемую съёмку: удаление берёт ту же блокировку ревизии съёмки, что и загрузка.
- R4. Объём оценочно 3–4,5 тыс. строк (backend ~2–2,5, frontend ~1–1,3, тесты ~1) — одна волна, без деления.
