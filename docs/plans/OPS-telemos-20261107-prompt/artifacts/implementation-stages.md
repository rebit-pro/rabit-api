# Этапы доработки MoreFoto по встрече 7 ноября 2026

Основание: одобренный пользователем `implementation-prompt.md` в этой же папке. Этот документ определяет порядок исполнения и границы коммитов. Полные требования и T01-T16 сохраняют силу; краткое описание этапа их не заменяет. Фактическое состояние первого этапа записано в `../OPS-order-photo-delivery/progress.md`.

## Порядок работы и коммитов

Один этап - один законченный коммит: продуктовый результат, нужные миграции, тесты, обновление затронутой инструкции и собственные `plan.md` / `progress.md`. Не выделять DTO, миграцию без сценария или макет без работающего API в самостоятельный этап. Коммит делается после проверки собственного diff; результаты непроведённых проверок остаются PENDING/BLOCKED.

По AGENTS.md каждый самостоятельный OPS-этап ведётся в своей ветке `codex/ops-...` и отдельном PR в `main`. Зависимый этап начинается после merge поставщика в `main`. «Один этап - один коммит» не означает восемь несвязанных коммитов в старой ветке #232 и один общий PR. Merge и deployment выполняются отдельно; в этом документе нет разрешения выполнять их автоматически.

Рекомендуемый последовательный порядок: **1 -> 2 -> 3 -> 4 -> 5 -> 6 -> 7 -> 8**. Таблица показывает технические зависимости, чтобы независимый этап можно было выполнить раньше при задержке соседнего.

**Проверки:** backend Commerce/Files unit и затронутые integration/architecture; frontend `test:commerce`, проверки frontend при его изменении; T01-T04 через реальный сценарий отдельным исполнителем E2E. ## Этап 4. Формат печатного архива группы

**Ветка:** `codex/ops-print-archive-layout`.
**План:** `docs/plans/OPS-print-archive-layout/`.
**Коммит:** `feat(production): preserve filenames and group print quantities`.
**Вход:** этап 2 в main; существующие L1 версии и снимки состава.

- [ ] Получать исходные имена через контракт Media. В новых версиях сохранять имя файла без замены кодом кадра и без суффиксов `_x2` / `_x3`.
- [ ] Для одного отпечатка класть файл в папку продукции, для двух - один раз в `2шт`, для трёх - один раз в `3шт`, далее `Nшт`. Не создавать `1шт` и копию того же задания в корне.
- [ ] Считать `quantity * printCount`, суммировать повторные оплаченные строки одного фото и одной продукции внутри группы; не группировать по одному имени. Сохранить связь манифеста со всеми строками заказов.
- [ ] Зафиксировать детерминированное правило конфликтов путей с сохранением исходного basename. Разные фото с одинаковым именем и разные продукции одного формата не перезаписывать и не объединять. Небезопасные имена обрабатывать явно, не выдавать тихо переименованный файл за неизменённый оригинал.
- [ ] Обеспечить совпадение ZIP и CSV-манифеста. Сохранить версии, дополнения, приватный доступ, ошибки отсутствующих оригиналов и повторяемую сборку.
- [ ] Применить формат к новым версиям, не переписывать уже выданные исторические версии; обновить инструкцию подготовки печати.

Точки входа: `ArchiveLayout`, `VersionSnapshot`, `ArchiveBuilder`, `CsvManifestWriter`, контракты Media/Commerce. При необходимости хранения новых полей использовать `migrations.foundation` в этом же законченном сценарии.

**Готово, когда:** существующее действие архива группы выдаёт пригодный для лаборатории ZIP нового формата. Это самостоятельная проверяемая функция, а не заготовка DTO для будущей кнопки учреждения.

**Проверки:** T10-T13 в части группы, T15; unit количества/путей, интеграция сборки ZIP, реальные имена/байты/дерево, повтор сборки и старые версии. Полная сверка с новой ведомостью по T10 состоится на этапе 6; не отмечать весь T10 окончательно пройденным раньше.
