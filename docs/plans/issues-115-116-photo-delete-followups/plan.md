# Issues #115 и #116 — удаление кадров: потерянный ответ и проверки на реальной БД

## Цель

Закрыть два неблокирующих замечания ревью PR #107 (удаление кадров группы, #106):

1. **#115 (frontend).** После успешного коммита удаления ответ может потеряться. Сейчас каждое подтверждение
   создаёт новый `Idempotency-Key`, поэтому повтор получает `REVISION_CONFLICT`, затем `PHOTO_NOT_DELETABLE`;
   сохранённый успех восстановить нельзя.
2. **#116 (backend, покрытие).** T08 (удаление canonical-кадра с duplicate-ссылками) и T10 (`PHOTO_PROCESSING`) из
   плана #105/#106 остались PENDING: unit-тест подменяет `MediaMutationRepository`, реальный SQL не проверен.

## Контекст

- `POST /api/v1/groups/{group_id}/photo-deletions` `{ revision, photoIds }` + `Idempotency-Key`.
  `DeleteGroupPhotosUseCase` проверяет идемпотентность **до** сверки ревизии: тот же ключ с тем же payload
  (ревизия + ID в том же порядке) возвращает сохранённый `{ deleted, revision }`, другой payload — `IDEMPOTENCY_CONFLICT`.
- Во frontend подход «неизвестного исхода» уже есть в support (`mayHaveBeenStored`, `firstQuestion.ts`,
  `useQuestionThread.ts`): попытка с ключом хранится, пока ответ не определён (сеть или 5xx), и повторяется как есть.
- Реальный MySQL есть только на E2E-стенде. Верификаторы `api/tools/e2e/verify-*.php` запускаются после группы
  браузерных спеков (`tools/run-browser-e2e.py`, `VERIFIERS`); `zz-media` — группа `a`.
- `ck_mf_photo_state` допускает `processing` с `UF_JOB_STATE='published'` и уже готовыми превью; воркер берёт из БД
  только `pending`, поэтому такой кадр остаётся «в обработке», пока его не вернут.

## Scope

**#115 — frontend `photos`**
- Чистый модуль `photos/deletion.ts`: хранит попытку `{ groupId, revision, photoIds, key }` до определённого ответа;
  повтор того же набора отправляет тот же payload и ключ; определённый ответ (успех, 4xx) попытку завершает.
- Правило неизвестного исхода и разбор ошибки переносятся из support в общий `src/api/outcome.ts`
  (`RequestProblem`, `requestProblem`, `mayHaveBeenStored`); support использует его без изменения поведения.
- `photosApi.remove` принимает ключ; `usePhotoWorkspace.removePhotos` работает через попытку; при неизвестном
  исходе — сообщение «Не удалось подтвердить удаление…», кнопка диалога «Повторить удаление».
- Отмена диалога после неизвестного исхода забывает попытку и обновляет список (он покажет фактическое состояние).
- Определённый 409 (`REVISION_CONFLICT` и др.) обрабатывается как раньше.
- Unit (node) тест: «сервер выполнил, ответ потерян» → тот же ключ и payload → сохранённый успех, цикла 409 нет;
  определённый 409; отмена; 5xx; другой набор.
- Live E2E в `zz-media.spec.ts`: ответ удаления обрывается после выполнения на сервере (`route.fetch()` +
  `route.abort()`), повтор из диалога уходит с тем же ключом и телом и закрывает диалог.

**#116 — проверки на реальной БД**
- Тот же live-сценарий удаляет canonical-кадр, на который ссылается duplicate-запись (повторная загрузка того же
  файла): duplicate исчезает, оставшиеся кадры, назначения и обложка корректны (HTTP → реальный SQL).
- Верификатор `api/tools/e2e/verify-photo-deletion.php` (группа спека `zz-media`): по группе сценария проверяет в
  MySQL T08 (нет строк/назначений удалённого кадра и его duplicate, оставшиеся строки целы) и T10: переводит один
  готовый кадр в `processing/published`, вызывает реальный `DeleteGroupPhotosUseCase` для набора ready + processing,
  ждёт `PHOTO_PROCESSING` и сверяет, что строки, назначения, обложка, ревизия, запись идемпотентности и файлы не
  изменились; затем возвращает кадр в `ready`.
- Дешёвая проверка без стенда: unit-тест SQL-порядка `MediaMutationRepository` на шпионе соединения
  (duplicate-ссылки и назначения удаляются до строк кадров, обложка переносится до удаления; `processing` → 409
  до любых изменений). Реальный SQL он не заменяет.

## Вне scope

- Сохранение попытки удаления между перезагрузками страницы (localStorage): после перезагрузки список и так
  показывает фактическое состояние.
- Унификация остальных копий правила неизвестного исхода (`orders/live`, `handoff`) — отдельный follow-up.
- Изменения backend-логики удаления.

## Решения

| ID | Решение | Почему |
|---|---|---|
| DEC-1 | Попытка хранится в памяти composable, не в storage | Диалог модален; после перезагрузки список показывает правду, повтор не нужен |
| DEC-2 | Неизвестный исход = сеть или `status >= 500` (`mayHaveBeenStored`) | То же правило, что в support и orders; 4xx — определённый отказ |
| DEC-3 | Повтор набора использует сохранённую ревизию и порядок ID | Сервер сравнивает hash payload; новая ревизия дала бы новый payload |
| DEC-4 | Отмена после неизвестного исхода — забыть попытку и обновить список | Пользователь видит фактическое состояние; повтор с новым ключом безопасен (409) |
| DEC-5 | T10 проверяет верификатор через реальный UseCase, а не HTTP | Браузер не может удержать кадр в `processing`: воркер стенда обрабатывает его сразу |
| DEC-6 | `removeFiles` удаляет оригинал и превью независимо, каждый сбой — отдельный warning (`files`: `original` или `previews`) | Gate `rabit-e2e-939944822035`: превью, записанные воркером от root, не удаляются FPM (`www-data`), и исключение превью оставляло на диске приватный оригинал. Сами превью — #141 |

## Критерии приёмки

- Потерянный ответ удаления восстанавливается повтором: тот же ключ и payload, получен сохранённый успех,
  список обновлён, диалог закрыт; 409-цикла нет.
- Определённый 409 обрабатывается как раньше; диалог можно отменить.
- На реальной БД: canonical с duplicate удаляется без FK-ошибок, duplicate исчезает, остальное не тронуто;
  набор ready + processing получает `PHOTO_PROCESSING` без изменений строк, назначений, обложки, ревизии и файлов.
