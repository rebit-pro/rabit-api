## Факты (разбор 2026-09-27)

- **Списки сотрудников** (`morefoto.handoff`): `GET/POST /staff-requests`, `GET/PUT /staff-requests/{id}`, уточнение,
  предпросмотр и перенос. Удаления нет. Статусы `submitted | clarification | transferred`. Таблицы `mf_staff_request`,
  `_row`, `_history` (FK RESTRICT на заявку), `_idempotency` (без FK). Список: `page`/`pageSize ≤ 100`, фильтры
  `institutionId`, `shootId`, `status`; порядок жёсткий `UPDATED_AT DESC`; `meta.summary.byStatus` по всей области.
- **Заказы** (`morefoto.commerce`): `GET /orders`, `GET /orders/{id}`; изменений персоналом нет. Фильтры `q`, область,
  `paymentStatus`, `productionStatus`, даты, `late`; порядок `CREATED_AT DESC`. Оплата: `unpaid | pending | declined | paid`.
  На `mf_order` держат FK RESTRICT: `mf_order_line`, `mf_order_access_key`, `mf_order_checkout`,
  `mf_payment_attempt` (→ `mf_payment_fact`), `mf_file_download`; без FK — `mf_file_download_request`.
- **Платежи** (`morefoto.payment`): `GET /payments`, `GET /payments/{id}`; действий нет (сверка — только CLI).
  Попытки: `unknown | pending | succeeded | canceled`; порядок `CREATED_AT DESC`, `summary` нет.
- Сверка и старт оплаты берут `orders->lock()` строки заказа — удаление под той же блокировкой не гонится с оплатой.
- `UiDataTable` управляемый (`sort`/`page` наружу) — годится для серверных страниц без доработки.

| DEC-03 | Выбранные строки заказов и платежей выгружаются в CSV на клиенте; backend для выгрузки не меняется. |

## Scope

### Backend

1. **Серверная сортировка** (DEC-05) — `sort`/`direction` в `*ListRequestDto`, белый список в input-mapper,
   `422 INVALID_SORT` на неизвестное поле; стабильный хвост `ID DESC`:
   - заказы: `createdAt` (по умолчанию), `number`, `total`, `buyerName`, `institutionName`, `paymentStatus`, `productionStatus`;
   - платежи: `createdAt` (по умолчанию), `orderNumber`, `amount`, `status`, `paymentMethod`;
   - списки сотрудников: `updatedAt` (по умолчанию), `createdAt`, `status`, `createdByName`.
2. **Удаление заявки** (`morefoto.handoff`): `DeleteStaffRequestUseCase`, `DELETE /api/v1/staff-requests/{id}` → `204`;
   блокировка заявки, проверка автора/организатора (`403`), `409 STAFF_REQUEST_TRANSFERRED`; удаляются строки,
   история и ключи идемпотентности заявки; `404` — «уже удалена».
3. **Удаление заказа** (`morefoto.commerce`): `DeleteOrderUseCase`, `DELETE /api/v1/orders/{id}` → `204`; право
   (DEC-06), `orders->lock()`, отказ по оплате (DEC-02). Удаляет строки, ключи доступа, оформление, заявки и файлы
   выгрузок (у неоплаченного их не бывает — защитно). Попытки оплаты — через контракт
   `Rebit\Share\Contracts\Payment\OrderPaymentRemovalInterface` (реализация и DI в `morefoto.payment`): под блокировкой
   проверяет, что нет `succeeded`/`unknown`/`pending`, и удаляет отменённые попытки. Заказ с номером исчезает из
   реестров; покупатель по старой ссылке видит «заказ не найден».
4. Новые контроллеры — по правилу чистых контроллеров; миграции не нужны.

### Frontend

1. **Списки сотрудников**: `StaffRequestTable` на `UiDataTable`. Колонки: учреждение · съёмка, автор, детей, статус,
   передан, обновлён. Плитки-фильтры по статусу остаются, фильтр по учреждению и съёмке. Действия: открыть, изменить
   (автор), удалить (DEC-01). Мультивыбор → «Удалить». Карточка заявки (`/staff-requests/{id}`) — кнопка «Удалить список».
2. **Заказы**: `StaffOrderTable`. Колонки: заказ (номер + дата), покупатель (имя + телефон), учреждение · группа, сумма,
   оплата, изготовление. Фильтры прежние, компактнее (одна строка на desktop + «Ещё фильтры»). Плитки: найдено и
   разбивка по изготовлению — как сейчас. Действия: открыть, платежи заказа, удалить (только допустимые, DEC-02).
   Мультивыбор → «Выгрузить CSV», «Удалить». «Выгрузить всё» (DEC-07). Карточка заказа — «Удалить заказ».
3. **Платежи**: `PaymentTable`. Колонки: заказ, учреждение · группа, способ, сумма, статус (+ «поздняя»), начат.
   Действия: открыть, к заказу. Мультивыбор → «Выгрузить CSV»; «Выгрузить всё».
4. Общий `useCsvExport` (UTF-8 с BOM, `;`, экранирование, имя `orders-YYYY-MM-DD.csv`) и `useServerTable`
   (sort/page ↔ URL query, выбор между страницами) в `ui/`.
5. Mobile — карточная раскладка `UiDataTable`, как в срезе 1. Демо-режим (`CuratorScreen`, mock API) не трогаем.

### Исключено

- Отмена/возврат оплаченного заказа, ручная перепроверка платежа из интерфейса.
- Смена статуса изготовления из таблицы заказов (нет API, отдельная задача).
- Демо-экраны «Производство», «Доставка», «Обращения», «Проверка»; `WorkTable`/`PrintRows`, `TransferHistory`, `UploadQueue`.
- Серверная выгрузка CSV/XLSX (DEC-03).

## Зависимости и риски

- Зависимостей от незамерженных веток нет; всё на `main` `9e00856c`.
- R1. Сортировка по полям без индекса (`TOTAL`, `BUYER_NAME`) — filesort в пределах области; сейчас сотни строк,
  на тысячах — добавить индексы отдельной задачей.
- R2. Удаление заявки влияет на шаг «списки сотрудников» в «Ссылках» (#154): проверить live E2E, что после удаления
  группа больше не ждёт этот список.
- R3. Удалённый заказ пропадает из реестра платежей вместе с отменёнными попытками — это осознанно (DEC-02); денег
  по ним не было.
- R4. Объём оценочно 2,5–3,5 тыс. строк (backend ~1–1,3, frontend ~1–1,3, тесты ~0,7) — одна волна.

## Критерии приёмки

- Три экрана выглядят как одобренные скриншоты (desktop 1440, mobile 390), без горизонтального скролла.
- Сортировка по колонкам упорядочивает весь отфильтрованный список, а не страницу; порядок и страница сохраняются в URL.
- Заявку на проверке удаляет автор или организатор; перенесённую удалить нельзя, отказ понятен.
- Неоплаченный заказ удаляется организатором; оплаченный и с открытой оплатой — отказ, данные не меняются.
- CSV открывается в Excel с кириллицей; содержит выбранные строки или весь фильтр до 1000 строк.
- `npm run check`, unit PHP, phpstan, архитектурные проверки и `make test-e2e` зелёные.
