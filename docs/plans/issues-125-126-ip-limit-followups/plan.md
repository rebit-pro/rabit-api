# Issues #125 и #126 — доработки лимита гостевых обращений по IP

## Цель и контекст

Неблокирующие находки ревью PR #121 (issue #111, лимит `POST /api/v1/public/feedback` по IP гостя, слит в main `4fc9dce`).
Это issue-ветка, не волна: `docs/waves/graph.json` не меняется.

- [#125](https://github.com/rebit-pro/rabit-api/issues/125): `ClientAddressResolver::normalize()` оставляет IPv4-mapped
  IPv6 (`::ffff:8.8.8.8`) как есть. PHP `FILTER_FLAG_NO_PRIV_RANGE | FILTER_FLAG_NO_RES_RANGE` считает `::ffff:0:0/96`
  зарезервированным, поэтому публичный IPv4 в mapped-форме признаётся доверенным proxy, и resolver читает подставленный
  клиентом левый hop `X-Forwarded-For`. `resolve('8.8.8.8', '1.1.1.1')` → `8.8.8.8`, но
  `resolve('::ffff:8.8.8.8', '1.1.1.1')` → `1.1.1.1`.
- [#126](https://github.com/rebit-pro/rabit-api/issues/126): `SendGuestFeedbackUseCase` проверяет replay
  `Idempotency-Key` до блокировки счётчика адреса. Два одновременных одинаковых запроса на границе лимита (4 из 5):
  оба не видят ключа, первый под блокировкой создаёт 5-е обращение и фиксирует ключ, второй дожидается блокировки,
  видит счётчик 5 и получает `429 RATE_LIMITED` вместо сохранённого номера.

  `/home/user/rabit-api-worktrees/issues-125-126-ip-limit-followups`, base `origin/main` `4fc9dce`.

## Установленные факты

- PHP 8.4.25 (образ `rabit-api-php-cli:d1-local`): `::ffff:8.8.8.8`, `::FFFF:8.8.8.8`, `0:0:0:0:0:ffff:808:808` —
  валидные IP, не публичные по фильтру; `inet_ntop(inet_pton())` даёт `::ffff:8.8.8.8`, то есть текущий `normalize()`
  форму сохраняет. Обычный IPv6 `2001:db8::1` — публичный.
- Mapped-адрес — штатный вид IPv4-пира у dual-stack сокета, слушающего `::`: так его может записать прокси в
  `X-Forwarded-For` или отдать php-fpm в `REMOTE_ADDR`. Есть ли такая форма в текущей цепочке stage, не подтверждено.
- `GuestAddressHasher` (morefoto.support) уже сводит mapped к IPv4, но после выбора адреса: решение о доверии это не
  исправляет. Там же IPv6 режется до /64.
- `BitrixSupportTransaction` — READ COMMITTED. `lockGuestAddress()` — upsert + `SELECT … FOR UPDATE` строки адреса:
  запросы одного адреса выполняются по очереди до commit. `idempotency()` — `SELECT … FOR UPDATE` в
  `mf_support_idempotency`; для отсутствующей строки в READ COMMITTED ничего не резервирует, но блокирующее чтение
  всегда видит последнюю зафиксированную версию.
- `mf_support_idempotency`: PK `(SCOPE_KEY, KEY_HASH)`, `QUESTION_ID INT UNSIGNED NOT NULL` с FK на вопрос.
  Резерв ключа до создания вопроса (как в #27 для handoff) потребовал бы миграции `QUESTION_ID NULL`.

## Решения

- **R1 (#125). Канонизация в `ClientAddressResolver::normalize()`.** После `inet_pton` 16-байтовый адрес с префиксом
  `::ffff:0:0/96` сводится к 4 байтам и печатается как IPv4. `normalize()` вызывается и для `REMOTE_ADDR`, и для каждого
  hop XFF, поэтому доверие и итоговый адрес считаются уже по IPv4: публичный IPv4 не доверен в обеих формах, приватный
  в обеих формах проходится как proxy. Обычный IPv6 не меняется.
- **R2 (#125). Канонизация в `GuestAddressHasher` остаётся.** Для текущего HTTP-пути она теперь недостижима, но убирать
  её небезопасно: хешер — отдельный порт с контрактом «любой IP → идентичность абонента». Без этой ветки mapped-адрес от
  любого другого источника попал бы в IPv6-ветку /64, и все такие гости делили бы одно окно `::/64` на 5 обращений.
  Это одна строка; общий helper между `rebit.share` и `morefoto.support` ради неё — оверкодинг.
  Разделение: resolver решает, кому верить, хешер — какой адрес считать одним абонентом.
- **R3 (#126). Replay проверяется под блокировкой адреса, одна проверка вместо ранней.** Порядок в транзакции:
  удалить старые окна → хеш адреса → `lockGuestAddress()` → replay (`idempotency()`) → лимиты → создание.
  Второй запрос того же адреса ждёт commit первого на блокировке строки адреса и затем читает уже зафиксированный
  ключ: тот же ключ и тело → сохранённый номер без нового обращения/сообщения/счётчика; другое тело →
  `409 IDEMPOTENCY_CONFLICT`; другой ключ → `429 RATE_LIMITED`.
  Почему не ранняя + повторная проверка: две одинаковые проверки без выигрыша, кроме пропуска upsert для редких
  повторов. Почему не резерв ключа (`INSERT IGNORE`, как #27): нужна миграция `QUESTION_ID NULL` и новые методы
  репозитория, это больше изменений, чем требует сценарий issue.
  Порядок блокировок: адрес → ключ. Галерейный сценарий блокирует только свой ключ (другой `SCOPE_KEY`), цикла нет.
  Цена: повтор теперь хеширует адрес и делает upsert строки адреса (окно с 0 обращений, живёт час); без
  `REBIT_ENCRYPTION_KEY` повтор тоже получает 503 (первый запрос без ключа и так не проходит).
- **R4 (#126). Тот же ключ с разных адресов.** Последовательно: повтор с другого (даже исчерпанного) адреса отдаёт
  сохранённый номер и не расходует лимит этого адреса — проверяется unit-тестом. Одновременно: разные адреса не
  сериализуются блокировкой адреса; второй запрос создаёт обращение, ждёт PK `mf_support_idempotency` в `remember()`,
  после commit первого получает duplicate key, транзакция откатывается → `503 SUPPORT_UNAVAILABLE` без дубля; повтор
  после этого — сохранённый номер. Поведение как до PR #121 и как в галерейном сценарии; закрытие требует резерва ключа
  с миграцией — ограничение фиксируется в PR, отдельный follow-up по решению пользователя.

## Scope

- `rebit.share`: `ClientAddressResolver::normalize()`, тесты `ClientAddressResolverTest`.
- `morefoto.support`: `SendGuestFeedbackUseCase` (порядок и phpDoc), тестовый double `InMemoryQuestions` (управляемая
  «конкурентная фиксация» во время блокировки адреса), тесты `GuestFeedbackTest`, комментарий `GuestAddressHasher`.
- E2E-verifier `api/tools/e2e/verify-support.php`: раздел 7 — mapped hop в XFF и параллельные одинаковые запросы на
  границе лимита.

Исключено: резерв ключа/миграция (R4), другие формы встраивания IPv4 в IPv6 (NAT64 `64:ff9b::/96`,
IPv4-compatible `::a.b.c.d`, SIIT `::ffff:0:a.b.c.d` — PHP тоже считает их зарезервированными; в цепочке docker-сетей
не встречаются, сообщаются как попутное наблюдение), frontend, nginx/Traefik, деплой.

## Риски и ограничения

- R4: одновременные одинаковые запросы с разных адресов — второй получает 503, не дубль.
- Конкурентный порядок в unit моделируется double репозитория; реальная DB/HTTP-проверка — только в `make test-e2e`
  (раздел 7 `verify-support.php`), гонка на стенде недетерминирована: verifier проверяет контракт (все ответы 202 с
  одним номером, одно обращение, счётчик 5), но не гарантирует попадание в окно гонки.

## Критерии приёмки

- Публичный IPv4 в plain и mapped форме (remote и правый hop XFF) — клиент, левые hop не читаются.
- Приватный IPv4 в plain и mapped форме одинаково проходится как proxy; обычный IPv6 без изменений.
- Одновременный повтор с тем же ключом и телом на границе лимита адреса → сохранённый номер, без нового
  обращения/сообщения/счётчика; другое тело → 409; другой ключ → 429.
- Повтор с того же ключа с другого адреса → сохранённый номер, лимит этого адреса не расходуется.
