# D3 — атомарные переносы ребёнка и служебной заявки

## Цель

Организатор переносит полный набор ребёнка между группами одного типа одной съёмки (MED-07). Организатор или куратор проверяет заявку сотрудника (HND-10) и подтверждает льготный перенос наборов детей в папку сотрудников (HND-11). Перенос атомарен, сохраняет ID кадров, детей и связей и `originalGroupId`, не создаёт дублей и накопления скидок, не меняет заказы и сбрасывает подготовку ссылки F2 затронутых групп.

## Решения

Приняты пользователем 2026-09-22 в предложенном виде: «Подтверждаю все восемь решений, начинай». D11 внесён в `acceptedImplementationDecisions`, D12 снят с gates D3 (`decisionEvidence.D11`, `decisionEvidence.D3-D12-SCOPE` в обоих графах); запись в реестре MoreFoto — `docs/frontend/business-review/decisions.md`.

**D3-DEC-01 — купленные кадры при льготном переносе (D11).**

- Предложение (как в прототипе R17): HND-11 разрешён и тогда, когда у ребёнка есть заказы в исходной группе, при любом статусе оплаты.
- Заказы не меняются: снимок, суммы, статусы, строки и ключ остаются прежними.
- ID кадров, детей и связей сохраняются, поэтому будущие выдача файлов и печать по заказу ссылаются на те же кадры.
- Скидки задним числом нет; исправления и возвраты — только I1/I3.
- Новые покупки идут в папке сотрудников по D05. Порог подарка считается внутри заказа, накопления между заказами нет.
- HND-10 отдаёт `hasOrders`, UI предупреждает. Факт заказов входит в signature, поэтому заказ, созданный после preview, даёт 409 `SIGNATURE_CONFLICT`.
- Альтернатива: 409 `CHILD_HAS_ORDERS` при любом заказе. Это проще, но поздний список сотрудника после открытия галереи становится невозможным.

**D3-DEC-02 — состояния групп.**

- MED-07 — исправление разметки до открытия:
  - обе группы в подготовке (`sentAt` пуст), у ребёнка нет заказов;
  - иначе 409 `GROUP_LOCKED` / `CHILD_HAS_ORDERS` — так работают `moveChild` прототипа и строка матрицы о купленных фото.
- HND-11:
  - исходная группа — в любом состоянии;
  - целевая staff-группа — `preparing` или `open`;
  - закрытая целевая — 409 `TARGET_GROUP_CLOSED`, иначе ребёнок теряет возможность покупки.
- Альтернатива: запретить перенос и из закрытой исходной группы.

**D3-DEC-03 — совместные кадры (M:N по D03).**

- Предложение: кадр, назначенный и ребёнку, который остаётся в исходной группе, блокирует перенос — 409 `SHARED_PHOTO` с кодами кадров в ответе и preview.
- Если все дети такого кадра переносятся одной операцией (одна заявка, одна целевая группа), кадр переносится один раз вместе с ними.
- Альтернативы:
  - снять связь с остающимся ребёнком — он теряет кадр;
  - показывать кадр в нескольких группах — меняет модель D1/D2/E4/F2, нужно отдельное решение.
- Инструмент разделения совместного кадра — follow-up issue при первом реальном случае.

**D3-DEC-04 — целевая папка и коды.**

- HND-10/11: целевая группа — единственная staff-группа той же съёмки и учреждения:
  - нет — 409 `STAFF_GROUP_REQUIRED`;
  - несколько — 409 `STAFF_GROUP_AMBIGUOUS`. Прототип берёт первую, а контракт выбор не передаёт.
- HND-10/11: коды — следующие свободные в целевой группе в порядке строк (A…Z, AA…).
- MED-07: код задаёт организатор — 1–3 латинские буквы, свободный, иначе 409 `TARGET_CODE_TAKEN`.
- Номера кадров и `assignmentId` сохраняются, меняется только буквенная часть кода кадра (A003 → C003). Прототип перенумеровывает с 1; при непрерывных номерах результат тот же.

**D3-DEC-05 — обложки.**

- Перенесён кадр-обложка исходной группы — обложкой становится первый оставшийся назначенный готовый кадр группы (по коду ребёнка и номеру). Если кадров не осталось — обложка снимается.
- Целевой группе без обложки назначается первый перенесённый кадр.
- Прототип только снимает исходную обложку. Открытая галерея осталась бы без обложки навсегда: MED-06 после передачи заблокирован.

**D3-DEC-06 — COM-13 после переноса.**

- `correctionPhotos` строится по детям строк заказа независимо от их текущей группы: кадры ребёнка с текущими кодами. Снимок строк не меняется.
- Нынешний фильтр по группе заказа дал бы для перенесённого ребёнка пустой список.
- Альтернатива: оставить фильтр до I1.

**D3-DEC-07 — D12 и граф.**

- D3 не меняет оплату, возвраты, печать и файлы. Последствия переноса с оплатой и возвратом проверяет I3: она уже зависит от D3 и закрыта решением D12.
- Предложение для обоих графов:
  - D11 внести в `acceptedImplementationDecisions` по DEC-01…05 с `decisionEvidence`;
  - D12 убрать из `decisionGates` D3 с записью `D3-D12-SCOPE`.
- Альтернатива: ждать полного решения D12, D3 остаётся заблокированной.

**D3-DEC-08 — коллизия ID D3 (#42, п. 3).**

- В D3, только документами:
  - перенести материалы PR #32 в `docs/plans/OPS-stage-media-recovery/` вместе с `visual/` и обновить ссылки;
  - добавить в AGENTS.md и CLAUDE.md правило: оперативные исправления вне графа не используют ID волн.

- Альтернатива: оставить всё в #42, отчёт D3 положить рядом со старыми снимками PR #32.

## Архитектурные правила

- **Транзакция.**
  - Одна локальная транзакция у владельца команды: Media для MED-07, Handoff для HND-11.
  - Участники других модулей работают внутри неё через контракты `rebit.share/lib/Contracts/<Domain>` и не делают commit; эталоны — `GroupCalendarInterface`, `StaffChildReference`.
  - Промежуточного сохранённого состояния нет: при любом сбое откатывается всё.
  - Deadlock и lock wait — ограниченный повтор всей операции, как в `OrderTransaction`.
- **Порядок блокировок** — как в F2:
  1. состояние Access;
  2. группы Organization — исходные и целевая, по возрастанию ID;
  3. актор;
  4. идемпотентность;
  5. ревизия медиа съёмки;
  6. строки детей `FOR UPDATE`;
  7. проверка заказов Commerce.
- **Сериализация с COM-10.** Строки детей блокируются до проверки заказов, а COM-10 (SERIALIZABLE) читает те же строки. Возможны два исхода: заказ виден переносу (при устаревшем preview — `SIGNATURE_CONFLICT`) либо COM-10 после переноса получает `INVALID_CART` или `QUOTE_STALE`.
- **Идемпотентность.**
  - `Idempotency-Key` (32 hex) обязателен для MED-07 и HND-11.
  - Ключ резервируется до replay и проверок (как E5/H1); порядок F1 (#27) не копируется.
  - Тот же ключ и тело — тот же ответ; другое тело — 409 `IDEMPOTENCY_CONFLICT`.
  - HND-11 для заявки в `transferred` после проверки прав отдаёт 200 с сохранёнными `results` без повторного переноса, даже с другим ключом.
- **Сохранение ID.**
  - Перенос обновляет существующие записи: `mf_media_child.GROUP_ID/CODE`, `b_hlbd_mf_photo.UF_GROUP_ID` и `UF_REVISION + 1`.
  - Не меняются `UF_ORIGINAL_GROUP_ID`, `PUBLIC_ID` кадров/детей/связей и `SEQUENCE_NO`. Поэтому остаются согласованными право сотрудника (`StaffEligibility` по `CHILD_ID`), строки заказов и `results`.
  - `ux_mf_media_child_code` — последняя защита от занятого кода.
- **Signature HND-10** — SHA-256 канонического состояния:
  - заявка и её revision;
  - целевая группа и занятые в ней коды;
  - по каждой строке — ребёнок, исходная группа, код и целевой код, кадры с revision и статусом, совместные связи;
  - факт заказов и состояния групп.
  - HND-11 пересчитывает signature внутри транзакции после блокировок.
- **Подготовка F2.** Отдельного флага нет: изменение кадров, связей, обложек и статуса заявки меняет signature обеих групп. Непереданные группы получают `prepared=false` и снова требуют HND-03. Отдельный вызов Handoff из Media не нужен.
- **Права (D08).**
  - MED-07 — организатор (`media.manage`).
  - HND-10/11 — организатор и куратор своей области; руководитель и воспитатель — 403; заявка вне области — 404.
  - Отказы D3 отдают коды в собственном коде: `FORBIDDEN`, `STAFF_REQUEST_NOT_FOUND`, `GROUP_NOT_FOUND`.
- **DI и контроллеры.**
  - Commerce уже зависит от Handoff, поэтому `ChildOrdersInterface` Handoff получает лениво через DI-замыкание, как в F2.
  - Новые контроллеры чистые: наследуют `AuthenticatedApiJsonController`, один RequestDto на action. `MediaController` не расширяется.
- **Тело HND-11.** `reason` — необязательный комментарий до 500 символов после trim (в прототипе подтверждение без причины), пишется в историю. `confirmed=true` обязателен, иначе 422 `CONFIRMATION_REQUIRED`.
- **Контракт MED-07.** `childCode` в ответе — код ребёнка в целевой группе. Уточняется в каноне вместе с кодами ошибок.

## Риски и ограничения

- **Размер.** Оценка — 4–5,5 тыс. рукописных строк, в пределах разрешённых 6 тыс.
- **Конкуренция.** Параллельные COM-10 (SERIALIZABLE) и HND-03/04 могут давать deadlock, нужен повтор. Обязателен реальный конкурентный MySQL-тест.
- **Регрессия E5.** Изменение `ChildPhotosInterface` затрагивает COM-13.
- **Совместные кадры.** Без инструмента разделения они блокируют перенос (DEC-03).
- **Открытая галерея.** Перенос из неё убирает набор у родителей исходной группы, корзины устаревают. В UI нужен текст предупреждения.
- **#42.** Отказы общих источников Access до его исправления отдают `SERVICE_UNAVAILABLE`. E2E D3 проверяет HTTP-статусы и коды собственных отказов.
- **Файлы F2.** Граф, checklist, маршруты и DI Handoff, `prepare.php` и runner пересекаются с F2. Конфликтов не будет: F2 слита, изменения ложатся поверх `44f2e36`.

## Критерии приёмки

1. MED-07, HND-10 и HND-11 соответствуют уточнённому канону, HND-08 отдаёт `results`. MED-02/04 после переноса показывают новую группу и код при прежних ID и `originalGroupId`.
2. Перенос атомарен: при сбое любого участника ни одна таблица не изменена. Повтор после сбоя тем же ключом завершает перенос ровно один раз.
3. Два переноса, повтор, конкурентные подтверждения и несколько детей не создают дублей детей, связей и кадров и не переносят набор дважды.
4. Заказы после переноса не меняются: снимок, суммы, статусы, строки, ключи.
   - COM-11 и COM-13 работают.
   - Старые корзины исходной галереи отклоняются.
   - Новые покупки в папке сотрудников получают льготу D05 без накопления.
5. Каждый из следующих случаев даёт 4xx без изменений:
   - устаревшие revision, signature или набор;
   - занятый код;
   - чужая, закрытая или неоднозначная целевая группа;
   - совместный кадр;
   - запрещённая роль.
6. Подготовка F2 обеих групп сбрасывается: HND-02 `prepared=false`, `staffRequestsPending` снимается, снова нужна HND-03. Разметка и обложка после передачи ссылки или заказа запрещены.
7. Миграция ставится на пустую БД, повтор `up()` безопасен, `down()` не уничтожает данные.
8. Реальный browser E2E и визуальная проверка desktop/mobile переноса ребёнка и льготного переноса, без demo-хранилища.
9. PASS для PHPUnit, PHPStan, php-cs-fixer, frontend check/unit и DAG/99 API; в PR нет чужих коммитов.
