# Компактная сводка продаж группы

## Цель и контекст

Этап 3 одобренных доработок MoreFoto по встрече 07.11.2026: сохранить существующую сводку продаж и иерархию учреждение → съёмка → группа, сократить визуальный шум на уровне группы и согласовать экран с PDF.

Источник требований: `docs/plans/OPS-telemos-20261107-prompt/artifacts/implementation-prompt.md`, раздел 3 и T06/T07, и `implementation-stages.md`, этап 3. Пакет сохранён в PR #235; его наличие в другой ветке не является runtime-зависимостью и не разрешает перенос её продуктового кода.

Ветка: `codex/ops-compact-group-report`. База: проверенный удалённый main `90755f3a3700d55dae94befabea387ca8637c217`. PR пока не создан.

## Scope

- Компактные строки существующего отчёта группы: заказ, указанное для всего заказа ФИО либо «Не указано», состояние оплаты, показатели печати/digital/bundle и сумма.
- Убрать крупные и повторяющиеся миниатюры из рабочего отчёта; не загружать изображения, которые больше не выводятся в PDF.
- Сохранить итоговые показатели, печать по продукции, доступ по ролям и все существующие уровни отчёта.
- Дать доступ к строкам «Нет заказа» без длинного списка пустых строк в основном рабочем виде.
- Согласовать состав строк и значения экрана/PDF; обновить относящуюся к сводке инструкцию.

Вне scope: новая производственная ведомость этапа 6, новые архивы/формат ZIP, этапы 1/2/4–8, расчёт продаж заново, изменение схемы заказов/оплат, исправления общего UI-kit, merge, deployment и внешняя публикация.

## Решения и открытые вопросы

- Рабочий вариант из одобренного этапа: по умолчанию компактный список детей с заказами; явный счётчик строк «Нет заказа» и переключатель полного списка. Скрываются только строки без заказа, а не неоплаченные и поздние заказы. Исходные данные и агрегированные итоги не удаляются.
- ФИО принадлежит целому заказу. Нельзя сопоставлять ФИО ребёнку по совпадению имени или миниатюры; один заказ с несколькими детьми не должен удваивать сумму. Исторические null сохраняют «Не указано».
- Дизайн использует текущие Vuetify-компоненты, UiDataTable, MfStatus и токены `--mf-*`; визуальное направление и навигация существующего кабинета сохраняются. Главный элемент — компактный список, без новых декоративных карточек.
- Режим PDF передаётся явно через query `childrenView=ordered|all`: это выбор представления строк, а не изменение продаж. Существующий JSON остаётся полным; без параметра PDF сохраняет полный список для совместимости. Новый экран по умолчанию использует ordered и передаёт выбранный режим PDF. Полный набор и счётчик доступны в обоих режимах, поздние/неоплаченные не скрываются. HTML получает явный параметр через writer-контракт, обозначает режим/счётчик и форматирует готовые данные; итоги и права не пересчитывает.
- Изменение request/result/controller, если оно потребуется для режима PDF, допускается только с проверкой совместимости всех вызовов и архитектурным тестом чистоты HTTP-границы. Новых маршрутов и миграций пока не планируется.

## Зависимости, риски и ограничения

- По таблице этапов 3 не зависит от merge этапов 1/2. Ветка создана непосредственно от main; код незамерженных веток не переносится.
- Этап 1: исправления R1/R2 в `e62b720`, доказательства T01–T04/visual и тестовая обвязка в `e9e7bb304faa5af5166fbe1967fd35b504606671`; PR #235 ещё Draft, локальные коммиты не отправлены. Целевая группа b прошла 80/80, a отдельно 81/81; полного объединённого зелёного запуска нет.
- Этап 2 уже реализован в `codex/ops-gallery-original-filenames`, HEAD `7f4a5f3d06c70f23a204941127fa4c4811ca9ed7`, отдельный worktree. Он требует собственного ревью и E2E/visual и не повторяется здесь.
- Нельзя суммировать по детским строкам показатели заказа с несколькими детьми: источником общих итогов остаются действующие агрегаты Commerce.
- У большой группы PDF проверяется по содержимому и числу страниц, а не только по `%PDF`/HTTP 200. Настоящие desktop/mobile/HTTP/E2E остаются отдельным обязательным этапом перед merge; стенды на этапе подготовки не поднимаются.
- AST текущего worktree отделён от индекса исходного checkout. Для чтения/записи служебного кеша требуется разрешённый доступ вне sandbox; watcher не включён.
- Backend с поддержкой childrenView должен выпускаться до нового frontend либо вместе с ним: старый StrictRequest отклонит новый параметр. Старые клиенты с новым backend совместимы.

## Состав решения — реализовано, версия 1 от 09.11.2026

Состав выбран до первой правки кода. Используются существующие агрегаты Commerce, JSON и ролевые проверки; SQL, схема и контроллер не меняются.

- `SalesReportRequestDto`: последний необязательный `string $childrenView = 'all'`, Symfony Choice для all/ordered. Реальный StrictRequest запрещает строковые bool в GET, поэтому wire-параметр — строка; неизвестный режим даёт действующую ошибку валидации 422. `SalesReportResultMapper::input()` преобразует его в последний `bool $includeUnordered = true` Application InputDto. DTO остаются без методов.
- `ExportSalesReportPdfUseCase`: убрать зависимость Media и чтение миниатюр; передавать готовый отчёт и includeUnordered в writer. `SalesReportPdfWriterInterface::pdf(SalesReportOutputDto $report, bool $includeUnordered = true): string`; единственный production writer, его DI, HTML и unit-вызовы меняются вместе. Метаданные детей и preview endpoint сохраняются для совместимости.
- `SalesReportHtml::body($report, bool $includeUnordered = true)`: компактная таблица без изображений, отдельные digital/bundle, явный счётчик строк без заказа и выбранный режим. Общие суммы остаются из report.totals; таблица заказов с ФИО остаётся отдельной и компактной, без сопоставления с кодом ребёнка. Табличные thead повторяются в PDF.
- Компоненты: `SalesReportScreen` только собирает разделы; новый `ReportChildrenSection` получает полный children и includeUnordered, отдаёт `update:includeUnordered`, показывает счётчик и фильтр; `ReportChildrenTable` получает видимые строки/пустое состояние и отвечает за сортировку/пагинацию; `ReportOrdersTable` получает orders и выводит существующий UiDataTable, с именем/оплатой/суммой и пагинацией. `useSalesReport` владеет единственным переключателем и защищает PDF от устаревшего ответа при смене области/режима.
- Внешние маршруты прежние. `GET /api/v1/sales-report/pdf?...&childrenView=ordered` экспортирует все строки выбранного вида, независимо от страницы/сортировки таблицы. JSON и прежние запросы без параметра совместимы; новые ошибки/миграции отсутствуют. Контроллер остаётся чистым, архитектурный тест и настоящий mapper проверяют wire-контракт.

### Визуальное решение

Адресат — организатор/сотрудник, который сверяет заказы перед работой с группой. Область: учреждение, съёмка, код ребёнка, заказ, оплата, печатная продукция, digital/комплект. Сигнатура — компактные коды и счётчик «Нет заказа», отдельно от указанного на заказ ФИО. Вместо фотоленты, длинных пустых списков и карточки на каждый заказ используются рабочие таблицы.

Для Screen/ChildrenSection/ChildrenTable/OrdersTable едины: фокус на строках и оплате; текущие белые поверхности, тёмный текст, синий акцент, зелёный подтверждённой оплаты и янтарный поздней из токенов МореФото; тонкие существующие границы без новых теней. Manrope для заголовков, Golos Text для строк; плотность compact, интервалы `--mf-space-2/3/4` по сетке 4 px, числовые колонки с tabular-nums. Счётчик и переключатель вторичны к данным; состояния loading/error/empty и мобильные карточки предоставляет действующий UI-kit. Новой палитры/общего UI-kit не вводится.

## Критерии приёмки

Пустая, обычная и большая группа дают читаемую сводку без потери заказов, состояний или сумм. В рабочем режиме нет длинной таблицы «Нет заказа», но точный счётчик и полный список доступны. Неоплаченные/поздние заказы остаются видимыми и не становятся подтверждённой продажей. ФИО не приписывается детям по догадке; исторические null и заказы на нескольких детей сохраняют семантику. PDF согласован с режимом экрана и не читает ненужные миниатюры. Все уровни и права действующей сводки сохранены.

## Тест-кейсы

1. **T07-EMPTY.** Предусловие: пустая группа либо группа только с детьми без заказов. Действие: открыть рабочий/полный список и получить PDF. Ожидание: понятные разные пустые состояния, точный счётчик «Нет заказа», доступный полный список; итоги не меняются. План: адресный `SalesReportTest|SalesReportPdfTest`, `node --experimental-strip-types --test tests/ui/sales-report.test.mjs` из frontend; перед merge реальный HTTP/E2E.
2. **T07-ROWS.** Предусловие: дети/заказы с paid, unpaid/pending, late и none, несколько видов печати и digital/bundle. Действие: открыть оба режима и PDF. Ожидание: скрывается только none, все остальные строки и показатели сохранены; счётчик точен, общий итог не зависит от режима. Те же адресные PHP/frontend команды.
3. **T07-LARGE.** Предусловие: большая обезличенная группа с длинными именами/названиями и множеством строк. Действие: сортировка, пагинация, смена режима и выгрузка PDF. Ожидание: нет потери строк/обрезаний/лишних миниатюр, PDF содержит все выбранные строки с читаемыми заголовками. План: `SalesReportPdfTest`, frontend unit; реальный desktop/mobile и просмотр страниц PDF перед merge отдельным исполнителем.
4. **T06-NAMES.** Предусловие: исторический заказ без ФИО, одинаковые ФИО в разных заказах, один заказ на нескольких детей. Действие: экран/PDF. Ожидание: «Не указано» только для null, заказы не склеены по имени, ФИО не сопоставлено детской строке по догадке, общий итог не удвоен. План: `SalesReportTest|SalesReportPdfTest`, frontend unit и реальный сценарий перед merge.
5. **T07-SCOPE.** Предусловие: organizer/curator/head/teacher с разными областями. Действие: переходы учреждение → съёмка → группа, возврат, запрос чужой группы и PDF. Ожидание: прежняя навигация/область доступа и отсутствие чужих данных. План: `SalesReportTest|SalesReportArchitectureTest`; реальный HTTP/E2E перед merge.
6. **T07-LOAD.** Предусловие: ошибка запроса/повтор и быстрая смена группы/режима во время загрузки PDF. Действие: повторить загрузку. Ожидание: явные loading/error/empty, отсутствие двойного запроса и устаревшего ответа в новом отчёте. План: frontend unit/типы; реальный сценарий перед merge.
