# Защита от повторной покупки одного файла

## Цель и границы

Организатор задаёт правило в карточке товара «Электронный кадр». Родитель добавляет конкретный оригинал один раз за заказ, в том числе когда один снимок привязан к нескольким детям или предложен через две позиции каталога. По умолчанию защита включена для существующих и новых электронных товаров. Печать, комплекты, подарки, выдача оригиналов и заказы других покупателей сохраняют собственные правила. Поиск по истории оплаченных заказов вне задачи.

## Состав решения

- Commerce владеет признаком товара. В действующих POST/PATCH каталога поле `allowDigitalQuantity` типа boolean опционально, при создании по умолчанию false. PATCH с пропущенным полем сохраняет значение для электронного товара. При смене вида на печать или комплект пропущенный флаг становится false. Обратная смена вида сохраняет false до явного разрешения количества. Явный true для печати или комплекта отклоняется. Условия группы и пересчёт с учётом расходов передают настройку товара. Сохраняем совместимость повторов прежних запросов каталога.
- Правило PATCH принадлежит Domain. В существующий `ProductPatch` добавляется `allowsDigitalQuantity(ProductKind $currentKind, bool $currentlyAllowed): bool`. `ProductMapper::apply()` передаёт текущее состояние этому методу, `ProductDetails` проверяет допустимость полученного товара. Сигнатуры HTTP и DTO сохраняются.
- В защищённом режиме идентичность файла определяет Media `photoId` из разрешённого назначения. В расчёте и перед checkout один файл нельзя провести двумя отдельными электронными строками, если хотя бы одна защищена. Сервер возвращает 422 при нарушении. Номер кадра и принадлежность ребёнку не идентифицируют файл. При снятии ограничения у конкретного товара можно явно выбрать 1–99 экземпляров. Для комплекта всегда действует одна единица на ребёнка.
- Две миграции foundation добавляют настройку HL-каталога и фиксируют разрешение количества в снимке строки заказа для проверки MySQL. Старые записи получают безопасное значение. Откат должен сохранять оплаченные данные.
- ProductFields — переключатель организатора. ProductSelector — добавление/удаление либо счётчик согласно настройке. CartLineItem — то же правило в корзине. Сервисы выбора узнают файл при повторном добавлении, сохранённая корзина сверяется с актуальным каталогом и назначениями снимка перед расчётом. Устаревшая привязка к ребёнку не вытесняет доступный кадр. Демо использует те же правила выбора, live дополнительно проверяет сервер.
- Зависимости входят в `main`: каталог E1/E2, условия E3, витрина E4 и заказ E5. Используются существующие маршруты, транзакции, ревизии и защита checkout от повторной отправки.

## Тест-кейсы

1. T01. Создать электронный товар без поля, поменять галочку, перечитать товар, повторить старый POST и выполнить PATCH без поля. Ожидаются безопасное начальное значение, сохранение выбора и совместимый хеш. PHPUnit CatalogApiTest/CatalogTest, live catalog.
2. T02. Добавить общий снимок с двух назначений или через другой электронный товар, отправить количество 2 для защищённого товара. Сервер отклоняет повтор. Два разных снимка допускаются. Печать того же снимка рассчитывается отдельно, комплект сохраняет собственное ограничение. PHPUnit StorefrontQuoteTest.
3. T03. При разрешённом количестве выбрать две единицы и оформить заказ. Сумма равна удвоенной цене, снимок заказа хранит количество. Миграция позволяет старые строки, ограничивает комплект и защищённый файл. PHPUnit, Playwright и проверка CHECK на строке оформленного заказа в `api/tools/e2e/verify-orders.php` на одноразовом стенде.
4. T04. Проверить переключатель карточки, действия на кадре и в корзине, повторное добавление, удаление и восстановление старой корзины. Команды `npm --prefix frontend run test:commerce`, `npm --prefix frontend run check` и Playwright live на desktop/mobile.
5. T05. Проверки поставки — точечный PHP-CS-Fixer, PHPStan, PHPUnit, frontend production build, `git diff --check`.
6. T06. У электронного товара количество разрешено. Через PATCH сменить вид на печать или комплект с пропущенным флагом, поменять цену, явно передать false и true, вернуть прежний вид. Ожидаются сброс при уходе из электронного вида, сохранение при обычном редактировании, применение явного boolean и предметный отказ при true для печати/комплекта. Проверить как Domain-правило, так и путь `UpdateProductUseCase` до записи. Команда из api в PHP 8.4 — `php vendor/bin/phpunit --do-not-cache-result --no-progress --colors=never --testsuite unit --filter 'CatalogApiTest|CatalogTest'`.
7. T07. Сверить порядок поставки ниже с двумя миграциями, текущими POST/PATCH, схемой снимка заказа и регламентом W04. Ожидаются совместимость промежуточных версий, определённый момент включения функции и сохранность данных при откате. Проверка чтением указанных исходников и `git diff --check`.
8. T08. На текущем снимке после N1/N3 запустить все группы реального E2E в изолированной БД по A8, проверить изображения desktop/mobile затронутого сценария и остановить ресурсы запуска. Ожидаются PASS всех групп, ноль skipped/flaky/unexpected, манифест SHA-256 исходников и подтверждённая очистка. Планируемая команда — `make test-e2e` с проверенными kernel/vendor/образами и `E2E_YOOKASSA_ENV=/dev/null`. Пользователь выбрал модель GPT-6.2 Sol и reasoning max. Перед запуском сохраняются HEAD и SHA-256 всех tracked/untracked исходников; plan/progress учитываются отдельным манифестом. При проблемах Docker допускается восстановить только тестовую инфраструктуру без изменения приложения и семантики runner. В конце повторно сверяются исходники, отчёты всех групп и отсутствие ресурсов своего запуска.
9. T09. На базе `975cc7fd` совместить миграцию приватной галереи съёмки из PR #244 и две миграции количества электронных товаров. Прогнать `make test-e2e` на свежих MySQL по всем группам. Ожидаются установка трёх разных версий, успешная покупка из приватной галереи съёмки и проверка обоих положений галочки количества. После каждого запуска проверить exit status и запись в истории. ## Откат поставки

- При ошибке миграции или backend сохранить уже добавленные колонки и историю, завершить исправление миграции либо вернуть совместимые образы. Схема расширена безопасными defaults для прежних записей.
- Возврат frontend совместим с новым backend. Если требуется также вернуть прежний API, сначала вернуть прежний frontend и завершить сохранения из открытых вкладок нового редактора, затем переключить API. Открытым вкладкам нового редактора требуется перезагрузка, поскольку прежний API отклоняет новое поле.
- При возврате прежнего API утрачиваются выбор количества электронного товара и защита одного оригинала между строками. Снимки уже оформленных заказов, их количество и суммы сохраняются. У товаров с `UF_ALLOW_DIGITAL_QUANTITY = 1` прежний код не сбрасывает флаг при смене вида, поэтому такой PATCH может быть отклонён CHECK. Для сохранения новых правил покупки и редактирования используется исправление backend вперёд с совместимой схемой.
- В рабочей БД сохранять обе новые колонки. `down` первой миграции отказывает при разрешённом количестве в каталоге, второй — при наличии заказа с `ALLOW_DIGITAL_QUANTITY = 1`. Заказы и значения их снимков сохраняются при откате кода. Обратимость схемы проверяется на одноразовой базе без таких данных.
