# W05 — предметная модель первого среза

**Предложение, не утверждённая модель.** Источники и условия приёмки — в [пакете W05](../waves/w05/README.md). Каноническая предметная область MoreFoto пока ожидает R17; после согласования перенести туда принятые положения. Здесь нет реализованных `morefoto.*`.

## Термины и границы

| Термин | Смысл и владелец записи |
| --- | --- |
| Identity | Учётная запись Bitrix, идентификатор пользователя, пароль, блокировка Auth и сессия; `rebit.auth` |
| StaffProfile | Служебная роль, активность MoreFoto, revision/accessRevision; `morefoto.access`. Совпадение email не создаёт профиль |
| Назначение | Связь сотрудника с учреждением в роли curator/head либо с группой в роли teacher; Access |
| Учреждение | Название и адрес, общий контекст съёмок; `morefoto.organization`. Контакты родителей здесь не хранятся |
| Съёмка | Самостоятельное событие учреждения, название, календарная дата; Organization |
| Группа | Группа конкретной съёмки, regular/staff, календарь приёма; Organization. Одинаковые названия в разных съёмках не означают одну запись |
| Передача ссылки | Факт и история передачи, подтверждение подготовки; `morefoto.handoff`. Меняет календарь через Organization |
| Личная ссылка | Capability одного заказа; `morefoto.commerce`. Отличается от доступа к галерее и права скачать файлы |
| Сводка учреждения | Ролевая проекция Organization, финансовые факты поставляет Settlement. Проекция не владеет финансовыми записями |

`curatorId`, `headId`, `teacherId` во внешних формах — поля команд/проекций. В таблицах Organization независимых копий назначений нет. Реальные name/email читает Auth-контракт; Access не дублирует пароль, токен или самостоятельно управляемый email.

Одна роль на профиль; organizer работает со всем проектом без назначений. Curator/head могут иметь несколько учреждений, teacher — несколько групп. На учреждение допускается один curator и один head, на группу — один teacher. Пустая область допустима. Это предложение D08, а не вывод из структуры мокового массива users.

## Состояния и инварианты

Identity: pending/действующая/заблокированная сессия — ответственность существующего Auth; это не служебная роль. StaffProfile: active/inactive. Успешный login без активного StaffProfile не даёт прав MoreFoto. Повторная регистрация не активирует профиль. Блокировка Auth всегда запрещает доступ, даже при active=true в Access.

Учреждение и съёмка в первом срезе не требуют искусственных draft/published статусов. Публичных delete/archive команд в W07/W08 нет; удаление связанных данных и история не проектируются как cascade. Профили отключаются, а не уничтожаются.

Состояние приёма группы выводится из календаря и серверного now:

- `preparing`: sentAt и closesAt не установлены;
- `open`: передача подтверждена и now < closesAt;
- `closed`: now >= closesAt;
- продление закрытой группы может вернуть `open`, сохранив факт и историю прежнего закрытия.

Комбинация «sentAt есть, closesAt нет» недопустима. Cron не является источником истины для закрытия. Статус приёма не заменяет готовность фотографий, оплату, печать, доставку или выдачу файлов. Подтверждение передачи проверяет Handoff, а сроки атомарно меняет Organization. В W08, до Handoff, новые группы остаются preparing.

Имя/съёмка/тип группы: PATCH может изменить имя и назначение, но не переносит существующую группу в другую съёмку и не меняет regular/staff. Родительская цепочка проверяется сервером; чужой institutionId не может расширить область. Дата съёмки — отдельное календарное значение, не начало продаж.

Неактивная/неизвестная роль не получает ни одного действия. Отсутствие назначения даёт пустой разрешённый список, но не доступ по прямому ID. ACC-01 не содержит токенов и чужих контактов; permissions сообщает разрешённые действия, а не заменяет серверную проверку. Любая публичная регистрация/льготная галерея остаётся вне этой матрицы.

Для отсутствующего и чужого ресурса предлагается одинаковый 404 после проверки служебной сессии; запрещённое действие при известной допустимой области — 403. Невалидный/отозванный/истёкший Bearer — 401. Детали ошибок и enum-коды фиксируются в волне реализации и генераторе API.

## Смена назначений и версии

`revision` — версия редактируемой сущности. `accessRevision` — версия прав конкретного сотрудника. `assignmentSignature` — непрозрачная версия **всего текущего набора назначений**, полученная от Access. В первом срезе достаточно версии одной служебной строки AccessState; хешировать моки и доверять строке из браузера нельзя. Эти три значения не взаимозаменяемы.

Предлагаемые изменения канонического API до W07/W09:

- ACC-04 с назначениями должен получать assignmentSignature, как ACC-05. В текущей карте ACC-04 поле не указано.
- ORG-03/05/10/12 при изменении curatorId/headId/teacherId должны получать assignmentSignature и явный replaceAssignments для занятого назначения; сам revision учреждения/группы недостаточен. Подпись возвращается в соответствующих редакторских проекциях. Отсутствующее поле сохраняет назначение; null явно снимает допустимое назначение.
- Пустое создание без назначений не требует подписи; устаревшая подпись с изменением назначений даёт конфликт без частичного сохранения name/address. `replaceAssignments=true` разрешает подтверждённую замену, но не отменяет сравнение версии.
- В ACC-04/05 изменения роли/active также сверяются с актуальным состоянием под блокировкой. При смене роли назначения прежнего типа явно удаляются/заменяются в той же операции, иначе конфликт. Организатора с последними действующими полномочиями нельзя отключить/понизить.

Это открытые контрактные дельты W05. `build.py`, endpoints.json и Postman сейчас не изменены: после согласования обновлять исходный генератор, затем все производные файлы, а не править только таблицу Markdown.

## Транзакционная граница

Предлагается общий локальный MySQL connection и InnoDB, без распределённых транзакций. Владелец HTTP-сценария управляет одной транзакцией; Access/Organization/Auth выполняют свои записи через узкие контракты в её рамках. Контракту запрещён самостоятельный commit. Возможность существующего Auth участвовать в этой операции надо доказать на реальном ядре до W09; наличие метода отзыва этого не доказывает.

Порядок блокировок для операций с правами: AccessState → затронутые Institution/Shoot/Group в фиксированном порядке → StaffProfile по userId → соответствующие учётки Auth по userId. Все команды используют один порядок, включая Organization-редакторы и bootstrap организатора. Под блокировкой повторно проверяются полномочия инициатора, revision, assignmentSignature, занятость слотов, active/role и последний организатор. Простое предварительное чтение не защищает от гонки.

Записи бизнес-полей, назначений, версий, истории и отзыв всех затронутых сессий коммитятся вместе. В том числе изменяется прежний сотрудник, у которого забрали назначение. При любой ошибке — rollback всего сценария. Удалённый HTTP, письмо или доставка приглашения не выполняются внутри транзакции; их запуск/повтор описывается отдельно после commit. Deadlock требует повторить целую операцию с тем же idempotency key в ограниченном retry, не отдельный SQL UPDATE.

Каждый защищённый запрос проверяет актуальные Auth и Access. Для команд, меняющих данные, проверка области и запись защищены общей транзакцией от конкурентного снятия назначения. Кеш прав не может задерживать отзыв; до появления проверенного механизма инвалидации использовать прямое чтение. Обычный список выполняет scope-фильтр в БД; перед выдачей чувствительного результата повторно проверяет accessRevision, при её изменении отклоняет результат.

## Владельцы будущих агрегатов

| Владелец записи | Собственные данные | Получаемые факты |
| --- | --- | --- |
| Auth | Identity, пароль, сессии | Команда изменения/отзыва от Access |
| Access | Роль, active, назначения, версии прав | Identity; существование/цепочка Organization |
| Organization | Учреждение, съёмка, группа, календарь | Назначения Access; финансовый итог Settlement |
| Media | Фото, принадлежность, приватный оригинал/превью | Группа Organization; ограничения покупки Commerce/Settlement |
| Commerce | Каталог, расчёт, заказ, неизменяемый снимок, личный ключ | Фото/группа; подтверждённая оплата Payments |
| Handoff | Подготовка/факт/история передачи, заявки сотрудников | Календарь через Organization, перенос через Media, назначения Access |
| Payments | Попытка, provider ID, подтверждённая оплата/возврат, чек | Сумма Commerce; запрос возврата Settlement |
| Files | Право и операция выдачи, срок/отзыв, история доставки | Состав/оплата/решение Settlement; оригинал Media; ключ Commerce |
| Support | Обращение, ответ, согласование | Проекция заказа, финансовые факты, команда продления Handoff/Organization |
| Settlement | Исправление, резерв/распределение возврата, hold/перепечатка, финансовые итоги | Снимок Commerce; подтверждённые факты Payments |
| Production | Версия задания, отпечатки, комплектация | Закрытие Organization; состав/исправление/hold Commerce/Settlement |
| Shipping | Готовность версии, партия, факт передачи | Комплектация Production; группа Organization |
| Notification | Операция и попытка доставки, без права на оригинал | Разрешённый материал/получатель от Payments/Files |

Существующие Lead/LeadHunter сохраняются и не становятся частью заказов MoreFoto. Один владелец меняет свой агрегат; ReadModel не является новым агрегатом или контрактом.

Технические контракты остаются в Share/Application/Contract. Для предметных договорено отдельное Share/Contracts в PR #3 и MoreFoto; текущая база W04 ещё содержит старые инструкции. Перед кодом согласованно применить PR #3, сохранив существующие namespaces; не создавать две реализации одного контракта. W05 классы не размещает.

## Проверки будущих волн

W06: известные четыре роли, неизвестная роль, отсутствующий профиль, пустая область, revoked token. W07: чужой ID/список, конкурентные curator/head, повтор создания, устаревшая revision/signature, ORG-04 без фиктивных значений. W08: две съёмки одного учреждения, несовместимая цепочка ID, граничные сроки, повтор/конкурентное продление. W09: одновременная замена, блокировка/понижение, попытка отключить двух последних организаторов, гонка login/отзыва, сбой после каждого шага общей транзакции. Это критерии проверки будущего кода, не выполненные тесты W05.
