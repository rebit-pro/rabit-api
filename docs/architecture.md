# Архитектура RaBit API

## Модули и слои

Прикладная основа — `rebit.share` и `rebit.auth`; `rebit.notification` принимает и доставляет заявки с сайта, самостоятельная действующая лидогенерация находится в `rebit.leadhunter`. Будущие владельцы маршрутов MoreFoto определены в соседнем проекте. Слои: Domain, Application, Infrastructure, Presentation, Shared. UseCase оркестрирует сценарий; Controller преобразует HTTP-вход/выход; legacy Bitrix, HTTP, кеши и внешние системы закрываются Infrastructure.

Предметный ORM/SQL-репозиторий может находиться в Domain по принятому Bitrix-профилю. Сам SQL не требует интерфейса на каждый репозиторий. SQL в UseCase и бизнес-правила в форматтерах запрещены.

LeadHunter запускается командой `app:leadhunter:scan` по cron: Application управляет сбором, отбором, сохранением и доставкой заявок; Infrastructure реализует RSS fl.ru, хранилище, Telegram и email. Для Telegram используется общий клиент Share; торговые контракты и отдельный notification consumer для LeadHunter не требуются.

Notification обслуживает публичный `POST /api/v1/lead`: Controller валидирует вход/вложение, SubmitLeadUseCase вызывает порт доставки, Infrastructure отправляет сообщение через Telegram-клиент Share с условным email fallback. Сценарий синхронный. Старая торговая ветка очереди исключена; общая асинхронная доставка требует отдельных событий и контрактов. LeadHunter продолжает собственный рабочий поток доставки; перенос его на Notification этим восстановлением не выполняется.

## Репозитории и Result

Для нового чтения не использовать Bitrix Objectify-коллекции и гидрацию `fetchCollection()`/`fetchObject()` ради передачи данных. Один обычный запрос выполняется через D7 ORM, сложный запрос — чистым SQL в репозитории. Репозиторий возвращает результат запроса; потребитель читает массивные строки через `fetch()`/`fetchAll()`.

Различать `Bitrix\Main\ORM\Query\Result` и `Bitrix\Main\DB\Result` для чтения, `Bitrix\Main\Result`/AddResult/UpdateResult/DeleteResult для результата записи и API DTO. Не собирать массив лишь для повторной упаковки в Result. Для count, ID и флагов допустимы типизированные скаляры и массивы скаляров. Shape строк, nullable и типы дат фиксируются в phpDoc.

Result не проходит в HTTP, кеш или межмодульный контракт. Выбирать нужные поля, ограничивать списки, задавать устойчивый порядок; предотвращать N+1. Существующий write-путь с Entity не переписывается автоматически. Ошибки записи проверяются через `isSuccess()`.

Узкий `final readonly` ReadModel допустим для нескольких зависимых запросов, когда одного Result или скаляров недостаточно. Расположение: `Domain/<Aggregate>/Repository/ReadModel/`; собирается репозиторием и преобразуется непосредственным потребителем в его DTO/VO. Один SELECT с JOIN не требует ReadModel. ORM-объекты, Result, сервисы и чужие контрактные DTO в ReadModel не входят.

## Контракты и DI

Контракты Share разделяются по назначению, с двумя разными каталогами и namespace:

| Назначение | Каталог | Namespace |
| --- | --- | --- |
| Общие технические возможности | `rebit.share/lib/Application/Contract/<Capability>/` | `Rebit\Share\Application\Contract\<Capability>` |
| Предметное взаимодействие между модулями | `rebit.share/lib/Contracts/<Domain>/` | `Rebit\Share\Contracts\<Domain>` |

`Application/Contract` — единственное число. Существующие `Cache`, `Messenger`, `File` и `Auth/TokenResolverInterface` остаются здесь: они описывают технические возможности, а не правила заказа, покупки или доступа к приобретённым фотографиям.

Корневая `Contracts` — множественное число, рядом с `Application`, `Domain`, `Infrastructure`, `Presentation`, `Shared`. Это публичная граница предметных модулей, а не новый слой реализации. Например, `Contracts/Order/OrderReaderInterface.php`, `Contracts/Order/Dto/OrderOutputDto.php`, `Contracts/Payment/` — расположение будущих контрактов. Сам каталог не означает, что эти предметные сценарии уже реализованы.

Выбор определяется смыслом: техническая передача сообщения относится к `Application/Contract/Messenger`, событие конкретного заказа — к `Contracts/Order`. Загрузка файла — техническая возможность; право получить купленный оригинал — предметное правило. Внутренние интерфейсы репозитория, порты и DTO, которыми не пользуются другие модули, остаются в `Domain`/`Application` своего модуля.

В обоих каталогах находятся только публичные интерфейсы и необходимые для их границы DTO/события; реализация и DI принадлежат поставщику. Контракт не экспортирует ORM/Result или внутренний ReadModel и не содержит SQL, адаптеры или UseCase. Потребитель зависит от контракта, а не от внутренних классов поставщика. Auth разрешает пользователя; право доступа к объекту проверяет владелец сценария.

ServiceLocator разрешён только в DI/bootstrap. Сервисы без изменяемого состояния получают зависимости через конструктор. Для interface-key с ручной сборкой в Bitrix применяется `constructor`; для concrete-key — `className + constructorParams`. Не создавать входной интерфейс на каждый UseCase без необходимости.

## Основание

Правила сверены с текущими главами 07, 06 архитектурного руководства и главой 13 правил кода соседней Orteka. У Orteka допустимы некоторые малые коллекции с поведением сущностей; пользователь задал для нового чтения RaBit API более строгое правило. Предметные модули и namespaces Orteka сюда не переносятся.
