# Аудит основы RaBit API и плана MoreFoto

Дата: 11.09.2026. Это аудит исходников и локальных контрактов; HTTP, БД, доставка почты и production не проверялись.

## Результат

Старая P2P-реализация заменена основой из `rebit.share` и `rebit.auth` с приёмом заявок с сайта в `rebit.notification` и самостоятельной действующей лидогенерацией `rebit.leadhunter`. Удалены старый frontend и четыре торговых модуля (`bybit`, `exchange`, `identity`, `wallet`), их Composer-регистрации, bootstrap, маршруты, очереди, cron и торговые контракты Share. Технические `rebit.dev` и Sprint Migration сохранены.

По уточнению пользователя LeadHunter восстановлен после ошибочного отнесения к P2P. Он получает внешние заявки из RSS fl.ru, фильтрует их и доставляет в Telegram через Share с резервным email при настройке `REBIT_LEADHUNTER_FALLBACK_EMAIL`. Восстановлены модуль и его подключения, конфигурация cron и две миграции LeadHunter. После отдельного уточнения пользователя восстановлена ветка заявок с сайта Notification: публичный `/api/v1/lead`, синхронный Telegram и условный email fallback. Торговая ветка и её consumer исключены. История миграций остаётся на месте, а default-набор содержит семь миграций Auth/Audit/LeadHunter/Notification. База данных не менялась.

Проект, сборка, Compose и CI называются RaBit API / `rabit-api`. Рабочая директория и существующие домены, сертификаты и имена секретов остаются совместимыми с текущим окружением. Новое Compose project name использует другое пространство имён томов; при будущем переходе нужно отдельно выбрать/перенести данные.

[Документация MoreFoto](../../MoreFoto/docs/05-rest-api/README.md) сохраняет исходные 97 контрактов и 11 будущих продуктовых модулей. Общий инвентарь дополнен SHR-01 и NTF-01 до 99 операций; это существующие платформенные маршруты, а не новые продуктовые требования. Владельцы маршрутов и файлы routes.php сверяются генератором. Будущие роли, права, ресурсы и сессии не объявляются готовыми по наличию общего Auth. В текущей основе шесть HTTP-маршрутов; `/api/v1/lead` не расширяет продуктовый реестр MoreFoto.

Правила SQL/ORM с Result, узкого ReadModel, общих контрактов и DI сверены с актуальной документацией Orteka. Для нового чтения действует прямое указание пользователя: без Objectify-коллекций; сложный SQL либо ORM с массивными строками из Result. Инструкции проекта и скиллы приведены к этому профилю.

## Уточнение плана после аудита

[План MoreFoto](../../MoreFoto/docs/04-bitrix-modules/backend-waves.md) разбит на **35 последовательных волн W00–W34**: основа/безопасность, бизнес и схема, отдельные продуктовые ответственности, затем сквозная приёмка. В каждой указаны владельцы, зависимости, первичные REST-ID, повторные проверки и критерии подключения. Ориентир 3–4 тысячи строк используется для удобства ревью, без жёсткой квоты.

Добавлены платформенные SHR-01 и NTF-01; новая [коллекция Postman по волнам](../../MoreFoto/docs/05-rest-api/postman/MoreFoto.backend-waves.postman_collection.json) использует те же 99 запросов, что коллекция по модулям. Тела и статусы прежних 97 контрактов сохранены. Notification проектируется как внутренний исполнитель доставки чеков/файлов в W20/W21/W26; REST остаётся у Payments/Files. Публичный inbox и торговые обработчики не добавляются.

Дополнительные находки исходников при сверке текущих REST:

- **W03:** `rebit.share/lib/Infrastructure/Controller/Request/RequestFileToDtoMapper.php:142` и `Infrastructure/Helpers/ValidationHelper.php:20` вызывают `enableAnnotationMapping()`, которого нет в установленном `Symfony\Component\Validator\ValidatorBuilder` (имеется `enableAttributeMapping()`). Проверить реальные пути вызова и исправить валидацию; наличие Router не доказывает успешный upload. `InvalidFileException` не наследует HTTP-исключение, поэтому негативные сценарии требуют проверки кода ответа.
- **W04:** `api/docker/common/nginx/conf.d/default.conf:16` не включает PATCH в `Access-Control-Allow-Methods`. В продуктовой карте есть PATCH; нужно проверить CORS/OPTIONS через реальный путь frontend→proxy→API до подключения редакторов.
- **NTF-01:** поле `source` проходит вход, но сейчас не передаётся в сообщение; `accepted=true` не подтверждает доставку вложения, а заполненный honeypot `company` даёт тихий успех без доставки. Эти ограничения описаны в инвентаре, не скрыты общим обещанием уведомлений.

Изменены документы, генераторы и офлайн-проверки. PHP, nginx, БД и действующая доставка в этой плановой задаче не менялись. Проверки артефактов и их контрольные суммы — в [verification.json](../../MoreFoto/docs/05-rest-api/verification.json); прежние результаты PHPUnit ниже относятся к восстановлению основы.

Проверено 11.09.2026 по исходникам до удаления: `source-before-extraction.tar.gz` из `/tmp/rabit-api-extraction-20260911-uyuq9gdv/`; удалённые контракты Share сверены с `/tmp/morefoto-share-before-extraction-20260911.tar.gz`. Ниже сохранён анализ до возврата модуля; описания отсутствующего маршрута и рекомендации относятся к тому снимку. Теперь ветка Lead восстановлена в описанном выше объёме. ### Фактические зависимости и ограничения

- `include.php:7` требует только `rebit.share`. Прямых импортов Exchange, Bybit, Wallet или Identity внутри Notification не обнаружено. Два торговых обработчика Exchange использовали общий publisher как потребители, а не предоставляли зависимость модулю Notification.
- Текущий LeadHunter ищет внешние заявки и напрямую вызывает собственный HuntNotifier с общим Telegram-клиентом Share. Он не вызывает Notification. Общие chat ID и fallback email в окружении не делают модули зависимыми друг от друга.
- Заявки с сайта и найденные заявки — разные входы. Восстановление LeadHunter не вернуло `/api/v1/lead`; в текущем RaBit API по-прежнему зарегистрированы пять маршрутов Auth/Share.
- Telegram для Lead уже реализован, но Telegram-канал общей очереди в `di/notification.php:45` только закомментирован. Нельзя считать всю очередь готовой многоканальной системой.
- Общий SendNotificationDto требует userId и скалярный payload. Заявка для заданного Telegram-чата с файлом имеет другой контракт; перенос обоих Lead-потоков в старый DTO не является простой заменой.
- Handler неизвестного типа или типа без канала только пишет лог и возвращается (`SendNotificationMessageHandler.php:32–40,72–77`). Поэтому удаление торговых enum-кейсов и включение прежнего consumer не создаст работающий общий сервис. Для обязательных уведомлений нужно явно определить поддерживаемые типы и поведение ошибки.
- В рассмотренной реализации нет готового пользовательского inbox, предпочтений доставки и истории прочтения; наличие старых миграций Notification/NotificationPreference не подтверждает эти возможности.

### Рекомендуемое решение

1. Вернуть `rebit.notification` отдельным модулем RaBit API и восстановить существующую ветку заявок с сайта с Telegram/условным email fallback. Для этой ветки RabbitMQ consumer не нужен. При возврате необходимо согласовать Composer, DI/bootstrap, центральный реестр маршрутов, настройки формы и почтовую миграцию `Version20260820120001`.
2. Исключить торговые типы, шаблоны, payload и команды/тесты торговых примеров. Не восстанавливать биржевые модули ради Notification.
3. Общую асинхронную отправку подключать под конкретные события и получателей RaBit API/MoreFoto, с поддерживаемыми каналами и проверкой ошибок. До этого не включать consumer без действующих типов. Общие Messenger-примитивы уже находятся в Share.
4. Сохранить границы: Share — технические клиенты и общие контракты; Notification — доставка, форматирование и резервные каналы; LeadHunter — поиск, фильтры и дедупликация внешних лидов; Auth — аутентификация. Вызов общей доставки из LeadHunter можно унифицировать позже через подходящий контракт, без изменения его рабочего поведения при восстановлении.

Lead intake — сценарий лидогенерации, а не универсальная транспортная функция. На текущем объёме его можно сохранить внутри Notification для восстановления существующего API. Выделять ещё один модуль только ради архитектурной симметрии сейчас не требуется.
