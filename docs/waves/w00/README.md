# W00 — исходная основа и контракты

Статус: **подготовка к ревью**, не принята. Ветка `codex/w00-foundation-inventory`; целевая ветка `main`. Реализация W01 и продуктовых MoreFoto-модулей не входит в этот PR.

## Результат и границы

Создан самостоятельный репозиторий RaBit API с чистой историей. В него перенесена текущая основа Share/Auth/Notification/LeadHunter и технические rebit.dev/Sprint Migration. Импорт сохраняет поведение работающих заявок и не запускает миграции, внешние отправки или deployment. README описывает универсальную платформу; MoreFoto обозначен отдельным продуктом.

В первом PR присутствует существующий код платформы, а не только новые строки волны: до него main содержит пустой технический root-коммит. Для ревью нового кода в первую очередь смотреть два verifier, workflow, правила PR, README и этот пакет. Полный импорт остаётся в diff. `source-import.json` перечисляет SHA-256 исходных файлов до адаптации документации/CI, исходный commit старого checkout и пропущенные архивные пути. Он не является утверждением, что все файлы уже существовали в исходном commit: перенос включает ранее подготовленные незакоммиченные изменения.

Старый frontend, торговые модули, исторические P2P-миграции и benchmark не перенесены. Архивный checkout остаётся исходной копией. Сохранены семь активных foundation-версий и имя таблицы истории `sprint_migration_versions`; существующие БД не очищались и не преобразовывались.

## Контракты платформы

[HTTP API](../../api.md) описывает фактические поля/ошибки Auth, Share upload и Lead. Технический upload сохраняет завершающий `/`. `company` у NTF-01 — honeypot; `accepted=true` не гарантирует доставку вложения; `source` сейчас не выбирает адресата. LeadHunter имеет CLI-вход, а INF-01 относится к frontend nginx, не к Bitrix.

Две платформенные операции в обеих коллекциях заблокированы по умолчанию. Снимок — средство ревью, **не сценарий Run collection**: регистрационные AUTH-03/04 способны отправлять письма и менять учётные записи. Не запускать всю папку W00. В этой волне Postman-скрипты и HTTP-запросы не выполняются.

## Воспроизводимые проверки

Из корня, Python 3 без внешних библиотек:

```sh
python3 tools/verify-w00-inventory.py
```

Проверяются уникальность/покрытие 99 ID, method/path, 15 модульных папок, 35 волн, первичная и повторная проверка, совпадение запросов двух коллекций и четыре блокирующих platform guard. Результат не заменяет live API или исполнение JavaScript Postman. Историческая сохранность тел контрактов ограничена хешами зафиксированного снимка; исходный frontend не импортируется.

При подготовленном лицензированном ядре Bitrix в `api/public/bitrix/`:

```sh
php api/tools/verify-w00-router.php
```

Verifier загружает пять настоящих классов Bitrix Router, проверяет эффективную конфигурацию, точные шесть method/path/controller/action, дубли и компиляцию маршрутов, активный конфиг и семь имён миграций. Контроллеры, prolog, DI, БД и сами миграции не выполняются. В чистом GitHub runner ядра нет, поэтому этот шаг доказывается локальным отчётом отдельно от CI.

PHP-проверки из `api/`: `composer lint`, `composer cs-check`, `composer phpstan`, `composer test`. Новые инструменты дополнительно проверяются lint/CS. Отчёты текущего запуска собраны в `verification/`; негативные fixtures подтвердили отказ при повреждении method/route/migration config и снимков Postman.

## CI и production

Первый workflow содержит только api-checks и inventory-checks, permissions `contents: read`. Автоматические build/push/deploy из старого проекта не включены: новый GitHub не должен менять работающие пути/тома при первом merge. Воспроизводимый выпуск — отдельная ответственность W04. В `.dockerignore` добавлено исключение локальных dotenv, чтобы они не попадали в стандартный build context.

Рабочий production уже зафиксирован [отчётом 11.09.2026](../../deployments/2026-09-11-rabit-api.md), включая снимок исходников и backup/rollback. Это доказательство предыдущего выпуска, а не новый deployment W00. Для инвентаризации не отправлялись тестовые заявки и не применялись миграции.

## Приёмка и следующая волна

После review и успешных обязательных checks W00 можно принять. Включать продуктовые экраны frontend пока нельзя. Следующий самостоятельный PR W01 закрывает HTTP-логирование; затем W02–W04 устраняют ограничения основы. Утверждение бизнеса/схемы W05 предшествует продуктовым сценариям.

Откат W00 до merge — закрытие PR. После merge — отдельный revert PR; этот выпуск не требует отката БД. Архивный репозиторий, текущий сайт и production-конфигурация при подготовке W00 не меняются.

## Замечание вне границ W00

В выводе unit-тестов сохраняется предупреждение существующего кеша метаданных DTO: DtoClassMetadata/DtoParameterMetadata не readonly и не объявляют `__clone`. Тесты проходят; W00 не меняет эту реализацию. Сообщение сохранено в checks.json для отдельного разбора, без объявления исправленным.

## Конфигурация Basic Auth

При переносе обнаружен непустой `.htpasswd` со старым APR1-хешем. Он заменён пустым placeholder в новом репозитории; исходное значение не публикуется. Новые сборки не содержат встроенной учётной записи Basic Auth: перед их выпуском защищённые nginx-зоны требуют runtime-файла с учётными данными. Этот шаг относится к W04; первый PR не развёртывается на production. Старый хеш мог уже находиться в прежней публичной истории — его применимость к текущему доступу и ротация требуют отдельной проверки. Рабочая конфигурация сервера W00 не менялась.

Проверка whitespace выполнена для новых и адаптированных файлов W00. Полный импорт содержит прежние trailing whitespace/пустые строки в шаблонах Bitrix и поставляемом Sprint Migration; они не переформатировались ради переноса. PHP-CS-Fixer прикладного кода и нового verifier проходит.
