# План подключения бэкенда MoreFoto по волнам

Дата: **11 сентября 2026 года**. Сервер — **RaBit API**. Статус: **план реализации, 35 последовательных волн W00–W34; ни одна волна этим документом не объявлена выполненной**. R17 и D01–D12 сохраняют свой фактический статус. Работающие Lead/LeadHunter сохранены; продуктовые morefoto.* ещё не подключены.

[Карта модулей и правила](README.md) · [REST-контракты](../05-rest-api/README.md) · [Postman по волнам](../05-rest-api/postman/MoreFoto.backend-waves.postman_collection.json) · [Postman по модулям](../05-rest-api/postman/MoreFoto.postman_collection.json) · [Решения D01–D12](../frontend/business-review/decisions.md).

## Как работать по этому плану

Одна волна — одна проверяемая ответственность, обычно один PR. Внутри неё вместе идут нужные таблицы/индексы и миграции, Repository, UseCase/DTO, DI/routes, тесты и описание поведения. Не выносить все DTO, все миграции или все тесты отдельными техническими выпусками: ревьюер должен увидеть работающий сценарий целиком.

Порядок последовательный: следующая волна принимается после предыдущей и её указанных зависимостей. Сначала W00–W04 исправляют проверенные ограничения существующей основы; W05 фиксирует бизнес/домен/схему; W06–W33 добавляют продуктовые сценарии; W34 проверяет весь путь. Новую разработку MoreFoto не начинать до бизнес-проверки R17. Неподтверждённое решение блокирует зависимую часть, а не подменяется значением мока.

**Ориентир 3–4 тысячи строк — сигнал проверить размер, не квота.** Считать прежде всего рукописный production-код, миграции и значимые тесты. Генерируемые коллекции/реестры, lock-файлы и форматирование учитывать отдельно при оценке ревью, но не прятать из diff. Маленькую волну не раздувать. Если два независимых предмета или слишком большой diff — заранее разделить её на A/B, указать новую зависимость и обновить JSON/карты. ID остальных волн не сдвигать. Например, W10 может разделиться на приём оригинала и обработку превью; MED-03 считается готовым после обоих. W19 (платёжная надёжность) и W20 (транспорт) также требуют проверки размера до кодирования, но не дробления по папкам.

### Реализация, проверка и подключение — разные отметки

- `implementationWave` в реестре/Postman — где реализуется основная ответственность endpoint. Для существующих методов это инвентаризация или исправление, не разработка заново.
- `verificationWaves` — где его нужно повторно проверить после появления смежных владельцев данных. Это не обратная зависимость реализации.
- **Подключение** в карточке волны — допустимый уровень использования: изолированный стенд, готовый сценарий frontend или финальный допуск к внешним эффектам. Наличие метода/пути не означает готовность полного ответа.

Реальные `unpaid`, `not-started`, отсутствие назначения и пустой список допустимы для соответствующего состояния данных. Если обязательное поле ещё нельзя получить от его владельца, контракт остаётся неподключённым; `0`, `null`, `{}` или `[]` не маскируют отсутствующий модуль. Финальные карточки заказа/обращения и сводки завершаются в W33. Для каждого переключаемого экрана проверить весь набор его запросов, запись и последующее чтение; не смешивать реальные изменения со скрытым fallback на моки.

Волны Postman — навигация для ревью, **не сценарий автоматического Run collection**. Внутри папки порядок ID не определяет последовательность действий и тестовые данные. Настраивать отдельный стенд/окружение, выбирать необходимые запросы вручную. SHR-01/NTF-01 блокируются по умолчанию через `allow_platform_requests`; явное разрешение нужно только для осознанной проверки upload/заявки на тестовом адресате. Offline-валидаторы не отправляют HTTP и не подтверждают работу PHP/БД/Telegram.

## Notification в MoreFoto и карте API

Общий реестр содержит **99 операций: исходные 97 плюс 2 платформенных**. Из исходных 97: 89 проектных операций MoreFoto, 3 эскиза webhook, 2 используемых Auth, 2 унаследованных регистрации и 1 frontend health. Добавлены только существующие **SHR-01 POST /share/file/upload/** и **NTF-01 POST /lead**; префикс backend `/api/v1`. Эти методы не становятся продуктовыми требованиями MoreFoto. Наличие исходников отмечается отдельно от live-проверки. LeadHunter HTTP-методов не добавляет.

| Сценарий | REST-владелец | Роль Notification |
| --- | --- | --- |
| Заявка с внешнего сайта | rebit.notification, NTF-01 | Существующая синхронная доставка в Telegram, условный email fallback |
| Чек и повтор его отправки | morefoto.payments, PAY-04–PAY-06/PAY-09 | W20/W21: исполнение доставки; фискальный факт остаётся Payments |
| Письмо с файлами и восстановление | morefoto.files, FIL-05–FIL-08 | W26/W27: доставка; право/срок оригинала остаётся Files |
| Ответ куратора | morefoto.support, SUP-05 | Только если выбран внешний канал; хранение ответа уже самостоятельный сценарий |
| Передача ссылки / партии | Handoff / Shipping | HND-04 и SHP-04 записывают ручной/физический факт, не подразумевают отправку |

Не добавлять вымышленные `/notifications`, inbox, настройки каналов или просмотр прочтений. Старые торговые enum/очередь не возвращаются. Для нового транспорта проверить поддерживаемые каналы, повтор/дедупликацию, неизвестный исход и разницу между принятием транспортом и доставкой. W20 не переписывает действующие Lead/LeadHunter в универсальную очередь.

| Находка исходников | Волна | Чем доказать исправление |

## Общий пакет ревью каждой волны

1. Конкретный результат и граница: что теперь делает пользователь/система, какие инварианты сохраняются; ссылка на закрытые решения D и актуальную domain/database-спецификацию.
2. Миграции/индексы/уникальность/версии и владелец записи. Репозиторий читает SQL/ORM Result как массивы; новый код не гидрирует Objectify-коллекции. ReadModel не выходит за непосредственный маппер в API/контракт/кеш.
3. Method/path/action/RequestDto/InputDto/OutputDto, роль/область всех ID, DI и эффективный router. Контракт между модулями — `rebit.share/lib/Application/Contract/`; interface-key с ручной сборкой — `constructor`. ServiceLocator только bootstrap/DI.
4. Значимые проверки: happy path, запрещённая роль/чужой ID, неверные поля, stale version, повтор/гонка, сбой зависимости и восстановление — по применимости. Для денег проверять реальную транзакционную БД, для файла реальное ограничение доступа, для HTTP реальные mapper/proxy. Не ограничиваться тестами, повторяющими реализацию.
5. Проверки изменённого PHP и требуемые проверки репозитория, миграции на тестовой БД, генерация/валидация карты/Postman. Без массового форматирования постороннего кода.
6. Доказательство выхода: выполненные команды и результаты, оставшиеся ограничения, путь отката/включения и список целых frontend-сценариев, которые можно подключить. Offline fixtures отдельно от живого HTTP и доставки.

Если волна требует открытого решения, её подготовленная схема/контракт остаётся проектом до подтверждения. Дополнительный scope оформляется отдельной волной, а не дописывается в уже принятую незаметно. Для W34 все необходимые продукту решения должны быть подтверждены; визуальная приёмка D01 не задаёт автоматически серверные правила.

## W00. Зафиксировать исходный состав и контракты

Есть воспроизводимая точка отсчёта; исходники отделены от проверки работающего HTTP.

**Владельцы:** `rebit.share`, `rebit.auth`, `rebit.notification`, `rebit.leadhunter`, `platform.nginx`.
**После:** начало плана. **Решения:** нет новых бизнес-решений.
**Первичные REST:** AUTH-03, AUTH-04, NTF-01, INF-01.

**Входит в волну:**

- Инвентаризировать четыре прикладных и два технических модуля, шесть POST в rabit-api.php, bootstrap, Composer, DI и семь активных миграций foundation.
- Сохранить исходные 97 строк карты; добавить SHR-01 и NTF-01. Унаследованная регистрация не используется покупателем MoreFoto. LeadHunter — CLI/cron без REST; INF-01 — frontend nginx.
- Сверить scalar/file поля и ошибки действующих методов. NTF-01: company — honeypot; accepted не гарантирует вложение; source сейчас не управляет получателем.

**Предмет ревью:**

- Сравнение с реальным Bitrix Router без выполнения контроллеров; не включены торговые модули/consumer.
- Postman — ручной выбор сценария; platform-запросы заблокированы по умолчанию.

**Доказательство готовности:**

- Зафиксированы commit/diff, версии и результаты исходных тестов, а не результаты прежнего запуска.
- Все 99 ID уникальны; шесть серверных маршрутов сопоставлены с исходниками; сделана резервная копия.

**Подключение:** Сохранить действующие Lead/LeadHunter. Никаких реальных сообщений или миграций ради инвентаризации.

## W01. Убрать секреты из HTTP-логов

Запрос, ответ и ошибка логируются без паролей, кодов, Bearer и capability-ключей.

**Владельцы:** `rebit.share`.
**После:** W00. **Решения:** нет новых бизнес-решений.
**Первичные REST:** нет новых REST.
**Повторная проверка:** AUTH-03, AUTH-04, NTF-01.

**Входит в волну:**

- Исправить LoggerFilter и путь записи исключений: маскировать вложенные поля, заголовки, URL и ответы до передачи логгеру.
- Оставить correlation ID, операцию, длительность и безопасный код результата; исключить тела файлов и полные контакты.

**Предмет ревью:**

- Секрет не попадает в лог при ошибке валидации/сериализации; одна политика вместо копий по контроллерам.

**Доказательство готовности:**

## W20. Общая надёжная доставка Notification

**Входит в волну:**

**После:** W10, W18, W24, W28. **Решения:** D06, D10, D12.

**Входит в волну:**

## W34. Сквозная приёмка и управляемое включение

Подтверждена готовность функций и известны восстановление, включение и пределы гарантий.

**Первичные REST:** нет новых REST.
**Повторная проверка:** все 99 операций реестра, с разделением platform/frontend/product.

**Входит в волну:**

- Все роли: учреждение→съёмка→фото→ссылка→заказ→оплата→чек/файлы→исправление/возврат→печать→передача.
- Пересобрать Postman/реестр, сверить фактические method/path/action/DTO/DI и точные интеграции; выбранные живые запросы на тестовом backend.

**Подключение:** После приёмки можно согласовать production-выпуск. Сам запуск не входит в подготовку этого плана.

## Поддержание плана

Единый источник очереди, зависимостей и соответствия ID — [backend-waves.json](backend-waves.json). Тела HTTP-контрактов остаются в [build.py](../05-rest-api/build.py). Этот Markdown строится [render-waves.py](render-waves.py); сначала изменить JSON, затем выполнить из корня MoreFoto:

```sh
python3 docs/04-bitrix-modules/render-waves.py
python3 docs/05-rest-api/build.py
python3 docs/05-rest-api/validate.py
node docs/05-rest-api/validate-postman.cjs
```

Вторая коллекция содержит те же запросы и тесты, что основная, сгруппированные по implementationWave. Волны без REST представлены описанием; повторные проверки перечислены в карточках, не дублируют запросы. Проверки требуют 99 уникальных ID, ровно одну первичную волну на каждый, существующие зависимости без циклов и соответствие коллекций. Команды не подтверждают live-интеграцию.
