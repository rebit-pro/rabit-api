# ORG-04 — предложение обязательного summary

**Статус: контрактная форма принята пользователем 11 сентября 2026 года для реализации.** Сейчас `GET /institutions/{institution_id}` в канонической карте обещает обязательные shoots, groups и summary без формы последнего. Финансовый поставщик и D06 ещё не готовы. Произвольные `{}`, null или нулевые суммы скрыли бы отсутствие реализации.

Предлагается обязательный discriminated union. Поле называется summary в обоих случаях; вариант определяется availability. Это изменение формы канонического контракта, а не уже существующий ответ API.

```typescript
type InstitutionSummary =
  | { availability: 'unavailable'; reason: 'dependenciesNotReady' }
  | {
      availability: 'ready';
      currency: 'RUB';
      paidOrderCount: number;
      paidAmount: number;
      confirmedRefundAmount: number;
      pendingRefundAmount: number;
      netAmount: number;
      calculatedAt: string;
    };
```

Все суммы — неотрицательные целые копейки; count — неотрицательное целое; calculatedAt — ISO 8601 с часовым поясом, момент согласованного расчёта. Поля двух вариантов не смешиваются. `netAmount = paidAmount - confirmedRefundAmount`; pendingRefundAmount выводится отдельно и не уменьшает netAmount до подтверждения. Ограничение подтверждённых/ожидающих возвратов проверяет Settlement по исходным платежам и резервам, не Organization.

**D06 принят как рабочее правило:** paidOrderCount считает заказы с подтверждённой оплатой, включая полностью возвращённые; это рабочая семантика принятого предложения. ready возможен после реализации всех поставщиков. Неизвестный платёж не считается paid.

## Источник и область

Один summary относится к одному institutionId: все его съёмки/группы, включая staff, за весь срок; учитываются только реальные подтверждённые факты. Это предлагаемый охват без несуществующего фильтра периода. Если бизнесу нужна текущая съёмка/период, согласовать query и определение показателей до подключения.

Organization проверяет доступ, затем вызывает узкий контракт Settlement, который получает факты из Commerce/Payments. Organization не читает их таблицы и не суммирует frontend-моки. Агрегат вычисляется согласованным снимком/версией поставщика, не несколькими несвязанными запросами. calculatedAt не доказывает транзакционную согласованность сам по себе.

Organizer/curator/head получают допустимый summary; head — только агрегаты, без контактов, позиций, ключей или индивидуальных заказов. Teacher не имеет ORG-04; его групповая проекция денег не содержит. Пустая разрешённая финансовая выборка при **работающем** поставщике даёт ready с настоящими нулями. До поставщика — unavailable, сбоивший поставщик — ошибка HTTP, а не unavailable или нули.

## Этапы подключения

| Этап | Предлагаемое поведение |
| --- | --- |
| W07 до структуры W08 | ORG-03/05 и список могут быть готовы. У полного ORG-04 ещё нет поставщика shoots/groups: не отдавать пустые массивы-заглушки. Возвращать 503 с согласованной dependency-not-ready ошибкой или не подключать endpoint до W08; рекомендуемый вариант — явный 503 в тестовой среде |
| После W08, до Settlement/W33 | Если согласован этот union: реальные shoots/groups, summary unavailable. Ограниченно подключать только готовый редактор, интерфейс явно сообщает «Сводка пока недоступна» |
| После D06 и всех зависимостей, W33 | Реальные shoots/groups и summary ready; полный ролевой сценарий на интеграционном стенде |
| Сбой уже подключённого поставщика | Без успешного неполного 200: 503 по общей политике API; лог с correlation ID без чувствительных данных |

Принят вариант union: после W08 разрешена ограниченная карточка с явной недоступностью финансовой сводки, полный ready — после поставщика в W33. Не откладывать готовые редакторы ради финансовых разделов.

Для shoots/groups предлагаются две независимо перелистываемые выборки: query `shootsPage` и `groupsPage` от 1, общий `pageSize` от 1 до 100 (по умолчанию 50). Каждое поле имеет форму `{items, meta: {page, pageSize, total}}`; стабильная сортировка createdAt DESC, ID DESC. groups содержит группы всех съёмок этого учреждения, каждая с shootId; фильтр учреждения/области применяется до LIMIT. summary остаётся итогом всего учреждения и не зависит от страницы. Это принятая дельта ORG-04: исходная карта не обещает такую query/форму. Обновить build.py, Postman и затем потребителя в его волне; не возвращать усечённый массив без meta. Вложенные списки других карточек проверить отдельно в их волнах.

## Примеры данных для ревью

Поставщик ещё не подключён:

```json
{"availability":"unavailable","reason":"dependenciesNotReady"}
```

Поставщик подключён, есть подтверждённые факты; пример синтетический:

```json
{"availability":"ready","currency":"RUB","paidOrderCount":3,"paidAmount":150000,"confirmedRefundAmount":25000,"pendingRefundAmount":10000,"netAmount":125000,"calculatedAt":"2026-09-11T14:30:00+03:00"}
```

Проверка будущего API: оба варианта; реальные нули; runtime-сбой; неизвестный исход платежа; полный/частичный возврат после D06; равенство формулы; отказ teacher/чужому head; отсутствие контактов/ключей; согласованность общей суммы при конкурентном подтверждении возврата. В W05 проверяется только структура примеров, не работа endpoint.
