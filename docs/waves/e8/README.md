# E8 — заказ с email без ФИО и телефона

Ветка `codex/e8-email-only-checkout` от main `28a8c55` (merge D4, PR #175). Зависимости E5, G1 и E7 слиты, решения D07/D10 приняты. План и журнал: `docs/plans/E8_email-only-checkout/`. Требование R02 из плана владельца `docs/plans/OPS-telemos-feedback-plan/`.

Покупатель оформляет заказ по одному email. Имя и телефон форма не спрашивает, сервер их не хранит и не подменяет выдуманными значениями. Заказы, оформленные до E8, показывают свои имя и телефон как раньше. Комментарий заказа остаётся. Контакт для писем J2 и чеков G2 — email из заказа.

## Решения (12.10.2026)

- **E8-DEC-01.** Сервер игнорирует имя и телефон. COM-10 по-прежнему допускает поля `name` и `phone`: страница, открытая до выкладки, и восстановленная попытка не получают `UNKNOWN_FIELD`. Значения не проверяются и в заказ не попадают. `INVALID_BUYER_NAME` и `INVALID_BUYER_PHONE` больше не выдаются.
- **E8-DEC-02.** `BUYER_NAME` и `BUYER_PHONE` допускают `NULL`. Сохранённые значения проверяет прежнее правило E5, email обязателен.
- **E8-DEC-03.** Хеш повтора строится по прежнему кортежу из исходных значений тела. Повтор ключа попытки, начатой до выкладки, возвращает исходный заказ.
- **E8-DEC-04.** «Покупатель» и «Телефон» показываются, только если они есть. В списке сотрудника заказ без имени показан по email.
- **E8-DEC-05.** Демо-режим тоже без имени и телефона. Исправление контактов в демо-«расчётах» требует только email.

## Контракты

| Где | Изменение |
| --- | --- |
| `POST /api/v1/public/galleries/{token}/orders` (COM-10) | `buyer`: обязательны `email` и `reviewed`; `comment` и `receiptChannel` — как раньше; `name` и `phone` допустимы, но игнорируются |
| Ответы COM-10…13 | `buyer.name` и `buyer.phone` — `null` у заказов с E8, прежние значения у ранних заказов |
| Поиск сотрудника (COM-12) | Без изменений: по номеру, email и — для ранних заказов — имени и телефону |
| PAY-01 | Без изменений: контакты в оплату не передаются |

## Хранение и миграция

Миграция `20261012100001` одним `ALTER` делает `BUYER_NAME` и `BUYER_PHONE` `NULL`-допустимыми и пересоздаёт CHECK `ck_mf_order_values`. Остальные условия E5 переносятся дословно. Покупатель: `(BUYER_NAME IS NULL OR CHAR_LENGTH(TRIM(BUYER_NAME)) >= 2) AND BUYER_EMAIL <> '' AND (BUYER_PHONE IS NULL OR BUYER_PHONE REGEXP '^[+][0-9]{10,15}$')`. Исторические строки не меняются. Повторный `up()` безопасен. `down()` отказывает, если есть заказы без имени или телефона: E5-колонкам понадобились бы выдуманные значения.

## Выкладка и откат

1. Backend и точечно `migrate up 20261012100001` — одним окном. Старый frontend продолжает работать: он шлёт имя и телефон, сервер их игнорирует.
2. Затем frontend: форма без имени и телефона.

Откат: frontend, затем backend. Миграция `down()` возможна только до первого заказа без имени и телефона, после него схема E8 остаётся. Старый backend с такой схемой работает: его запись всегда содержит имя и телефон.

## Ограничения

- Кеш старой страницы может отправить имя и телефон ещё некоторое время — они отбрасываются.
- Каналы чека, фискализация и обязательные поля провайдера — G2. Письма покупателю — J2.
