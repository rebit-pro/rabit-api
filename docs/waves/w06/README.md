# W06 — Access: профиль и серверная проверка прав

Реализованный код: `api/public/local/modules/morefoto.access/`. Это первый предметный модуль MoreFoto; API Auth/Share продолжают работать. Ветка основана на main после merge W00–W05. GitHub Actions оставлен в состоянии disabled_manually; YAML не изменён.

## Поведение

- `GET /api/v1/me` принимает существующий Bearer Auth и возвращает `data: {id, name, email, role, active, accessRevision, permissions}`. Токен, пароль, внутренний ID профиля и чужие контакты в ответ не входят.
- 401 — отсутствующий, истёкший или отозванный Bearer / заблокированная Auth identity. 403 — отсутствующий или выключенный StaffProfile, неизвестная роль или запрещённое действие. Проверка прямого чужого ресурса через Access guard возвращает 404.
- Действия первого среза: `profile.read`, `staff.manage`, `institution.read`, `shoot.read`, `group.read`, `organization.manage`. Список permissions описывает полномочия и не означает, что все предметные endpoints уже реализованы.
- Organizer имеет проектную область. Curator/head/teacher с пустой областью получают только `profile.read`. Сохранённых назначений ещё нет; они появятся в W07–W09. Политика проверена на собственной/чужой области и отсутствии подтверждённой родительской цепочки.
- Межмодульный `Rebit\Share\Contracts\Access\AccessGuardInterface` — единый серверный вход проверки действия. Он перечитывает Auth и профиль при вызове. Идентификатор сотрудника берётся из проверенного Bearer, принадлежность ресурса — из БД владеющего модуля.

## Установка в тестовом окружении

1. Установить зависимости Composer с новым PSR-4 `Morefoto\Access\`; требуются PHP 8.4, MySQL 8, highloadblock, rebit.share и rebit.auth.
2. Выполнить активные foundation-миграции штатным Sprint Migration. Новая `Version20260911200001` создаёт настоящий HL `MfStaffProfile` и `mf_access_state`, затем устанавливает модуль. `b_user`, `b_uts_user` и обе таблицы Access должны использовать InnoDB.
3. После проверки выбранного существующего Auth user ID выполнить в `api/public`:

```sh
APP_ENV=test php local/bin/bitrix-console morefoto:access:bootstrap-organizer 123 --confirm-user-id=123
```

`123` — пример, его нужно заменить проверенным ID. Команда не создаёт учётную запись и не задаёт пароль. Она требует активную, не pending identity и пустой справочник сотрудников. Профиль + отзыв прежней сессии + версия AccessState коммитятся вместе. Для входа после назначения нужен новый login. Повтор той же команды — no-op; изменение другого профиля через bootstrap невозможно. Production и неизвестный APP_ENV отклоняются до обращения к сценарию.

Публичного bootstrap-маршрута нет. При откате кода данные сохраняются; down-миграция отказывает при существующих профилях или изменённой версии AccessState. Это не сценарий удаления рабочих сотрудников.

## Проверка

```sh
bash api/tools/run-w06-access-integration.sh
```

Runner использует отдельную временную MySQL и внутреннюю Docker-сеть, без host ports, project .env и рабочих данных. Пути read-only ядра/vendor и образы задаются существующими переменными `W02_KERNEL_ROOT`, `W02_VENDOR_ROOT`, `W02_PHP_IMAGE`, `W02_MYSQL_IMAGE`; совпадающие имена fixture-контейнера/сети вызывают отказ, а не переиспользование.

Стенд исполняет настоящий Bitrix Loader/DI, native HL install, миграцию, CUser, SQL/ORM, HTTP Request/Controller/BearerFilter и сериализатор. Запрос запускается через контроллер в CLI-контексте: полный prolog и nginx/FPM здесь не проверяются. Единственная подмена — управляемый сбой после настоящего отзыва токена для доказательства rollback.

Результаты сохранены рядом в `verification.json` и `integration.json`. Замороженный снимок W00 не менялся. Удалённый CI отключён по просьбе владельца; его отсутствие не выдаётся за успешный CI.
