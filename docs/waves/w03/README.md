# W03 — загрузка файлов и постоянный владелец

## Ответственность и порядок

Одна волна, одна ветка `codex/w03-upload-ownership`, один PR поверх W02. W03 закрывает техническую загрузку **SHR-01** и повторно проверяет скалярный DTO с необязательным вложением **NTF-01**. Новых REST-маршрутов и полей ответа нет. Frontend MoreFoto не подключается. [Снимок плана](../w00/snapshot/backend-waves.md) и Postman остаются исходным согласованным инвентарём; текущие изменения описаны здесь.

## Что изменилось

`RequestFileToDtoMapper` и `ValidationHelper` используют Symfony `enableAttributeMapping()` вместо удалённого `enableAnnotationMapping()`. Один файл берётся строго из поля `file`. `moduleId` обязателен в POST и должен соответствовать имени технического модуля: строчные латинские буквы, цифры, сегменты через точку, максимум 50 символов. Пример: `rebit.share`. Пути вроде `../private` отклоняются.

`TechnicalUploadValidator` проверяет штатный PHP upload, код ошибки, читаемость, фактический размер и MIME через `finfo`. Для технического файла принят предел **15 MiB**, включая граничный размер. Разрешены PDF, DOC/DOCX, XLS/XLSX, TXT, ZIP, PNG, JPEG, WEBP с соответствующими расширениями. SVG, PHP, пустой и незавершённый файл отклоняются. Имя превращается в basename, очищается от управляющих символов, ограничивается 120 символами. MIME из браузера и присланные `name/type/size/tmpName` не заменяют серверные метаданные.

Новый `UploadedFileOwnerRepository` читает через D7 `Query\Result` и `fetch()` массивной строки, без Objectify. Единственный потребитель превращает строку в `userId/moduleId`; курсор не попадает в кеш или HTTP. Ошибки БД преобразуются в предметный `FileUploadFailedException` с безопасным статическим сообщением.

Владелец записывается в `rebit_share_uploaded_file_owner` по уникальному `FILE_ID`. Запись неизменяема; повторный `FILE_ID` не меняет пользователя или модуль. `UploadedFileOwnershipService::isOwnedBy(fileId, userId, moduleId)` сверяет всю тройку. Неизвестный файл или старый файл без записи владельца получают отказ. При недоступной БД и отсутствии пригодного кеша проверка завершается ошибкой, а не разрешением.

ManagedCache ускоряет чтение неизменяемой записи. Новый префикс `rebit_share_upload_owner_v2_` не доверяет старым записям кеша. Очистка, повреждение или отказ кеша не стирают владельца и не мешают сохранению записи в БД. Если после `CFile::SaveFile` не удалось сохранить владельца, созданный файл удаляется через `CFile::Delete`, успешный ответ не возвращается.

## Сохранённый HTTP-контракт

- `POST /api/v1/share/file/upload/` — завершающий `/` сохранён. Требуется прежний Bearer token. Multipart: `moduleId` и один `file`. Результат загрузки сохраняет `id`, `name`, `size`, `type`, `src`.
- Невалидный файл отображается как **HTTP 400**: `{"data":[],"error":{"message":"Некорректный файл или параметры загрузки."}}`. Путь, исходный текст и цепочка исключений не выдаются, даже при `debug=true`. Ошибки параметров DTO также дают 400 с безопасным статическим сообщением. Ошибка хранения остаётся 500.
- `POST /api/v1/lead` сохраняет скалярный DTO и необязательный `file`; обработка отправки Telegram/email и значение `accepted` не меняются. HTTP fixture выполняет только mapper и валидатор вложения, не запускает отправителей.

`src` существующей технической загрузки остаётся публичным путём Bitrix. Проверка владельца предназначена для последующего безопасного использования идентификатора файла внутри сценария. Она не превращает публичный URL в закрытое хранилище. У проекта пока нет отдельного REST download/attach endpoint, в который можно подключить эту проверку. Приватные оригиналы, подписанные ссылки, квоты и жизненный цикл MoreFoto рассматриваются в последующих волнах; W03 не объявляет их готовыми.

## Карта ревью

| Область | Проверка |
| --- | --- |
| Mapper и `TechnicalUploadValidator` | Настоящий multipart, ровно один файл, действительный размер/MIME, допустимое имя и модуль |
| `ValidationHelper`, `JsonExceptionResponse` | Совместимость Symfony attributes; предсказуемый 400 без путей и текста внутренних исключений |
| Table / Repository / OwnershipService | `FILE_ID` уникален, владелец неизменяем, массивный Result read, отказ для чужого и неизвестного файла, кеш не единственное хранилище |
| `FileUploadService` | Отсутствие успешного результата без постоянной записи, очистка только что созданного CFile |
| Миграция `Version20260911130001` | Только foundation, без backfill старых файлов; повторный up; безопасный rollback |
| Проверки | HTTP fixture с реальными Bitrix/Symfony; ORM/MySQL и кеш в двух процессах; unit-регрессии текущих модулей |

## Воспроизведение

Лицензированное ядро и Composer vendor подключаются read-only, в Git не включаются. Требуется Docker и локальные образы PHP 8.4 / MySQL 8.0. Команды из корня checkout:

```sh
python3 tools/verify-w03-upload.py --kernel /path/to/bitrix --vendor /path/to/api/vendor
python3 tools/verify-w03-ownership.py --kernel /path/to/bitrix --vendor /path/to/api/vendor
python3 tools/verify-w00-inventory.py
```

Первый runner создаёт временный PHP container с `--network none`; curl исполняется внутри него по loopback. Нет host ports, БД или отправки сообщений. Проверяются 19 групп сценариев: корректные TXT/PDF и предел 15 MiB; поддельные поля и MIME; basename; missing/multi/extra/empty/oversize; некорректные moduleId и расширения; реальный JSON 400 при debug; Lead с вложением и без него.

Второй runner отказывается использовать существующие ресурсы `rabit-w03-tests` / `rabit-w03-mysql`, создаёт отдельную internal network и БД `rabit_w03` на tmpfs без host ports/постоянных volumes и удаляет их в `finally`. Фикстура не читает `.env`, рабочие `.settings.php` или production-конфигурацию. Используются реальные Bitrix ORM, соединение MySQL и файловый ManagedCache. Глобальный bootstrap приложения и загрузка установленных обработчиков отключены; пользовательские timezone options не читаются. Сначала проверяются запись, повторная миграция и запрет изменения владельца, затем второй PHP-процесс, удаление/повреждение/отказ кеша, чужой/неизвестный файл, недоступная таблица и отказ разрушительного rollback.

Команды из `api/` с локальными dependencies:

```sh
vendor/bin/phpunit --no-progress --do-not-cache-result
vendor/bin/phpstan analyse --configuration=phpstan.neon --no-progress
vendor/bin/phplint --no-cache
php tools/verify-w00-router.php
```

PHP CS Fixer запускается с `public/local/php-cs-fixer.php` только для изменённых PHP-файлов. Для старых файлов стабов изменены только требуемые сигнатуры `CFile::Delete`, без массового форматирования. Дополнительно W04 независимо проверена на исходниках W03 через nginx → реальный PHP-FPM: multipart и сохранение CORS; этот расширенный proxy-runner принадлежит PR W04.

Фактический локальный отчёт этой ветки: [verification.json](verification.json). Исходная независимая проверка W01 + W03: 99 тестов / 536 assertions. После переноса поверх W02 повторный полный gate — **132 теста / 622 assertions**, PHPStan, lint, полный CS, router6/migrations9 и inventory99 — PASS. Реальные HTTP19 и MySQL/ORM/cache в новом процессе повторно прошли на этом же объединённом коде. Отчёты: [integrated-verification](integrated-verification/). Родитель — W02, [PR #4](https://github.com/rebit-pro/rabit-api/pull/4).

## Подключение и откат

До включения нового PHP-релиза выполнить `Version20260911130001` через активный набор `migrations.foundation`; существующая таблица истории миграций сохраняется. Без таблицы загрузка должна завершаться ошибкой, а не создавать файл без владельца. Старым файлам владелец не назначается автоматически.

После ревью W03 можно включить в согласованный следующий deploy; сам deploy в эту волну не входит. При откате PHP таблицу владельцев сохранить. `down()` удаляет только пустую таблицу и явно отказывается удалять заполненную. Старый код при откате не запишет постоянного владельца новым файлам — такие загрузки будут считаться неизвестными после возврата W03. Для отката релиза следует приостановить загрузки или исправить проблему вперёд.

В тестах реальный `CFile::SaveFile/Delete` не обращается к продуктивному файловому хранилищу: orchestration и очистка проверены unit-двойником; ORM, миграция, кеш, HTTP upload и JSON error boundary проверены настоящими реализациями. Реальные контакты, рабочие загрузки и сообщения Telegram не использовались.
