# J5 — оригиналы фото вложениями в письме заказа

Ветка `codex/j5-order-email-attachments` от main `1a28aa7`. Зависимость J2 слита (PR #200). План и журнал: `docs/plans/J5_order-email-attachments/`. Волна добавлена в граф PR #207 (`docs/plans/OPS-waves-e9-j5/`).

После подтверждённой оплаты родитель получает на email заказа все оплаченные кадры оригиналами во вложениях: digital-кадры, подарок, копии печати J4. Кадры идут по порядку страницы заказа, при необходимости несколькими письмами «письмо k из n». В каждом письме есть ссылка на заказ (J2). Отправка включается общим флагом J2 `MOREFOTO_ORDER_EMAIL_ENABLED` после проверки #161.

## Решения (17.10.2026)

- **J5-DEC-01.** До 18 МБ (18 MiB) исходных байт вложений в письме — около двух кадров по 8 МБ, около 24 МБ после base64.
- **J5-DEC-02.** Кадр крупнее 18 МБ уходит отдельным письмом. Кадр выше 20 МБ (≈27 МБ после base64, лимит письма Яндекса 30 МБ) не прикладывается: письма называют его, а скачать его можно по ссылке.
- **J5-DEC-03.** «Отправить ещё раз» пересылает все письма. Ограничение J2 прежнее: раз в 10 минут, 5 раз в сутки.

| Кадров по 8 МБ | Писем |
| --- | --- |
| 1–2 | 1 |
| 3 | 2 |
| 10 | 5 |
| 30 (подарок) | 15 |

## Как устроено

1. **План писем.** `OrderEmailSender` при первой отправке берёт право заказа (`OrderFileAccess`). `AttachmentPlanner` раскладывает кадры по письмам. План записывается одной транзакцией:
   - `mf_file_delivery.LETTERS` и `LINK_ONLY` — число писем и кадры «только по ссылке»;
   - `mf_file_delivery_part` — состав каждого письма: кадр, имя, тип, байты, путь оригинала.

   Повтор и параллельная отправка находят уже записанный план.
2. **Постановка.** Каждое письмо ставится в H1 с ключом `order-email:<deliveryId>:<k>`. Постановка идёт по сохранённому плану, поэтому после падения между письмами повторяется только непоставленное. Когда поставлены все письма, доставка становится `queued`. `OPERATION_ID` хранит первое письмо — так статус видит и код J2 после отката.
3. **H1** хранит у операции только ссылки на файлы (`ATTACHMENTS`: имя, тип, путь, байты). В RabbitMQ уходит ID операции.
   - Предел вложений письма — `EmailNotificationInterface::MAX_ATTACHMENT_BYTES` = 20 MiB.
   - После `accepted`/`failed` тексты и список вложений очищаются.
4. **Транспорт** читает файл в момент отправки и сверяет размер. Пропавший или изменённый оригинал — отказ `attachment_unavailable`, H1 повторяет попытки, затем `failed`.
   - Если опция Bitrix `main.max_file_size` меньше вложений, Bitrix молча подменил бы фото текстовой заглушкой. Транспорт вместо этого отказывает с `attachment_limit`.
   - Вложения передаются через `CEvent::SendImmediate(..., filesContent:)` без `METHOD`: обычная часть `image/jpeg; name="…"`.

Память: Bitrix кодирует письмо целиком. Пик потребителя ограничен размером письма (18–20 МБ исходных байт), `memory_limit` 1024M.

## Контракт FIL-05/06 и сводка

`GET /api/v1/public/orders/current/file-deliveries`, `POST …` и `GET …/{id}` получили у доставки поля:

```json
{ "letters": 3, "acceptedLetters": 2, "photos": 5, "linkOnly": 0 }
```

- `status`:
  - `accepted` — все письма переданы почтовому серверу, `acceptedAt` — последнее из них;
  - `failed` — хотя бы одно письмо окончательно не ушло;
  - иначе `pending`; `cancelled` — как в J2.
- `letters` — писем по плану, `0`, пока план не записан.
- `photos` — кадров во вложениях, `linkOnly` — кадров только по ссылке.

## Frontend

Блок письма на странице заказа (`OrderEmailNotice.vue`, правила `order-email-rules.ts`):

- «Отправляем 10 фото на … — 5 писем.»;
- «Фото и ссылка на заказ отправлены на … — 5 писем, 10 фото. Если писем нет — проверьте папку «Спам».»;
- «Не удалось отправить 1 из 3 писем на …. Фото можно скачать на этой странице.»;
- «N фото больше 20 МБ — их можно скачать только на этой странице.»

Подсказка у email при оформлении (видна только при включённой отправке): «На этот адрес отправим фото и ссылку на заказ после оплаты».

## Выкладка

1. Миграция `20261017100001` точечно (`up 20261017100001`) — до backend.
2. Backend, включая `morefoto_stage_notification_consumer`, `notification_dispatcher` и `order_email_runner`. Потребитель уведомлений должен видеть оригиналы по тому же пути `/app/var/private/media/...`:
   - на stage все сервисы монтируют общий `runtime/var`;
   - в `docker-compose-production.yml` добавлен read-only mount `private-media`.
3. `MOREFOTO_ORDER_EMAIL_PART_BYTES` на stage не задавать: по умолчанию 18 MiB. Стенд E2E ставит 1 байт, чтобы получить письмо на каждый кадр.
4. Перед включением отправки (#161) — `main.max_file_size` (лимит вложений писем Bitrix): 0 или не меньше 28 000 000 байт. Кадр 20 МБ после base64 ≈ 27,96 МБ. На stage сейчас стоит 20 000 000 — значение Bitrix по умолчанию.

Откат: `docker service rollback` для backend. Миграция совместима с кодом J2: колонки и таблица не мешают, `OPERATION_ID` указывает первое письмо.

## Ручная проверка после #161 (J5-T15)

На контролируемых ящиках Яндекс, Mail.ru и Gmail:

1. Оплатить тестовый заказ из 3+ кадров, дождаться писем.
2. Письма пришли, не в «Спаме»; тема «письмо k из n»; вложения открываются.
3. На телефоне вложение сохраняется в галерею.
4. Ссылка в письме открывает заказ.
