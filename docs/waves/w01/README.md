# W01 — безопасные HTTP-логи

## Ответственность

Одна волна, одна ветка `codex/w01-safe-http-logs`, один pull request в `main`. Основа W00 принята в [PR #1](https://github.com/rebit-pro/rabit-api/pull/1), merge `a6b3eb20d6b812f6a5f7387ace71dace4e5acd66`. Новые продуктовые маршруты не добавляются. Повторно проверяем существующие AUTH-03, AUTH-04 и NTF-01 на уровне общего логирования и прежних тестов сценариев.

До W01 фильтр записывал весь запрос/ответ, общий процессор добавлял URI и User-Agent, HTTP-клиент сохранял тело и заголовки в DEBUG-буфере, а Bitrix отдельно печатал исключения. Секрет мог быть значением, именем неизвестного поля или частью сообщения исключения.

После W01 логи содержат ограниченный набор диагностических полей. Неизвестные поля и их имена отбрасываются вместе с вложенным содержимым. Тела запросов/ответов, заголовки, полные URL, контакты, вложения, тексты исключений и trace arguments не записываются. Это сознательное ограничение диагностики: списка имён вроде `password` недостаточно для неизвестных полей и отражённых ответов интеграций.

## Карта ревью

| Часть | Что проверять |
| --- | --- |
| `LogSanitizer` | Единственная политика: фиксированные события и типизированные метаданные, ограниченные строки, фиксированное число lookup, без рекурсии и преобразования объектов |
| `LoggerFilter` | Читает только метод, controller/action и HTTP status; не разбирает запрос и не сериализует ответ; `extraData` проходит ту же политику |
| `AbstractController` | Ошибка получает запись `HTTP_EXCEPTION` после построения итогового ответа, с фактическим HTTP status и тем же requestId |
| `RebitHttpClient`, `TelegramBotApiClient` | Исходные запросы отправляются как прежде; логгер получает только диагностические значения, в том числе при ошибке и сбросе DEBUG-буфера |
| `CommonLoggerProcessor`, `Log`, `HttpDebugLoggerFactory` | Последний обязательный процессор перед handlers защищает stdout, Logstash и fallback-конфигурацию; сырой URI/IP/User-Agent не добавляются; HTTP-буфер сохраняет порядок processors |
| `SafeExceptionHandlerLog`, ранний bootstrap | Работает до Composer/DI/модулей, использует штатные блокировку и ротацию Bitrix; исключает стандартный formatter с Host/URI/trace |
| Тесты и `api/tools/verify-w01-*.php` | Проверяют готовые записи, независимый PSR-логгер, реальное ядро и отдельный файл исключений |

## Правила дальнейшего использования

- В `context` передаются метаданные, вычисленные приложением. Запрос, DTO пользователя, payload интеграции и результат контроллера нельзя передавать туда как набор разрешённых полей.
- `operation`, `controller`, `class`, `file`, `dependency`, `parameter` — доверенные имена кода, ограниченные форматом и длиной 200 байт. Формат не делает произвольную пользовательскую строку безопасной.
- `method`, `result`, `source` имеют фиксированные допустимые значения; HTTP status — целое 100–599. Счётчики и код исключения — целые. Длительность — конечное неотрицательное число миллисекунд с начала PHP-запроса.
- `requestId` создаётся сервером, общий для запроса и файла исключений; заголовок клиента не используется. В CLI он соответствует одному процессу.
- Текст события должен быть статичным и присутствовать в `LogSanitizer::MESSAGES`. Неизвестный текст заменяется на `[REDACTED]`; новые события добавляются в общей политике при ревью.
- Исключение сохраняет только класс, basename файла, строку и числовой код. Для диагностики используются эти поля вместе с operation/requestId; исходное сообщение в лог не возвращается.
- Политика делает фиксированные lookup по 23 разрешённым полям; вложенные данные не обходятся. Большой исходный контекст помечается `truncated`, но метаданные в конце массива не теряются.

## Проверка

Команды из `api/` (PHP 8.4 и установленные Composer dependencies):

```sh
vendor/bin/phpunit --colors=never
vendor/bin/phpstan analyse --configuration=phpstan.neon --no-progress
vendor/bin/phplint --no-cache
vendor/bin/php-cs-fixer fix --config=public/local/php-cs-fixer.php --dry-run --diff --allow-risky=yes
php tools/verify-w01-http-logs.php /path/to/licensed/bitrix
php tools/verify-w01-exception-log.php /path/to/licensed/bitrix
php tools/verify-w00-router.php
```

Из корня: `python3 tools/verify-w00-inventory.py`. Локальный результат: **95 тестов / 521 assertions**, PHPStan, phplint, CS и обе проверки реального ядра — PASS. Фактические результаты — в `verification/`. Проверки с ядром запускаются отдельно: лицензированный Bitrix не включён в репозиторий и отсутствует в GitHub Actions. PHPUnit выполняется в обычном PR workflow.

AUTH/Notification/LeadHunter проверяются локальными тестами; запросы в production, реальные регистрации и сообщения в Telegram в W01 не отправлялись. Тела и статусы API не маскируются: очищается только диагностика. SQL, миграции и payload Telegram не изменяются.

## Подключение и ограничения

После ревью и merge W01 готова к включению в следующий согласованный deploy. Переключение frontend и реализация продуктовых модулей идут по следующим волнам. Deployment в эту работу не входит.

Защита распространяется на прикладные PHP-логи через `Log`, общий HTTP-клиент и настроенный файл исключений Bitrix. Она не очищает старые журналы, access/error logs reverse proxy, PHP до запуска обработчика или произвольный сторонний logger. Runtime-журналы проверяются при настройке окружения W04. Производственный `APP_DEBUG` остаётся выключенным; содержание HTTP debug-ответов этим PR не меняется.

Для отката используется предыдущий релиз; изменений схемы нет. Откат вернёт прежнее содержимое логов, поэтому предпочтительнее исправление вперёд. Ротация и путь `logs/bx_error.log` сохранены.
