# W02 — срок, состояние и отзыв сессии

## Ответственность и порядок ревью

Ветка `codex/w02-session-lifecycle`, отдельный PR поверх W01. Пока предыдущая волна открыта, base PR — `codex/w01-safe-http-logs`: diff содержит только W02. После принятия W01 base переводится в `main`, проверки повторяются на актуальном основании. Merge и production deploy выполняются после ревью разработчика. PR workflow принимает также base `codex/**`, чтобы проверять зависимые волны до их последовательного слияния.

Волна исправляет AUTH-01/login и AUTH-02/logout и повторно проверяет AUTH-03/request-code и AUTH-04/confirm. URL, поля запросов и успешные DTO сохранены. Продуктовые роли MoreFoto относятся к W06.

## Изменение поведения

| Сценарий | Результат W02 |
| --- | --- |
| Токен имеет пустой, повреждённый или отсутствующий срок | 401; бессрочная сессия не создаётся |
| `expiresAt <= now` | 401; граница проверяется фиксированными часами |
| Пользователь `ACTIVE=N` или ещё pending | Вход и разрешение Bearer запрещены |
| Повторный login | Заменяет единственный токен пользователя |
| Logout с текущим токеном | Атомарно очищает токен и срок |
| Старый logout после нового login | Новый токен сохраняется: сравнение `userId + token` с точным регистром |
| Legacy `ACTIVE=N` без нового признака pending | Request-code/confirm не меняют пароль и не активируют пользователя |
| Подтверждённый код | Повторный confirm не выдаёт новую сессию |
| Администратор сохраняет `ACTIVE=N` через Bitrix | Постоянный обработчик снимает pending и отзывает токен |

Общий технический `TokenResolverInterface` по-прежнему возвращает ID только действующего пользователя. Новый `TokenRevokerInterface` находится в `rebit.share/lib/Application/Contract/Auth/` и отзывает предъявленную сессию; он не предоставляет полномочия отозвать чужие сессии. Предметные контракты будущих модулей размещаются отдельно в `rebit.share/lib/Contracts/<Domain>/`. Часы и транзакции регистрации — внутренние порты Auth.

## Хранение и миграция

Существующая `UF_TOKEN_EXPIRES_AT` остаётся строкой. Старые migration IDs не изменяются: Bitrix не переводит тип существующего UF через обычный `CUserTypeEntity::Update`. Новые записи используют строгий UTC `Y-m-d\TH:i:s\Z`; читаются также прежние точные `d.m.Y H:i:s` и `Y-m-d H:i:s` в часовом поясе сервера. Неизвестный формат требует повторного login, а не разрешения бессрочной сессии. При переносе старых строк нельзя одновременно менять серверный часовой пояс без отдельного преобразования.

Миграция требует InnoDB для `b_user`, `b_uts_user` и таблицы confirmation: при другом движке останавливается, не обещая недействующий rollback. Новая активная миграция `Version20260911120001` добавляет boolean `UF_AUTH_REGISTRATION_PENDING` с default 0 и постоянный совместимый обработчик `OnBeforeUserUpdate` в `rebit.auth`. Наличие старого registration-confirmation не доказывает происхождение пользователя: автоматического backfill pending нет. Старые незавершённые регистрации разбираются отдельно администратором, не снимая административные блокировки.

Новая регистрация создаёт `ACTIVE=N + pending=1` и confirmation в одной транзакции. Pending также запрещён нативным Bitrix login за счёт `ACTIVE=N`. Resend обновляет пароль без записи `ACTIVE=N`, поэтому не имитирует административную блокировку. Confirm проверяет связанного пользователя, очищает pending, активирует его, помечает код и сохраняет токен атомарно. Ошибочная попытка фиксируется до возврата 400. Почтовый транспорт вызывается после commit; ошибка доставки сохраняет cooldown и допускает последующий resend.

Resend/confirm блокируют confirmation, затем пользователя и UF. Для проверки после блокировки используется текущая SQL-выборка `FOR UPDATE`: обычная ORM-выборка могла бы прочитать прежний snapshot при MySQL REPEATABLE READ. Изменения пользователя выполняются через `CUser`, кроме условного отзыва токена одной SQL-командой. Стандартный `CUser::Update` пишет `b_user` и UF отдельными командами. Поэтому обработчик административного disable сначала отзывает pending/токен отдельным атомарным UPDATE UF, до записи `ACTIVE=N`, и затем сохраняет те же поля в обычном CUser Update. Это закрывает окно, когда confirm мог увидеть прежний pending между двумя командами администратора. Если последующий административный Update завершается ошибкой, предварительный отзыв остаётся в силе: безопасный отказ требует нового login или ручного разбора pending. Прямой административный SQL вне Bitrix не запускает событие и должен явно отзывать pending/сессию; такой обход не является API блокировки.

## Карта ревью

1. `TokenExpirationParser`, `TokenResolver`, `UserRepository`: строгий срок, активность, pending, точное сравнение opaque-токена, условный logout.
2. Request-code/confirm: происхождение pending, связанные email/userId, блокировки, транзакционная запись, завершённый код, commit неверной попытки.
3. Миграция и `RegistrationStateHandler`: значение по умолчанию для legacy, срабатывание в Bitrix admin, сохранение нативного запрета login.
4. `di/auth.php`: singleton clock и transaction без состояния запроса, interface-key через `constructor`.
5. Тесты и integration verifier: границы времени, настоящий CUser/UF/UserTable, обработчик, rollback и текущая locking-read.

```sh

vendor/bin/phpstan analyse --configuration=phpstan.neon --no-progress
vendor/bin/phplint --no-cache
vendor/bin/php-cs-fixer fix --config=public/local/php-cs-fixer.php --dry-run --diff --allow-risky=yes
```

Отдельный integration runner использует лицензированный Bitrix и новую временную MySQL 8 без published ports и без рабочих томов. Команда из корня:

```sh
W02_KERNEL_ROOT=/path/to/licensed/bitrix \
W02_VENDOR_ROOT=/path/to/api/vendor \
W02_PHP_IMAGE=rabit-api-php-cli:20260911-074507 \
  bash api/tools/run-w02-auth-integration.sh
```

Нужен CLI image PHP 8.4 с mysqli и расширениями проекта; используется локальный `mysql:8.0` (переопределяется `W02_MYSQL_IMAGE`). Runner отказывается переиспользовать одноимённый существующий контейнер/сеть и удаляет только созданные им ресурсы. CLI bootstrap загружает настоящее ядро, CUser, UF и ORM на исходной установочной схеме; полный prolog/агенты не запускаются, CAPTCHA и почта заменены тестовыми адаптерами.

Локальный результат: **128 тестов / 607 assertions; 66 integration-проверок**, PHPStan, lint, CS и frozen inventory — PASS. Реальное ядро Bitrix **25.750.0**, MySQL **8.0.45**, PHP **8.4.23**. Дополнительно инструментом будущей W04 проверены 46 регистраций DI, 11 singleton-сервисов и 6 маршрутов. Результаты в `verification/`. Bitrix не включается в GitHub и этот прогон не заменяется PHPUnit-stub. В CI работают обычные PHPUnit/PHPStan/lint/CS и проверка frozen W00. Ограничения тарифа GitHub отражаются отдельно от локального результата тестов.

## Подключение и откат

На тестовом окружении сначала применить новую foundation-миграцию, затем включить W02 и проверить AUTH-01…04. Код с выборкой pending нельзя включать до миграции. Совместимость схемы позволяет применить миграцию перед переключением релиза; на время переключения регистрацию остановить, поскольку старый код не выставляет pending и может изменять заблокированных пользователей.

Перед production — резервная копия, согласованное окно и отдельно одобренный deploy. В этой волне production не изменялся, реальные письма/Telegram не отправлялись. Down удаляет обработчик и pending-поле; выполнять только после выключения W02-кода и с проверенным backup. Предпочтителен fix-forward: возврат старого приложения возвращает исправленные здесь уязвимости, а происхождение legacy pending не восстанавливается автоматически.
