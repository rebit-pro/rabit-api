# D3 — атомарные переносы ребёнка и служебной заявки

Ветка `codex/d3-child-transfers` от main `a43e4ea183dccf99659cd3c99322ba25f28ac1ce` (merge F2 `44f2e36`, PR #40, и документы его развёртывания); после ревью влит `main` `57b2a81` (PR #45). PR https://github.com/rebit-pro/rabit-api/pull/46.

- **Зависимости:** D2 (#21), F1 (#25), E5 (#37), F2 (#40) — в main. Гейты D03 и D05 приняты ранее. D11 принят 22.09.2026 по решениям D3-DEC-01…06, D12 снят с D3 по D3-DEC-07 (`decisionEvidence` в графах).
- **План и журнал:** `docs/plans/D3_child-transfers/`. Материалы оперативного PR #32, ранее занимавшие ID D3, перенесены в `docs/plans/OPS-stage-media-recovery/` (D3-DEC-08, #42 п. 3).

Организатор до передачи ссылки исправляет разметку: переносит весь набор ребёнка в другую группу того же типа (MED-07). Организатор или куратор проверяет заявку сотрудника и подтверждает льготный перенос наборов детей в папку сотрудников (HND-10/11), в том числе когда у ребёнка уже есть заказы. Перенос атомарен, сохраняет ID кадров, детей и связей и `originalGroupId`, не меняет заказы и сбрасывает подготовку ссылки затронутых групп.

## Контракты

| ID | Маршрут | Роли (D08) | Суть |
| --- | --- | --- | --- |
| MED-07 | `POST /api/v1/shoots/{shoot_id}/child-transfers` | О | Весь набор ребёнка в другую группу того же типа; обе группы в подготовке, без заказов |
| HND-10 | `GET /api/v1/staff-requests/{id}/transfer-preview` | О, К своей области | Полные наборы строк, целевые коды единственной staff-группы, `hasOrders`, `signature` |
| HND-11 | `POST /api/v1/staff-requests/{id}/transfers` | О, К своей области | Одна транзакция по подписи превью; `results`, статус `transferred` |
| HND-08 | `GET /api/v1/staff-requests/{id}` | О, К, В | Добавлены `results`; `rows[].childCode` — код на момент переноса |
| COM-13 | `GET /api/v1/orders/{id}` | О, К | `correctionPhotos` — кадры детей в их текущей группе, после переноса с новыми кодами |

- **Правила (D11, D3-DEC-01…06):**
  - заказы при льготном переносе не меняются, скидки задним числом нет; новые покупки — в папке сотрудников по D05, подарок считается внутри заказа;
  - кадр, общий с ребёнком, который остаётся, блокирует перенос (`SHARED_PHOTO`, коды кадров в `error.details.photoCodes`);
  - цель HND-11 — единственная staff-группа съёмки, не закрытая; коды — следующие свободные (A…Z, AA…), номера кадров сохраняются;
  - перенесённая обложка исходной группы заменяется первым оставшимся назначенным кадром, группе без обложки назначается первый перенесённый.
- **Коды ошибок:**
  - 409: `GROUP_KIND_MISMATCH`, `GROUP_LOCKED`, `CHILD_HAS_ORDERS`, `SET_CHANGED`, `TARGET_CODE_TAKEN`, `SHARED_PHOTO`, `REVISION_CONFLICT`, `SIGNATURE_CONFLICT`, `IDEMPOTENCY_CONFLICT`, `REQUEST_TRANSFERRED`, `REQUEST_NOT_SUBMITTED`, `STAFF_GROUP_REQUIRED`, `STAFF_GROUP_AMBIGUOUS`, `TARGET_GROUP_CLOSED`;
  - 422: `VALIDATION_FAILED`, `INVALID_PHOTO_IDS`, `CONFIRMATION_REQUIRED`, `INVALID_IDEMPOTENCY_KEY`, `UNKNOWN_FIELD`;
  - 403 `FORBIDDEN`, 404 `STAFF_REQUEST_NOT_FOUND`/`GROUP_NOT_FOUND`. Отказы Access переводятся в коды внутри D3 до исправления #42 п. 1.
- **Повтор:** `Idempotency-Key` обязателен для MED-07 и HND-11. HND-11 для уже перенесённой заявки после проверки прав отдаёт сохранённые `results` без второго переноса.
- Уточнения внесены в канонический `build.py` MoreFoto; воспроизводимый diff внешних файлов — `morefoto-contract.patch`.

## Устройство

- **Media** владеет перемещением:
  - `ChildTransfers` реализует `Rebit\Share\Contracts\Media\ChildTransferInterface`: блокировка ревизии медиа съёмки и строк детей, чтение полных наборов с совместными кадрами, перенос `mf_media_child.GROUP_ID/CODE` и `b_hlbd_mf_photo.UF_GROUP_ID` (+`UF_REVISION`), замена обложек, один шаг ревизии;
  - MED-07 — `TransferChildUseCase` в собственной транзакции Media и чистый `ChildTransferController`.
- **Handoff** оркестрирует льготный перенос одной транзакцией вызывающего:
  - порядок блокировок F2: состояние Access → группы Organization (исходные и staff, по возрастанию ID) → актор → идемпотентность → строка заявки → ревизия медиа и строки детей → проверка заказов Commerce;
  - блокировка строк детей до проверки заказов сериализует перенос с COM-10: заказ либо попадает в подпись (устаревшее превью → `SIGNATURE_CONFLICT`), либо после переноса получает `INVALID_CART`/`QUOTE_STALE`;
  - deadlock и lock wait повторяют всю команду до трёх раз (`BitrixHandoffTransaction(3)` только для HND-11);
  - результат по строкам — столбцы `TRANSFER_*` в `mf_staff_request_row` (миграция `Version20260922180001`), журнал повтора хранит только `id/revision/status`.
- **Commerce:** `ChildOrdersInterface` — дети с заказами по индексу `ix_mf_order_line_child`; заказы не меняются. Право сотрудника (`StaffEligibility` по `CHILD_ID`) сохраняется, потому что ID ребёнка не меняется.
- **F2:** отдельного флага нет — изменение кадров, связей, обложек и статуса заявки меняет подпись обеих групп, поэтому непереданная группа снова требует HND-03.
- **Frontend:** live-перенос в рабочем месте фото (диалог «Перенести набор ребёнка»), проверка и подтверждение на экране заявки с предупреждением о заказах; куратор видит коды кадров, миниатюры — только организатор (служебные превью).

## Подключение и ограничения

- Включается вместе с F2 на тестовом стенде; реальные покупатели — после N2. Платёжные последствия переноса (поздняя оплата, возврат) — I3.
- Инструмента разделения совместного кадра нет: такой набор не переносится (follow-up при первом реальном случае).
- Миниатюры в проверке заявки для куратора — вместе с доступом куратора к превью (I1).
- Отказы общих источников Access/Auth вне D3 по-прежнему отдают `SERVICE_UNAVAILABLE` (#42 п. 1).
