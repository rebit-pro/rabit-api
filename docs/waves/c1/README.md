# C1 — самостоятельное ядро учреждений

C1 выделена из прежней W07 по правилу независимого слияния. База — main `2ac4ef9b3e4b63d734fc3dda5240cab50a550d44` после A1–A6 (W00–W05). Открытая B1 (W06, PR #8) для этой волны не нужна.

## Что работает

Модуль `morefoto.organization`: создание учреждения, чтение реквизитов, изменение с ожидаемой revision и список с поиском/пагинацией. Новый HL `MfInstitution` хранит публичный UUID, name, address, revision и UTC timestamps. UUID уникален и сравнивается канонически; revision меняется атомарным UPDATE с проверкой прежней версии. Устаревшая команда ничего не перезаписывает.

Имя обязательно, 1–255 символов после trim; адрес можно заполнить позже, максимум 500 символов. Строки — корректный UTF-8 без NUL. Имена не уникальны. Поиск — регистронезависимый буквальный префикс name до 100 символов: `%`, `_`, обратная косая черта и апостроф не становятся шаблоном или SQL. Для него добавлен индекс name, для списка — createdAt+ID. Page 1–1000000, pageSize 1–100 (по умолчанию 50). Сортировка createdAt DESC, внутренний ID DESC; total и items вычисляются одним SQL statement, в том числе за пределами последней страницы.

Простое чтение использует D7 Result; сложный запрос списка — DB Result. Result заканчивается в Application. Даты, внутренний HL ID и метаданные чужих модулей не попадают в выходной DTO реквизитов.

## Установка и использование

В активном наборе foundation новая миграция `Version20260911210001`. Она создаёт HL, ограничения/индексы и регистрирует модуль. Предварительно нужны штатные highloadblock и rebit.share. Повторный up не создаёт вторую таблицу/модуль. Down допускается только для пустого справочника; uninstall модуля данные не удаляет.

Штатный `Loader::includeModule('morefoto.organization')` регистрирует namespace и DI. Поэтому C1 не редактирует общий Composer, init.php, routes registry, PHPStan или тестовые стабы, занятые другими волнами. Сервисы Get/List/Create/UpdateInstitutionUseCase разрешаются из DI; внутренние команды принимают InstitutionId/InstitutionDetails. Данные передаются аргументами, singleton не хранит состояние пользователя.

Это внутренний сценарий хранения, без HTTP-маршрутов и без CLI обхода служебных прав. Он **не реализует полный ORG-04**. C2 добавит защищённые ORG-02/03/05 после C1+B1; C4 соберёт полную карточку после структуры C3. Назначения curator/head/teacher, съёмки/группы, финансовая сводка и их история в C1 не имитируются. Поля назначений не дублируются в учреждении.

## Проверки и независимость

```sh
bash api/tools/run-c1-institutions-integration.sh
```

Runner создаёт отдельные `rabit-c1-tests` и `rabit-c1-mysql`, tmpfs-БД, без host ports и внешней сети. Сетевой alias позволяет использовать неизменённую main-фикстуру W02 одновременно с E1. При совпадении существующего имени runner останавливается; удаляет только свои ресурсы. Ядро/vendor читаются через параметры W02_KERNEL_ROOT/W02_VENDOR_ROOT; production .env не загружается.

Реальное ядро Bitrix проверяет native HL install, up/up/down/up, namespace, DI, CRUD, stale revision, поиск со спецсимволами, устойчивую пагинацию, единый запрос items/total и ограничения БД. Access на этом стенде не установлен. Полный prolog, HTTP и deployment не входят в этот внутренний срез.

Доказательства — `integration.json` и `verification.json`. Замороженный W00 и контрактные источники других волн не меняются. C1 можно влить до или после B1/E1; она разблокирует C2, но не делает отсутствующие зависимости C2 готовыми. Бизнес-цены и внешние интеграции здесь не затрагиваются.
