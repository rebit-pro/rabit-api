# RaBit API

Модульная серверная платформа на **PHP 8.4 и Bitrix D7**. RaBit API объединяет общие возможности, которые можно использовать в разных проектах: аутентификацию, работу с файлами, приём заявок, доставку уведомлений и внешнюю лидогенерацию. Предметные функции приложения добавляются отдельными модулями.

Репозиторий содержит backend и [frontend MoreFoto](frontend/README.md). В MoreFoto реализованы доступ сотрудников, учреждения и каталог; A8 подключает настоящий браузерный путь входа и редактирования каталога. Остальные функции развиваются независимыми волнами.

## Что уже есть

| Модуль | Ответственность |
| --- | --- |
| `rebit.share` | Общая HTTP/DTO-инфраструктура, техническая загрузка файлов, аудит, Messenger, адаптеры и межмодульные контракты |
| `rebit.auth` | Вход и выход, Bearer-токены, подтверждение регистрации по email |
| `rebit.notification` | Приём заявок с сайта, синхронная доставка текста и вложения в Telegram, резервный email при настройке |
| `rebit.leadhunter` | Получение заявок из RSS FL.ru, отбор по правилам, дедупликация, доставка в Telegram и резервный email |
| `morefoto.access` | Роли сотрудников, разрешения и назначения на учреждения |
| `morefoto.organization` | Учреждения и защищённые команды их изменения |
| `morefoto.commerce` | Каталог продукции, ревизии и идемпотентные команды |
| `rebit.dev` | Инструменты разработки и правила форматирования |
| `sprint.migration` | Управление версиями схемы и настроек Bitrix |

Notification и LeadHunter используют общие инфраструктурные адаптеры, но сохраняют самостоятельные сценарии. Универсальная очередь доставки уведомлений, платежи и остальные бизнес-процессы остаются в плане. Роли MoreFoto принадлежат модулю Access.

## Текущий HTTP API

Префикс — `/api/v1`. Реестр маршрутов: [rabit-api.php](api/public/local/routes/rabit-api.php).

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/auth/login` | Вход и получение токена |
| POST | `/auth/logout` | Отзыв текущей сессии |
| POST | `/auth/register/request-code` | Запрос кода регистрации |
| POST | `/auth/register/confirm` | Подтверждение регистрации |
| POST | `/share/file/upload/` | Техническая загрузка файла; завершающий слэш значим |
| POST | `/lead` | Приём заявки сайта |
| GET | `/me` | Профиль, роль и разрешения сотрудника |
| GET, POST | `/catalog/products` | Каталог и создание продукции |
| PATCH | `/catalog/products/{product_id}` | Изменение продукции |

Поля, авторизация и ответы описаны в [HTTP API](docs/api.md). Фоновый LeadHunter запускается командой `app:leadhunter:scan` и не добавляет REST-методов. Проверки доступа к объектам и роли реализует модуль конкретного сценария; наличие токена само по себе их не заменяет.

## Архитектура

```text
api/public/local/modules/rebit.<module>/
  lib/
    Domain/          # предметные правила и данные
    Application/     # сценарии, DTO и порты
    Infrastructure/  # Bitrix/HTTP/кеши и внешние адаптеры
    Presentation/    # контроллеры и CLI
    Shared/          # локальные общие элементы модуля
  di/                # конфигурация зависимостей
  routes.php         # маршруты модуля
  include.php        # bootstrap
```

Контроллер проверяет вход и формирует HTTP-ответ, UseCase выполняет сценарий, репозиторий обращается к данным. Для чтения используются D7 ORM с Result и массивными строками либо SQL сложного запроса; Objectify-коллекции для нового чтения не применяются. Result не выходит в HTTP, кеш и межмодульные контракты.

Общие технические контракты находятся в `rebit.share/lib/Application/Contract/`, предметные межмодульные — в `rebit.share/lib/Contracts/<Domain>/`. Зависимости передаются через конструктор; ServiceLocator используется только в bootstrap и DI. Новые маршруты подключаются явно в центральный реестр. Подробности — [архитектура](docs/architecture.md) и [правила проекта](AGENTS.md).

## Локальная разработка

Потребуются Docker/Compose, PHP 8.4 с расширениями из `api/composer.json`, Composer и отдельно подготовленное лицензированное ядро Bitrix. Секреты, ядро, загруженные файлы и данные БД в Git не хранятся.

1. Подготовить локальную конфигурацию по `.env.example` и ядро в `api/public/bitrix/`. Адреса и реквизиты внешних сервисов задаются для выбранного окружения.
2. Установить зависимости: `make api-composer-install`.
3. Запустить подготовленное окружение: `make up`.
4. Проверить статус миграций: `make api-migrate-status`. Применение миграций выполняется отдельно для нужной БД.

Активны семь миграций в [migrations.foundation](api/public/local/php_interface/migrations.foundation/README.md). Исторические P2P-миграции остаются в прежнем архивном checkout и не входят в новый репозиторий.

Проверки из каталога `api/` после установки зависимостей:

```sh
composer lint
composer cs-check
composer phpstan
composer test
```

Автономная проверка снимка API из корня репозитория:

```sh
python3 tools/verify-w00-inventory.py
```

Проверка реального Bitrix Router при наличии ядра, без выполнения контроллеров и миграций:

```sh
php api/tools/verify-w00-router.php
```

## Расширение под продукт

Новый модуль получает конкретную ответственность, собственные сценарии, миграции, DI и маршруты. Общие технические решения остаются в платформе; роли, правила продаж, доступ к галереям и другие предметные ограничения принадлежат продукту. Один модуль может развиваться в нескольких волнах.

Активный план MoreFoto содержит **40 независимых срезов A–N**, карту прежних **35 волн W00–W34** и **99 API-контрактов**. Большинство контрактов описывает будущую реализацию, а не доступные сейчас endpoint. См. [волны и порядок работы](docs/waves/README.md), [снимок плана](docs/waves/w00/snapshot/backend-waves.md) и [реестр API](docs/waves/w00/snapshot/endpoints.json). Канонические продуктовые документы остаются в отдельном проекте MoreFoto.

## Pull requests и выпуск

**Одна независимая волна — одна ветка `codex/<буква><номер>-...` от актуального main и один PR в main.** Все зависимости уже должны быть слиты. Перед merge обязательны тесты backend/frontend, реальные E2E затронутого сценария и визуальная проверка пользовательских экранов. Merge и deployment выполняются отдельно после ревью; автоматически новые PR не сливаются.

```sh
make test-e2e
```

Порядок работы с изолированным стендом и границы покрытия — [A8](docs/waves/a8/README.md). GitHub Actions отключён вручную; YAML сохранён, проверки выполняются локально. Изменение репозитория не переносит рабочие БД, тома или домены.
