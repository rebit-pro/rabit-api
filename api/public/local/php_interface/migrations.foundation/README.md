# Миграции основы RaBit API

Конфигурация `../migrations.cfg.php` назначает эту директорию набором по умолчанию для Sprint Migration. Она сохраняет прежнюю таблицу учёта `sprint_migration_versions`.

| Файл | Назначение |
| --- | --- |
| `Version20260321120016.php` | HL-блок `RebitAuditLog`, таблица `rebit_audit_log` для общего аудита |
| `Version20260323120001.php` | Пользовательские поля `UF_TOKEN` и `UF_TOKEN_EXPIRES_AT` для авторизации |
| `Version20260326120008.php` | Таблица `rebit_auth_registration_confirmation` для подтверждения регистрации |
| `Version20260326120009.php` | Событие `REBIT_AUTH_REGISTRATION_CONFIRMATION` и почтовый шаблон регистрации |
| `Version20260713120001.php` | Регистрация самостоятельного `rebit.leadhunter` и таблица внешних заявок |
| `Version20260715120001.php` | Почтовое событие резервной доставки лидов при сбое Telegram |
| `Version20260820120001.php` | Почтовое событие `REBIT_NOTIFICATION_LEAD` для резервной доставки заявок с сайта |

Это копии семи миграций прежнего проекта. Оригиналы и остальные исторические P2P-миграции сохранены в архивном checkout `rebit-p2p/api/public/local/php_interface/migrations/` и не перенесены в новый репозиторий RaBit API. Sprint читает файлы непосредственно из `migration_dir`; вложенная директория и этот README не являются дополнительной конфигурацией. Автоматически обнаруживаемые конфиги должны иметь имя `migrations.<name>.php` и находиться непосредственно в `php_interface`.

Номера версий сохранены. Уже применённые версии не должны повторно запускаться на существующей БД; смена директории не удаляет старые таблицы, данные или записи истории. Историческую базу P2P этот набор не преобразует в чистую базу RaBit API. Не следует запускать rollback или очищать таблицу истории для переключения набора.

В копии почтовой миграции заменён только видимый бренд `Rebit P2P` на `RaBit API`; имя события и макросы остались прежними. На существующей БД уже созданные шаблоны автоматически не обновятся, поскольку номер версии сохранён. Копии приведены к локальному PHP-форматированию. Из-за форматирования и изменённого текста письма контрольные суммы отдельных копий могут отличаться от записанных ранее; номера версий сохранены. Изменение существующих шаблонов при необходимости должно выполняться отдельной новой миграцией, без повторного запуска исторической версии.

## Условия новой установки

Нужны установленное ядро Bitrix с основными пользовательскими и файловыми таблицами, модуль `highloadblock` для аудита и установленный Sprint Migration. Модули `rebit.share` и `rebit.auth`, Composer autoload и маршрутизация регистрируются штатным bootstrap проекта; миграции Auth/Audit не устанавливают сами прикладные модули; миграция Leadhunter регистрирует его модуль.

Почтовая миграция привязана к сайту `s1`. Этот сайт должен существовать, а `REBIT_AUTH_MAIL_EVENT_SITE_ID` в конфигурации Auth должен совпадать с сайтом шаблона (по умолчанию `s1`). Для фактической доставки отдельно требуется настроенный почтовый транспорт Bitrix. Копирование и проверка PHP-синтаксиса не подтверждают доставку или успешное применение на конкретной БД.

## Известный блокер TTL токенов

Миграция `Version20260323120001.php` создаёт `UF_TOKEN_EXPIRES_AT` как `USER_TYPE_ID = 'string'` (строки 44–48). При этом `../../modules/rebit.auth/lib/Domain/User/Repository/UserRepository.php` в строках 38–42 принимает значение срока только как `Bitrix\Main\Type\DateTime`; строковое значение преобразуется в `null`. Затем `TokenResolver.php` в `Infrastructure/Adapter` проверяет срок лишь при ненулевом `expiresAt` (строка 34). Поэтому при схеме, созданной этой миграцией, TTL токена не обеспечивает ожидаемого истечения доступа.

Этот существующий дефект сохранён при выделении основы: контракт и поведение Auth в рамках извлечения не менялись. До использования авторизации в новой установке нужно согласовать и проверить отдельное исправление представления срока и тест чтения реального UF-поля. Одних unit-тестов с готовым объектом DateTime недостаточно.

В ходе выделения этой директории миграции не запускались; обращения к БД и изменения её состояния не выполнялись.

Leadhunter — отдельный действующий модуль лидогенерации, сохранённый по уточнению пользователя. Он не относится к P2P; его две версии возвращены в активный набор без изменения логики и номеров. При восстановлении исходников миграции не выполнялись; существующие таблицы и история остаются прежними.

Notification восстановлен как отдельный модуль приёма заявок с сайта. В активный набор возвращена почтовая миграция `Version20260820120001` с прежним номером; она не регистрирует сам модуль. Для новой установки используется installer `rebit.notification` после `rebit.share`. В существующей БД уже применённая версия повторно не запускается. Рабочие данные и история при восстановлении не изменялись; торговые шаблоны Notification в активный набор не возвращались.
