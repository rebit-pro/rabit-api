# Инструкция по последующей оптимизации E2E MoreFoto

Дата: 2026-09-23. Статус: шаги 1–5 реализованы в ветке `codex/ops-e2e-optimization`. Реализация, замеры и оставшиеся резервы описаны в разделе [«Реализация и результаты»](#реализация-и-результаты). Журнал задачи — [`docs/plans/OPS-e2e-optimization/`](../../docs/plans/OPS-e2e-optimization/progress.md).

## Цель и границы

Сократить длительность полного `make test-e2e` и сдерживать её рост при добавлении сценариев, сохранив состав обязательных проверок и достоверность результатов. Пользовательский ориентир текущего полного прогона — 10–12 минут.

Сохраняются backend/frontend-проверки, production-сборка frontend, реальные HTTP → nginx → Bitrix/PHP-FPM → MySQL-сценарии, необходимые очереди и обработчики, визуальная проверка пользовательских экранов desktop/mobile. Demo/Cucumber и mocks не заменяют реальный E2E. Успешный результат требует завершения всех обязательных этапов.

Документ не меняет правила `AGENTS.md` и не разрешает пропускать проверки перед merge. Merge и deployment остаются отдельными действиями после ревью.

Кроме браузерного времени, значения приблизительные: рассчитаны по интервалам записи соседних логов и могут включать запуск контейнеров и подготовительные действия. Таблица не является полным профилем гейта и не объясняет целиком заявленные 10–12 минут.

Подтверждённые особенности runner на момент просмотра:

- Каждый запуск создаёт новый том `node_modules` и выполняет `npm ci`; постоянный npm-кеш в runner не подключён.
- `npm run check` запускает `vue-tsc`, а `npm run build` запускает его повторно.
- PHPStan запускается с `--debug`; каталог `var/phpstan` находится во временном `/app/var` контейнера.
- Большинство этапов выполняется последовательно.
- Live Playwright использует `workers: 1`, `fullyParallel: false`, `retries: 0`.
- Сценарии используют общие учётки, изменяемые серверные данные и файлы фикстур; есть проверки пустого каталога и отзыва сессии.
- Node/Chromium ограничены двумя CPU и 3 ГиБ RAM. Документация A8 фиксирует OOM отдельного demo-набора при двух workers. Это не измерение потребления live-набора, но основание проверить память перед увеличением параллельности.

## Порядок реализации

### 1. Зафиксировать исходную точку

До изменения кода создать или актуализировать `plan.md` и `progress.md` в папке задачи по правилам корневого `AGENTS.md`. Проверить текущий `main`, зависимости, review/issue и состояние рабочего дерева.

Добавить измерение каждого этапа runner монотонными часами: образы, зависимости, frontend-проверки, сборка, запуск сервисов, backend-проверки, миграции/фикстуры, браузер, проверки данных после браузера, очистка. Сохранять длительность и результат также при ошибке; секреты и raw payload в отчёт не включать.

Зафиксировать commit и незакоммиченный diff, lockfile, образы, CPU/RAM, состав сценариев и результаты. Сравнить несколько прогонов на одинаковом коде и ресурсах, отдельно с холодным и прогретым кешем. Использовать медиану и диапазон; единичный удачный запуск не считать гарантированным ускорением.

### 2. Ускорить зависимости и убрать повторные вычисления

1. Подключить постоянный кеш скачанных npm-пакетов, сохранив `npm ci` и установку по lockfile. При отсутствии или повреждении кеша выполнять корректную чистую установку.
2. Если установка остаётся существенной затратой, подготовить образ с зависимостями. Ключ повторного использования учитывает `package.json`, `package-lock.json`, Node/npm, платформу, базовый образ и параметры установки. Не использовать произвольный старый `node_modules`.
3. Выполнять проверку типов один раз в полном гейте на неизменном снимке исходников. Сохранить проверку типов у самостоятельной команды `npm run build`; для оркестратора допустим отдельный шаг сборки после успешного `check`.
4. Убрать `--debug` из обычного PHPStan-прогона и подключить сохраняемый штатный result cache. Анализировать весь установленный набор путей с теми же правилами. Учесть конфигурацию, зависимости, PHP, stubs и расширения при инвалидировании кеша. Диагностический режим оставить доступным отдельно.
5. Сохранять Docker build cache; готовые образы повторно использовать только при соответствии входным файлам и среде текущего checkout.

Production-сборка обязана соответствовать проверяемому коду. Тестовые БД, очереди и изменяемые данные не становятся общими между независимыми запусками ради кеширования.

### 3. Совместить независимые этапы

Организовать зависимости этапов так, чтобы backend-проверки и frontend-проверки могли выполняться одновременно, а запуск MySQL/RabbitMQ перекрывался со сборкой. Браузер запускается после готовности сборки, схемы, фикстур и сервисов.

Ограничить общую нагрузку с учётом WSL/Docker и ресурсов машины. Независимые процессы не должны изменять общие выходные файлы. Ошибка любого обязательного этапа блокирует успешный результат; очистка собственных ресурсов работает также при ошибке, таймауте или отмене.

### 4. Подготовить E2E к параллельному исполнению

Сначала устранить зависимости между сценариями, затем увеличивать число workers:

1. Выделить независимые группы сценариев и описать их фикстуры.
2. Обеспечить отдельные учётки и данные для параллельных групп. Отзыв сессии или изменение роли в одном сценарии не должен ломать другой. Между тестами одного worker также обеспечить предсказуемое исходное состояние.
3. Убрать зависимость от порядка файлов, чужих созданных записей и общего пустого каталога; каждый сценарий готовит необходимые ему предусловия.
4. Разделить файлы фикстур, отчёты, артефакты, media и другие изменяемые выходные пути. Включить проверки данных после браузера в соответствующую группу.
5. Для групп, которые сложно изолировать внутри одного backend, использовать отдельные стенды с БД, очередями, обработчиками и файловым хранилищем. Сборку и неизменяемые зависимости можно разделять между стендами.
6. Сравнить один и два workers по времени, пику RAM и стабильности. Дальнейшее увеличение или sharding между машинами вводить по измерениям.

Итоговый гейт должен удостовериться, что все ожидаемые сценарии выполнены и все части завершились успешно. Сравнивать состав сценариев, а не только произвольный нижний порог количества тестов. Повторы не должны скрывать появившиеся гонки.

### 5. Сократить цикл разработки

Для промежуточных правок предусмотреть быстрый запуск проверок затронутой области. Перед merge сохранять полный обязательный гейт и проверки затронутого UI desktop/mobile.

Быстрый запуск не выдаётся за полную приёмку. Перенос обязательной проверки только в ночной запуск не считается оптимизацией с сохранением текущего контроля качества.

## Критерии приёмки оптимизации

- На одинаковом исходном коде сохранены обязательные этапы, состав сценариев и проверяемые свойства.
- Нет новых пропусков, нестабильных падений, OOM и зависимостей от порядка запуска.
- Ошибка обязательной проверки или отсутствие ожидаемого результата блокирует зелёный гейт.
- Чистый запуск без кеша работает; изменение зависимостей, конфигурации или среды корректно инвалидирует соответствующий кеш.
- Реальные API, хранилища, миграции и значимые интеграции продолжают проверяться; demo/mocks не подменяют этот путь.
- Независимые запуски не загрязняют данные друг друга; очистка удаляет только ресурсы своего запуска.
- Сравнение до/после воспроизводимо; отдельно указаны холодный и прогретый кеш, оборудование, число workers, состав тестов и границы покрытия.
- Фактические команды и результаты внесены в `progress.md`; непройденные проверки не отмечены как `PASS`.

Первый приоритет — зависимости, повторная проверка типов и совмещение подготовки. Второй — изоляция и параллельный запуск браузерных сценариев. Конкретный выигрыш во времени фиксировать только после измерений.

## Реализация и результаты

Дата замеров: 2026-09-23. Все прогоны выполнены на одной машине (WSL2 и Docker Desktop, 20 логических CPU, 15,9 ГиБ RAM; в покое занято около 8,1 ГиБ) на коде `main` `aee6808`. Общие параметры:

- образы `rabit-api-php-cli:d1-local` и `rabit-api-php-fpm:d1-local`;
- 77 браузерных сценариев без opt-in bench;
- 4 MySQL-верификатора, Notification, PHP lint/PHPStan/PHPUnit, frontend lint/types/unit/production build.

### Что сделано

1. **Замеры.** Каждый этап runner записывает в `state.json` время старта, длительность и статус: `passed`, `failed` или `cancelled`, в том числе при ошибке и отмене. В конце печатается сводка. В `state.json` также фиксируются:
   - commit, изменённые пути и SHA-256 незакоммиченного diff;
   - hash lockfile и ID образов;
   - CPU/RAM машины;
   - состав сценариев по группам и spec-файлам.
2. **npm.** Скачанные пакеты хранятся в томе `rabit-e2e-npm-cache`. Сама установка по-прежнему выполняется `npm ci --prefer-offline` по lockfile с проверкой целостности. Образ с готовым `node_modules` не вводился: с прогретым кешем установка занимает 14–24 с вместо 72–114 с. `vue-tsc` и Vite пишут в `node_modules`, поэтому общий том только для чтения не подходит.
3. **Типы.** `npm run build` = `typecheck` + `build-only` — самостоятельная команда по-прежнему проверяет типы. Оркестратор раскладывает `npm run check` на входящие в него скрипты и запускает их одновременно с unit и `build-only`. Сборка используется только после успеха всех проверок.
4. **PHPStan.** Запуск без `--debug`. Result cache хранится в томе `rabit-e2e-phpstan-cache`. `api/tools/e2e/phpstan.neon` подключает основной конфиг без изменений правил и путей и ограничивает PHPStan двумя процессами под лимит `--cpus 2`. Без ограничения PHPStan запускал больше процессов и занимал 1,31 ГиБ при лимите 1,5 ГиБ.
5. **Совмещение этапов.** Одновременно идут frontend-ветка, backend-ветка и MySQL/RabbitMQ всех стендов. Отсутствующие PHP-образы собираются параллельно со штатным Docker build cache.
6. **Fail-fast и отмена.** Первая ошибка сразу удаляет одноразовые контейнеры запуска. SIGINT/SIGTERM/SIGHUP ведут к той же очистке: раньше SIGTERM оставлял контейнеры и тома. Удаляются только ресурсы с меткой своего запуска, общие кеш-тома сохраняются.
7. **Браузер.** Сценарии разделены на две группы в `frontend/e2e/live/groups.json`. Каждая группа идёт на отдельном свежем стенде: своя MySQL, RabbitMQ, FPM, media worker, nginx и runtime.
   - A: catalog, conditions, organization, staff, z-institution-detail, zz-media, zz-notification — 46 тестов.
   - B: zzz-handoff, zzzz-links, zzzz-storefront, zzzzz-orders, zzzzzz-transfers — 31 тест, плюс верификаторы storefront, orders, links и transfers.

   На одном стенде A, затем B повторяют прежний порядок файлов. Конфиг Playwright и runner отказываются запускаться, если spec не входит ровно в одну группу. Гейт сверяет состав: в результатах группы есть все её spec-файлы, нет unexpected/skipped/flaky и ошибок загрузки, выполнены все группы. Файлы фикстур и отчёты разделены по стенду и группе в `api/var/e2e/<run>/`.
8. **Режимы.** `E2E_STANDS=1` выполняет группы по очереди на одном стенде. `E2E_GROUPS=b` запускает частичный прогон с меткой `PARTIAL run, not a full gate` в выводе и `state.json`. `make e2e-up/e2e-test/e2e-down` работают как раньше, на одном стенде.
9. **Xdebug.** В PHP-контейнерах стенда задан `XDEBUG_MODE=off`, как в production-образах, где Xdebug нет. Раньше FPM на каждый запрос пытался подключиться к отладчику. Медиана API-запроса снизилась с 27,1 до 16,1 мс, суммарное время PHP за браузерный набор — с 42,6 до 26,4 с.

| Новый runner | холодные (тома удалены) | 2 | 302 с | 127 с | 161 с |
| Новый runner | прогретые | 2 | 269 с | 62 с | 196 с |

До этой работы гейт на `c304270` занимал 9 мин 39 с (`npm ci` без кеша — 114 с). Длительность браузерных групп колеблется от запуска к запуску:

- фоновая нагрузка машины: в одном из прогонов группа A заняла 196 с вместо 157–168 с;
- ожидание смены минуты в `zzzz-links`: от 24 до 57 с.

### Память

Пик суммарной памяти контейнеров запуска: 4,0–4,1 ГиБ на двух стендах и 3,6 ГиБ на одном. Пик приходится на одновременные typecheck (1,1 ГиБ), сборку (1,0 ГиБ), lint (0,57 ГиБ) и две MySQL (по 0,67 ГиБ). Пик занятой памяти хоста: 11,9–12,8 ГиБ против 10,8 ГиБ у старого runner. У старого runner контейнеры без меток, поэтому поконтейнерного пика для сравнения нет. OOM, пропусков, повторов и flaky не было.

Два одновременных полных гейта на машине с 16 ГиБ могут упереться в память. Для таких случаев и для машин с малой RAM есть `E2E_STANDS=1`.

### Проверенные свойства

- Холодный запуск без кеш-томов проходит.
- После прогрева PHPStan пишет «Result cache restored. 0 files will be reanalysed». Изменение содержимого одного PHP-файла приводит к повторному анализу этого файла. Смена `level` сбрасывает кеш: «metadata do not match: projectConfig, level».
- Ошибка типов останавливает гейт через 49 с: остальные этапы отменяются, ресурсы запуска удаляются.
- SIGTERM процессу runner во время браузера даёт код 143, и ресурсов запуска не остаётся.
- `up` → `test` → `down` на одном стенде: 77 сценариев, 4 верификатора, очистка.
- Spec вне групп или несуществующий spec в группе дают ошибку конфигурации.

### Оставшиеся резервы

1. `zzzz-links` ждёт смены минуты, это до 60 с в группе B. Сценарий можно перестроить так, чтобы предусловие не зависело от текущей минуты. Это изменение теста: только отдельной задачей и с сохранением проверяемого свойства.
2. Сейчас критический путь — группа A (157–196 с). По анализу зависимостей возможны три группы:
   - catalog, conditions, organization;
   - staff, z-institution-detail, zz-media, zz-notification, zzzz-links и verify-links;
   - handoff, storefront, orders, transfers и их верификаторы.

   Ожидаемая браузерная часть — около 100–130 с. Каждый стенд добавляет около 1,7 ГиБ RAM (MySQL, RabbitMQ, FPM, nginx, Chromium), поэтому вводить только после замера на целевой машине.
3. Два Chromium и два FPM конкурируют за CPU: на отдельных стендах группы идут на 10–20 % медленнее, чем по одной.
4. `npm ci` с прогретым кешем занимает 14–24 с. Копия готового `node_modules`, ключом которой служат lockfile, образ и параметры установки, сэкономила бы около 10 с. Выигрыш не оправдывает сложность, пока установка не станет заметной долей гейта.
